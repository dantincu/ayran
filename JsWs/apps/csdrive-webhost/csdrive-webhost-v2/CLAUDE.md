# CsDrive WebHost

Inside `csdrive-webhost-tauriapp`, the Tauri app's main window always shows the admin-app (see below) — its own bundle lives in an `admin` folder directly inside the machine app data folder, a sibling of a `user` folder meant purely for arbitrary user-authored content. The user can still write their own `.html` files anywhere under `user` (e.g. `user/index.html`, `user/myapp/index.html`), but those are only ever opened as *secondary* windows (via the admin-app's own Files tab or Apps tab — "Open as web app"/"add a new window entry") — placing one at `user/index.html` does not make it the main window's content the way it originally did before the admin-app took over that role permanently.

## Folder layout

**Where all of this lives is defined in exactly one place: `csdrive-webhost-tauriapp/src-tauri/src/layout.rs`** — `DEFAULT_DATA_FOLDER` (the default data folder; `%APPDATA%\com.ayran.csdrive-webhost-tauriapp` today), `ADMIN_BUNDLE_PATH` (the admin bundle file, relative to it; `admin/dist/index.html` today), and the `admin`/`user` folder names. Nothing else hardcodes them: the backend, the keychain entry names (the last component of `DEFAULT_DATA_FOLDER`), the `seed_demo_data` example (`#[path]`-includes that file) and the admin-app (which asks the backend for the user folder via `get_user_folder`) all derive from it. To run the app **completely isolated** from real data (e.g. for tests), set `DEFAULT_DATA_FOLDER` to a scratch absolute path (`r"C:\Temp\csdrive-isolated-test"`) and rebuild: the run gets its own data folder, database, admin bundle and keychain entries, and can't reach the real one. (The WebView2 browser-storage profile is still shared, as it is keyed by the app identifier; the app keeps no state there.) Remember to set it back.

Both folders sit directly under the data folder (the default above, or wherever Settings' "Change data folder" points):
- `admin/dist/index.html` — the admin-app's own single-file bundle, served to the main window via the `csadmin://` custom protocol (which serves `admin/dist/` as its root, so the URL is `csadmin://localhost/index.html`). The app makes this file byte-identical to the copy embedded in the binary (see "Bundling the admin-app into the installer" below) **on every start**: that installs it on a fresh install or after "Delete app data", updates it when the app is upgraded, and undoes any tampering (the admin window is the privileged one, so nothing may persist changes to its code). Anything else found in its folder is deleted. So during development, rebuild the Tauri app after building the admin-app; a bundle copied in by hand is replaced at startup. `data.db` sits next to `dist/`, not inside it, so it can never be served.
- `admin/data.db` — this app's own SQLite database (secondary windows/tab groups/tabs/tags, the generic `app_state` table, etc. — see `secondary_windows::init_db`).
- `user/` — arbitrary user-authored `.html`/`.js`/`.css`/etc., served to secondary windows via the `csuser://` custom protocol. The backend never reads anything from here except in response to the admin-app explicitly asking to open/list something in it.

Both folders are created unconditionally at startup (`lib.rs`'s `.setup()`), regardless of which files inside them do or don't already exist.

Now let's go inside folder csdrive-webhost-admin-reactapp and there create a react app that builds all its bundle in only 1 file and, when installed by the backend as the admin bundle file (`ADMIN_BUNDLE_PATH` in `layout.rs`), it will be able to "talk" to the backend of our app just like a regular tauri frontend app communicates with the tauri backend. The actual app will act like a file manager for the %APPDATA%\com.ayran.csdrive-webhost-tauriapp\user root folder, along with a file manager for filen.io cloud storage provider (with possibility to allow multiple users to be connected), and a sqlite management studio that performs all types of operations upon sqlite database files from inside the %APPDATA%\com.ayran.csdrive-webhost-tauriapp\user folder.

`csdrive-webhost-userapps/` holds source for small standalone apps that can be *deployed* — copied as a new folder of `.html`/etc. content into the `user` root — via the admin-app's own Files tab (see "Deploying apps" below), as opposed to `csdrive-webhost-admin-reactapp`, which is the one privileged app that's always built into the installer and always occupies the main window.

## App state storage: data.db, not browser storage

An app's own UI-state persistence (active tab, last-browsed folder, collapsed groups, ...) belongs in the app-owned `data.db` (see the generic `app_state` table in `secondary_windows`'s crate — `get_app_state`/`set_app_state`), *not* IndexedDB or Web Storage. Reason: the data folder can be relocated (see the Settings tab / `data_location`) precisely so testing can switch between profiles, but browser storage lives in the fixed WebView2 profile rather than wherever the data folder currently points — so it never actually switched with the rest of the app's data. Rows are namespaced by an `app_id` — the relative path of the html file the window was opened from (from `user/` for a secondary-window app, or just `index.html` for the admin-app itself, served from `admin/`) — which the **backend** works out from the calling window itself (`get_app_state`/`set_app_state` take no app id; any one a caller sends is ignored), so an app can only ever reach its own state — so the same app keeps separate state when copied to more than one location on disk, and multiple apps sharing this one database never collide. This applies to every app in `csdrive-webhost-userapps/`, present and future; the admin-app's own `src/lib/appState.ts` is the reference implementation. It does not apply to browser storage a user explicitly creates through a generic inspection tool (e.g. admin-app's Storage tab) — those are arbitrary by design and named by the user, not the app, and have nothing to do with an app's own settings. If an app used browser storage for this before switching to `data.db`, it's fine to just abandon the old IndexedDB database/keys rather than migrate their contents, unless they hold data too valuable to lose.

**The admin-app writes nothing to browser storage.** Verified against a pristine WebView2 profile after using every tab: `localStorage`, `sessionStorage`, IndexedDB, cookies, the Cache API, service workers and OPFS are all empty, and the profile holds no data for the admin origin beyond the engine's own bookkeeping (navigation history, site-interaction and preference records, which any webview keeps for any page). The only code that touches these APIs is the Storage tab, on the user's explicit action. Keep it that way: new admin-app state goes through `appState.ts` (`data.db`).

## What the backend exposes to web apps (capabilities)

User-provided web apps run in secondary windows (label = the window guid); the admin-app is the window labelled `main`. Tauri capabilities are per window label, so `src-tauri/capabilities/` has two files, and **every new command must be listed in `build.rs` and granted in exactly one of them**:

- `user-apps.json` (`windows: ["*"]`, so it covers the admin window too) — everything a web app is meant to be able to do: files under the user folder and folders the user picks with a native dialog (the fs plugin's *runtime* scope: at startup we allow the user folder, and native dialogs add whatever the person picks; the fs permissions in the capability are granted bare, with no static path scope. A web app finds the user folder with `get_user_folder`, then passes absolute paths to the fs commands); SQLite on `.db` files in those same places (below); Filen.io file operations on the accounts the user has connected (below); on Android, folders the user picked with the native folder picker (`device_*`, see "Android"); managing app windows, tab groups, tabs and their tags; reporting itself as a tab (`init_window_tab` etc.); and its own `get_app_state`/`set_app_state`. Deliberately **not** granted: system/OS/app/window introspection (`core:default` — app version, monitors, paths…), event emitting, connecting/disconnecting Filen accounts.
- `admin.json` (`windows: ["main"]`) — extras only the admin-app gets: `filen_login`/`filen_logout` (the only place a Filen password is ever typed), data-folder relocation and "Delete app data", the bundled-app deploy commands, `save_to_device` (Android export to Downloads), and path resolution. The capability files can't tell the admin-app from a web app on Android (see "Android" below), so those commands also call `window_host::require_admin`, which is what actually enforces it there — and on desktop too.

**SQLite** is our own (`sqlite_db.rs`), not `tauri-plugin-sql` (which opens any path on disk): `sqlite_load` takes an absolute path or one relative to the user folder, resolves symlinks/`..`, and refuses anything outside the fs scope; the returned handle only works in the window that loaded it and is closed when the window closes. SQL can itself name files, so every connection also runs under an authorizer: `ATTACH` is allowed only for in-memory/temp databases or absolute paths inside the same scope, `PRAGMA temp_store_directory`/`data_store_directory` and `load_extension` are denied, and `VACUUM INTO` (which SQLite doesn't route through the authorizer) is refused by a token scan of the statement. (Without these, `ATTACH DATABASE '…/admin/data.db'` read straight past the path check.) `sqlite_execute(db, query, values)` → `{rowsAffected, lastInsertId}`; `sqlite_select(db, query, values)` → array of `{column: value}` (BLOBs as byte arrays).

**Filen.io lives entirely in Rust** (`src/filen/`: `crypto.rs`, `api.rs`, `ops.rs`, `mod.rs`; ported from the Ayran Notes app's Rust client). No credential ever reaches a webview: the connected-accounts list (user id + email) is a table in `data.db`, and every account's session (API key, master keys, name-hash key; the RSA private key is used once at login and never kept) is in one encrypted file in the data folder, `layout::FILEN_SESSIONS_FILE` (`admin/filen-sessions.enc`), so it travels with `data.db` when the folder is relocated and is gone when the folder is wiped. Web apps identify an account by its numeric `userId` and call, with Filen paths (`/`, `/Folder/file.txt`): `filen_list_accounts` → `[{userId, email}]`, `filen_readdir` → `[{name, isDirectory, size, mtimeMs}]`, `filen_stat`, `filen_read_file` (returns an `ArrayBuffer`), `filen_write_file` (creates or replaces; the bytes are the raw request body, the account and path go in headers: `invoke('filen_write_file', bytes, { headers: { userId: String(id), path: encodeURIComponent(path) } })`), `filen_mkdir` (recursive), `filen_rm` (to trash), `filen_rename` (also moves). `src/lib/filen.ts` is the reference wrapper. Crypto is tested against vectors from Filen's own JS SDK (`@filen/sdk`); accounts on auth version 3 salt name hashes with an HMAC key derived from the RSA private key (fetched at login). 

The `csadmin://` protocol serves `admin/dist/` only, and only to the `main` window. The sample dashboard's CPU/memory numbers are just `Math.random()` — the backend has never exposed system info.

## Secrets at rest (`secure_store.rs`)

One random 32-byte key, generated the first time it's needed and kept in the platform key store (desktop: the OS keychain via the `keyring` crate — Credential Manager / Keychain / Secret Service, entry `app-encryption-key` under the service name from `layout::keychain_service()`; Android: the Android Keystore, see "Android"), encrypts everything sensitive that we persist. The sensitive data itself lives in ordinary AES-256-GCM files (`nonce(12) || ciphertext+tag`, written atomically) inside the data folder: the Filen sessions file (above) and the small pointer file (`data-location.enc`, in the *default* data folder) that records a relocated data folder. The key store therefore only ever holds 32 bytes (no entry-size limits), and the only platform-specific code is `platform::resolve_key`. **iOS is not implemented yet** — `resolve_key` returns an error there (rather than keeping the key unprotected); implement it with the iOS Keychain and nothing else in the module changes. (`keyring` is a desktop-only dependency in `Cargo.toml` for that reason.) New secrets should be added the same way: a JSON structure written with `secure_store::write_json`.

## No network access for any window (CSP)

Every page we serve (`csuser://` and `csadmin://`, so user web apps and the admin-app alike) carries a `Content-Security-Policy` header (`CONTENT_SECURITY_POLICY` in `lib.rs`) under which a script can reach only its own origin's files, `data:`/`blob:` URLs, and the IPC channel to this backend (`ipc:` / `http://ipc.localhost`) — `fetch`, XHR, WebSocket, EventSource, beacons, external scripts/styles/images/fonts/frames and form posts to anything else are all blocked, and `default-src` is `'none'` so anything not listed is too. Inline scripts/styles remain allowed (the admin bundle is one inlined file); `eval` is not. CSP doesn't cover navigating the window itself, so `lock_down_navigation` (`on_navigation` + denying `window.open`) confines every window to our two origins — applied to the main window and every secondary window, so any new window builder must use it. A web app that needs anything from outside talks to it through a backend command (as Filen does), never directly. To add an exception, edit the constant and its test (which asserts the policy names no external host).

## Android (and every other platform)

**Standing rule: everything in this app — what exists and everything added from now on — must work on Android as well as on desktop.** Check each new feature on the emulator, and keep desktop-only code behind `#[cfg(desktop)]` with a real Android counterpart (or an honest "not available on this platform" that the UI hides).

**Building.** The crate is a lib (`src/lib.rs`, `pub fn run()`, `#[cfg_attr(mobile, tauri::mobile_entry_point)]`) plus a two-line `src/main.rs`. The Android Studio project is `src-tauri/gen/android` — generated by `cargo tauri android init` but **committed and hand-edited**: `MainActivity.kt` (edge-to-edge + the safe-area bridge), `SecureKey.kt` and `DeviceFiles.kt` (Kotlin helpers Rust calls over JNI). Build the admin-app first (`npm run build`), then, from `csdrive-webhost-tauriapp`: `cargo tauri android build --debug --target x86_64 --apk` (needs `ANDROID_HOME`, `NDK_HOME`, and **JDK 17** as `JAVA_HOME` — Android Studio's bundled JDK 25 breaks Gradle). Testing without a device: an emulator (`quick_notes_pixel_34`, headless), `adb install -r` (keeps app data), and Chrome DevTools remote debugging (`adb forward tcp:9222 localabstract:webview_devtools_remote_<pid>`, then the CDP HTTP/WebSocket API) to run `window.__TAURI__.core.invoke(...)` in the pages. In Git Bash set `MSYS_NO_PATHCONV=1` for adb. The emulator's app data is its own — nothing touches the desktop data.

**Windows on Android** (`window_host.rs`, the one place that knows the difference). Desktop opens real OS windows; a phone has one webview, so the "windows" model becomes *navigating that webview* between the admin-app and web apps. A window entry (`secondary_windows` row) is **open** while its page is showing, **suspended** when the user leaves it (Back, another app, the admin-app: entry and tabs are kept, `reopen_secondary_window` navigates back), and deleted by an explicit close. Opening app B from app A suspends A. `activate_tab` navigates to the tab's window. All the commands (`open_new_/reopen_/suspend_/close_/close_all_/suspend_all_secondary_window(s)`, `focus_`, `activate_tab`) keep their signatures on both platforms. Which window a call comes from is worked out from the page's *origin* plus `HostState.active`, never from the window label (there's only `main`): `window_host::caller_guid`/`caller_key` give web apps their identity (app state, SQLite handles), `require_admin` gates admin-only commands.

**Custom protocols.** On Windows and Android the scheme `x://localhost/...` is served as `http://x.localhost/...`. `WebviewUrl::CustomProtocol` converts it when a window is built, but `navigate()` does not — always go through `window_host::navigation_url` (Android showed `chrome-error://chromewebdata` without it). Custom-protocol pages count as local, so capabilities can't scope by URL (hence `require_admin`).

**System bars and the safe area.** Tauri apps fill the whole screen on Android, under the status bar and the gesture/navigation bar. Android's WebView reports `env(safe-area-inset-bottom)` as 0, so `MainActivity.kt` measures the real insets (system bars + display cutout, in CSS px) and publishes them as CSS variables `--csdrive-safe-area-inset-top/right/bottom/left` on `<html>` (an initialization script on every page reads them from the `CsdriveSafeArea` JS interface and `__csdriveApplySafeArea` keeps them current). They are 0 when the bars are hidden, so a full-screen mode simply gets the whole screen — **the trigger for a full-screen mode isn't built yet**. The css that consumes them (`SAFE_AREA_CSS` in `code_snippets.rs`: pad `<html>` by the four variables, `height:100%`) reaches every page not because each web app copies it but as a **code snippet**: `init_window_tab`'s response has a `codeSnippets` list of `{ code, type }` entries (`type`: `css`, `html` or `javascript`; today one css entry), and `get_code_snippets` returns the same list. **Web apps must apply the snippets they receive** (`sample-apps/qwer/_tab-lib.js` does — `TabLib.applySnippets`, also called automatically for `openTab`'s response and on load; the admin-app does it before its first render, `src/lib/codeSnippets.ts`). Anything platform-specific that every page needs should be added to that list rather than asked of each web app. Layout inside the admin-app therefore uses `height:100%`, not `100vh`.

**Secrets.** `secure_store` on Android keeps the 32-byte key wrapped by an Android Keystore key (`SecureKey.kt`; the wrapped blob is in the private `csdrive_secure_store` preferences); Rust reaches it through `android_jni.rs` (`on_activity`, `helper_class` — the activity's class loader is required to find our own classes). Verified: same key across restarts.

**Admin-app differences** (`src/lib/platform.ts`: `isMobile` from the user agent). No custom data folder (`pick_and_set_custom_data_folder` errors; `DataFolderInfo.canRelocate` is false and Settings hides it). "Add root folder" works differently — see "Device folders" below. Uploads use the webview's own `<input type="file">` chooser (`pickFilesFromDevice`) because the native dialog returns content URIs the fs scope can't cover. Exports go through `save_to_device` (`device_files.rs` + `DeviceFiles.kt`): admin-only, the bytes are the request body and the name a header, stored in the public Downloads folder via MediaStore (no permission needed on Android 10+; a name collision gets ` (1)`); `exportToDevice` picks the desktop save-dialog or this. Byte payloads to the backend go through `invokeWithBytes` (see "Sending bytes to the backend"). "Delete app data" ends the process on mobile (`app.restart()` can't relaunch there) — the next launch starts fresh.

**Device folders (Android's "Add root folder").** The official dialog plugin has no folder picker on mobile (`FolderPickerNotImplemented`), and Android hands out `content://` URIs (Storage Access Framework) that path-based fs can't use. So a folder picked on Android is a *device root*, handled like a Filen account rather than by the fs plugin: `device_roots.rs` wraps the community crate `tauri-plugin-android-fs` (Rust API only — `default-features = false`, so none of the plugin's own JS commands exist and a webview can't reach it) behind `pick_device_root` / `list_device_roots` / `remove_device_root` and `device_readdir`/`_stat`/`_exists`/`_read_file`/`_write_file`/`_mkdir`/`_rm`/`_rename`, each taking a `rootId` plus a root-relative `/` path (`..` refused). Picking asks Android for read-write access to the tree and **persists it across restarts**; roots are remembered in `data.db` (`device_roots`), so the Files tab shows them again next launch (`fileRoots.ts`: `FileRoot.kind` is `'local'` for the user folder and desktop dialog picks, `'device'` for these; every root-relative operation dispatches on it, so the rest of the Files tab is oblivious). Removing a root releases the permission; "Delete app data" releases them all. Available to all windows like every file capability, so a web app can ask the user to pick a folder and use it. Behaviour to know: deletes are **permanent** (document providers have no trash); a move across folders is copy-then-delete (Android can only rename in place); `rename` never overwrites; created names may be sanitised by the provider. Not possible on these roots: **SQLite** (it needs a real file path — copy the database into the user folder), and `Open as web app`/deploy (they need `user/`). On desktop the `device_*` commands exist but `pick_device_root` errors and `list_device_roots` is empty; desktop keeps dialog + fs. Verified on the emulator: pick, list, read, create/replace (with truncation), nested create, non-ASCII names, rename, move file and folder, delete, restart persistence, removal releasing the grant, and 20 MB byte-identical round trips.

**Sending bytes to the backend.** Android's WebView can't hand a POST body to a custom protocol, so Tauri's IPC there falls back to postMessage, where a `Uint8Array` becomes a JSON array of numbers — 20 MB is tens of millions of JSON values (11 s and a huge memory spike in testing). Commands that take a file's bytes (`filen_write_file`, `device_write_file`, `save_to_device`) therefore read them through `ipc.rs` (`body_bytes`, `field`), which accepts the raw body + percent-encoded headers (desktop), or a JSON object `{ ...arguments, data: "<base64>" }` (Android; ~1 s for 20 MB), and the frontend calls them through `invokeWithBytes` (`src/lib/ipcBytes.ts`). A new upload-style command must do the same, and web apps sending big files on Android should send base64 that way too. (The fs plugin's own writes — the Files tab on the user folder — still use the plugin's array path on Android.) Responses are unaffected: raw `ArrayBuffer` responses work everywhere.

**Not done:** a full-screen mode; iOS (`secure_store` has an error stub; the Xcode project doesn't exist).

## Known limitation: links planted in `user/`

The fs plugin's scope check resolves links for paths that exist but not for ones that don't yet, so a directory junction/symlink that someone plants *inside* `user/` (web apps can't create one — no command does — but the OS user, an unzip, or a `git clone` can) lets a web app **create new files** (never overwrite or read existing ones) under the link's target. Nothing in `admin/` is affected in practice: `admin/dist/index.html` exists, so it's protected, and extra files in `dist/` are deleted at startup. Avoid linking folders into `user/` that you don't want web apps writing into.

## Bundling the admin-app into the installer

`csdrive-webhost-tauriapp/src-tauri/src/lib.rs` embeds `csdrive-webhost-admin-reactapp/dist/index.html` at Rust compile time via `include_str!`, as `ADMIN_APP_INDEX_HTML` — so it's baked into the compiled binary (and thus every installer built from it, with no separate resource file or internet access needed at runtime) and is what gets written out as `admin/dist/index.html` at every start. This means **the admin-app must be built before the Tauri app** — `cd csdrive-webhost-admin-reactapp && npm run build` — or `cargo build`/`cargo tauri build` fails fast with a clear message from `build.rs` pointing at that command, rather than a cryptic `include_str!` error. `build.rs` also declares `cargo:rerun-if-changed` on that file, so rebuilding the admin-app and then the Tauri app picks up the new bundle (this crate wouldn't otherwise notice changes in a sibling package). The same pattern is used for each deployable app under `csdrive-webhost-userapps/` — see "Deploying apps" below.

## Deploying apps

`csdrive-webhost-userapps/<name>/index.html` (none exist yet — the registry is currently empty, and the Deploy dialog says so) is source for a small standalone app that the admin-app's Files tab can *deploy*: pick "Deploy apps…" from the toolbar (available in any folder browsable by the file manager, not just the root), choose an app from the list, confirm or edit the destination folder name (defaults to `<name>`, the folder it sits under in `csdrive-webhost-userapps/`; rejected if a file/folder of that name already exists at the current location), and the admin-app creates that folder under the current location and writes the app's `index.html` into it — using the same generic `mkdirRoot`/`writeRootTextFile` root-relative file operations as the rest of the Files tab, not a separate Rust-side "deploy" command.

Each deployable app's `index.html` is embedded into the Tauri binary at compile time (`csdrive-webhost-tauriapp/src-tauri/src/deployable_apps.rs`, via `include_str!`, the same pattern as the admin-app's own bundle — see "Bundling the admin-app into the installer" above) and exposed to the frontend via two read-only commands, `list_deployable_apps` and `get_deployable_app_html`. Adding a new deployable app means: create `csdrive-webhost-userapps/<name>/index.html` (or point at a built bundle the same way the admin-app's `dist/index.html` is), add an entry to `deployable_apps::REGISTRY` (plus an `include_str!` for its `index.html`), and `cargo build`.

## Tags

Tags (`window_tags` table) are not specific to windows: `guid` is any opaque id — a window, tab group, tab, or, in the Files tab, a file-manager root (keyed `root:<rootId>`, e.g. `root:user`; custom `ext:` roots are session-only, so their tags stay in the database and reappear if the same folder is added again). **Everywhere tags appear they must be editable and sortable**, which is why every place renders them through the one shared `components/Tags.tsx` `TagList` component rather than its own markup: click a badge to edit its text/colors, drag badges (or use the arrows in the edit dialog) to reorder, × to remove. Backend commands: `list_tags`, `add_window_tag`, `update_window_tag`, `reorder_window_tags`, `remove_window_tag`; order is the `sort_order` column (new tags go last). Any new place that shows tags should use `TagList` too.

## Seeding demo data for the Apps tab

`csdrive-webhost-tauriapp/src-tauri/examples/seed_demo_data.rs` populates the real `data.db` with demo data for the 9 sample apps in `user/qwer/` (`index1.html`-`index9.html`), for stress-testing the Apps tab's nested windows/tab-groups/tabs UI at scale. To run it after a reset (or any time):

```
cd csdrive-webhost-tauriapp/src-tauri
cargo run --example seed_demo_data
```

It requires `data.db` to already exist and `user/qwer/index1.html`..`index9.html` to already be deployed (run the app once, and copy `sample-apps/qwer/` into the real `user/qwer/` folder, before running the script). It finds the real data folder itself the same way the app does, including a relocated custom data folder. Layout it creates: one `secondary_windows` entry per app, except `index1.html` which gets 10; the first of those 10 windows gets 10 `tab_groups`; the first of those groups gets 100 `tabs`. Safe to re-run — every row it creates is tagged `seeded:qwer-demo-data`, and each run starts by deleting only rows carrying that tag before recreating them, so it never touches any other window/tab/tag you created yourself.
