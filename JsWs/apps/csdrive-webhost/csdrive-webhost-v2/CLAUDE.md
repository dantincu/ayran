# CsDrive WebHost

The Tauri app in `csdrive-webhost-tauriapp` has exactly one frontend, the **admin-app** — a React/Vite project living at the root of that same folder (`src/`, `index.html`, `package.json`, `vite.config.ts`, with the Rust backend in `src-tauri/`). It is the Tauri app's own compiled-in frontend (`frontendDist` in `src-tauri/tauri.conf.json`, embedded into the binary and so into every installer), it always occupies the main window, and nothing — neither the user nor a web app — can replace it. It manages a machine-wide *data folder* (below) holding an `admin` folder for the app's own database and secrets, a `user` folder meant purely for arbitrary user-authored content, and a `files` folder for the Notes app's cache. The user can write their own `.html` files anywhere under `user` (e.g. `user/index.html`, `user/myapp/index.html`), but those are only ever opened as *secondary* windows (via the admin-app's own Files tab or User Apps tab — "Open as web app"/"add a new window entry"). Besides those *user apps* the app ships **system apps** — more pages of the same compiled-in frontend, **Notes** being the first — which are opened the same way and managed in the System Apps tab (see "System apps and Notes" below).

## Folder layout

**Where all of this lives is defined in exactly one place: `csdrive-webhost-tauriapp/src-tauri/src/layout.rs`** — `DEFAULT_DATA_FOLDER` (the default data folder; `%APPDATA%\com.ayran.csdrive-webhost-tauriapp` today), the `admin`/`user`/`files` folder names (and inside `files`: `a`, `b`, `c`, the thumbnails `t` and `tb`, and `data.db`, see "The Filen cache" and "Media"), `FILEN_SESSIONS_FILE`, and `ADMIN_APP_ID` (the admin-app's key for its saved UI state). Nothing else hardcodes them: the backend, the keychain entry names (the last component of `DEFAULT_DATA_FOLDER`), the `seed_demo_data` example (`#[path]`-includes that file) and the admin-app (which names the user folder as the root `user`, never by path) all derive from it. To run the app **completely isolated** from real data (e.g. for tests), set `DEFAULT_DATA_FOLDER` to a scratch absolute path (`r"C:\Temp\csdrive-isolated-test"`) and rebuild: the run gets its own data folder, database and keychain entries, and can't reach the real one. (The WebView2 browser-storage profile is still shared, as it is keyed by the app identifier; the app keeps no state there.) Remember to set it back.

The folders sit directly under the data folder (the default above, or wherever Settings' "Change data folder" points):
- `admin/` — the app's own files, none of which is ever served to a window: `data.db` (this app's SQLite database — secondary windows/tab groups/tabs/tags, the generic `app_state` table, the `global_settings` table, remembered device folders, connected Filen accounts; see `secondary_windows::init_db`) and `filen-sessions.enc` (below). The admin-app itself is **not** in the data folder: it's the Tauri app's compiled-in frontend, so there is no `admin/dist` and nothing on disk to tamper with.
- `user/` — arbitrary user-authored `.html`/`.js`/`.css`/etc., served to secondary windows via the `csuser://` custom protocol. The backend never reads anything from here except in response to the admin-app explicitly asking to open/list something in it.

- `files/` — the Notes app's cache of Filen accounts and their branches (`a/`, `b/`, `c/`, the thumbnails `t/` and `tb/`, and its own `data.db`; see "The Filen cache" and "Media"). Like `admin/`, it is a **protected path** (`data_location::protected_paths`): no file command or SQLite call can reach it, even inside a picked folder — only the `filen_cache_*` commands read and write it.

The three folders are created unconditionally at startup (`lib.rs`'s `.setup()`), regardless of which files inside them do or don't already exist. Whenever a folder needs a short name a program can rely on and a long one a person can read, the app uses **folder pairs** (`folder_pairs.rs`, strategy in `docs/strategies/folder-pairs-strategy.md`; `docs/strategies/` is where the app's strategies are written down, one `.md` each).

**The admin-app** is a React app (TypeScript, built by Vite into `dist/`, embedded by Tauri — see "Building and running"). It is a file manager for the `user` folder and any folders the user picks, a file manager for connected filen.io accounts (any number of them), a SQLite management studio for `.db` files in those places, the manager of the apps' windows/tabs/tags (the System Apps tab, first and the default, and the User Apps tab — the same component, `AppsTab kind="system" | "user"`), a browser-storage inspector, and the settings.

`csdrive-webhost-userapps/` holds source for small standalone apps that can be *deployed* — copied as a new folder of `.html`/etc. content into the `user` root — via the admin-app's own Files tab (see "Deploying apps" below), as opposed to the admin-app, which is the one privileged app: always built into the installer and always the main window.

## App state storage: data.db, not browser storage

An app's own UI-state persistence (active tab, last-browsed folder, collapsed groups, ...) belongs in the app-owned `data.db` (see the generic `app_state` table in `secondary_windows`'s crate — `get_app_state`/`set_app_state`), *not* IndexedDB or Web Storage. Reason: the data folder can be relocated (see the Settings tab / `data_location`) precisely so testing can switch between profiles, but browser storage lives in the fixed WebView2 profile rather than wherever the data folder currently points — so it never actually switched with the rest of the app's data. Rows are namespaced by an `app_id` — the relative path of the html file the window was opened from (from `user/`, for a secondary-window app; `system:<id>`, e.g. `system:notes`, for a system app; `layout::ADMIN_APP_ID` for the admin-app itself) — which the **backend** works out from the calling window itself (`get_app_state`/`set_app_state` take no app id; any one a caller sends is ignored), so an app can only ever reach its own state — so the same app keeps separate state when copied to more than one location on disk, and multiple apps sharing this one database never collide. This applies to every app in `csdrive-webhost-userapps/`, present and future; the admin-app's own `src/lib/appState.ts` is the reference implementation. It does not apply to browser storage a user explicitly creates through a generic inspection tool (e.g. admin-app's Storage tab) — those are arbitrary by design and named by the user, not the app, and have nothing to do with an app's own settings. If an app used browser storage for this before switching to `data.db`, it's fine to just abandon the old IndexedDB database/keys rather than migrate their contents, unless they hold data too valuable to lose.

**A paginated list's position is saved as the number of records skipped, never as a page number** (`src/lib/pagedPosition.ts`: `offsetOfPage`, `pageOfOffset`, `validOffset`). The page size is one setting for the whole app (below), so it can change between saving a position and restoring it, and "page 3" only means the same records for the same size; "50 records skipped" means the same records under any size — restored with a size of 10 the page shown is the 6th, which holds the record that was first on screen. Files, Filen.io and Notes save it with their place (`offset` in `filesTab.location` / `filenTab.location`, `o=` in a Notes tab's resource id and its last place), and **nothing is saved over a position until the listing it belongs to has loaded** (a `restoringPage` flag), or the page still saying 0 would overwrite it; a folder that can't be listed drops its position. A new paginated list that keeps its position does the same.

**Global settings** are the exception to "an app only reaches its own state": the `global_settings` table (`get_global_setting`/`set_global_setting`, granted to every window) holds the few preferences that are deliberately shared by every app — today the list **page size** (`listPageSize`, `src/lib/listPageSize.ts`), so paging 10 rows a page in the Files tab does so in Notes too. Keep it to genuinely global preferences.

**The admin-app writes nothing to browser storage.** Verified against a pristine WebView2 profile after using every tab: `localStorage`, `sessionStorage`, IndexedDB, cookies, the Cache API, service workers and OPFS are all empty, and the profile holds no data for the admin origin beyond the engine's own bookkeeping (navigation history, site-interaction and preference records, which any webview keeps for any page). The only code that touches these APIs is the Storage tab, on the user's explicit action. Keep it that way: new admin-app state goes through `appState.ts` (`data.db`).

**Each tab page of the admin-app keeps its own place**, independently of the others: going to another tab page and coming back — or restarting the app — finds the page where it was left. A page saves its navigation under keys of its own (`filesTab.location`, `filenTab.location`, `sqliteTab.navigation`, `storageTab.panel` and `storageTab.indexedDb`, and — one per kind — `systemAppsTab.navigation` / `windowsTab.navigation`), written on every change; `src/lib/tabState.ts` (`usePersistedState`) is the helper for a plain value. **What was saved is never trusted blindly**: a saved shape is checked before use, and whether it still leads anywhere is judged once the page has what it needs — the Apps tabs fall back to the deepest level that still exists (and wait until both the saved place and the list of windows have loaded, or they would reset a perfectly good place against an empty list), the Files and Filen tabs go to the top of the root/account when the saved folder can't be listed, the SQLite tab to its list of databases when the saved database is gone, the Storage tab's IndexedDB panel to its database list. A new tab page with navigation gets the same: its own key, a shape check, a check against reality.

## What the backend exposes to web apps (capabilities)

User-provided web apps run in secondary windows (label = the window guid); the admin-app is the window labelled `main`. Tauri capabilities are per window label, so `src-tauri/capabilities/` has three files, and **every new command must be listed in `build.rs` and granted in exactly one of them**:

- `user-apps.json` (`windows: ["*"]`, so it covers the admin window too) — everything a web app is meant to be able to do: files under the user folder and folders the user picks with a native folder picker, through **our own file commands** (`fs_read_dir`, `fs_stat`, `fs_exists`, `fs_read_file`, `fs_write_file`, `fs_mkdir`, `fs_remove`, `fs_rename`), which obey our own scope (see "The file scope" below) — the fs plugin isn't used at all. **No window ever sees a real path** (see "No real paths for web apps" below): every file command names a *root* — `user`, or the opaque id of a picked folder, from `list_picked_roots` — and a path *relative* to it; `pick_folder` asks the person to choose a folder and answers with its id and name. SQLite on `.db` files in those same places (below); Filen.io file operations on the accounts the user has connected (below); managing app windows, tab groups, tabs and their tags (and reloading the page an open window shows: `reload_secondary_window`, `reload_tab`); binding itself to its tab (`init_window_tab`) and adding another (`add_window_tab`, see "Who creates tabs" below); asking to open an external web site (`open_external_site`, see "External web sites" below) and managing the ones listed (`reopen_/focus_/suspend_/close_external_site`); `open_related_web_app`, with which **any web page opens another page in a window of its own** (see "Web apps opened from Notes"), and `open_file_as_web_app`, which only Notes may use (`is_system_page`); **the app's own clipboard** (`internal_clipboard_get`/`_set`, see "Details, clipboards and paths"); its own `get_app_state`/`set_app_state`; the shared `get_global_setting`/`set_global_setting`; `list_system_apps`; and the Filen *cache* commands (`filen_cache_*`, below). System apps are pages of the admin-app's own frontend but are **not** the admin-app: they run in ordinary secondary windows and get exactly this file's grants (plus the one below). Deliberately **not** granted: system/OS/app/window introspection (`core:default` — app version, monitors, paths…), event emitting, connecting/disconnecting Filen accounts.
- `admin.json` (`windows: ["main"]`) — extras only the admin-app gets: `filen_login`/`filen_logout` (the only place a Filen password is ever typed), data-folder relocation and "Delete app data", and the bundled-app deploy commands. On Android every call reaches Tauri through the one webview (see "Windows on Android" below), so the capability files can't tell the admin-app from a window there: the bridge applies the same list itself (`window_host::window_commands`, read from `user-apps.json` + `system-apps.json`) and those commands also call `window_host::require_admin` on the *real* caller, which is what actually enforces it there — and on desktop too. (Path joining is our own `joinPath` in `src/lib/localFs.ts`; Tauri's `path.join` permission isn't granted to anything.)
- `system-apps.json` (`windows: ["*"]`) — `save_to_device`/`choose_save_location`, exporting a file (the desktop "save as" dialog, or Android's Downloads folder), for the admin-app **and the system apps** (Notes exports files with them, and asks `media_url` for the address of a picture or video — see "Media"); exporting a file that is *already on disk* — a local one (`export_local_file`) or one of the Filen cache (`filen_cache_export`) — is the same kind of command and is copied on the Rust side (below), never through the page. It is granted to every window only because the capability files can't tell a system app from a user app — both are secondary windows — so the commands call `window_host::require_trusted` (the admin-app **or** a system app, as the caller is worked out — see `CallerWindow`), which refuses a user web app. Verified live: a user web app gets "Only the admin-app and the system apps can do that."; Notes gets past the check.

**SQLite** is our own (`sqlite_db.rs`), not `tauri-plugin-sql` (which opens any path on disk): `sqlite_load(root, path)` takes a root and a path relative to it, resolves symlinks/`..`, and refuses anything outside the file scope; the returned handle is the virtual name `<root>/<path>` (never a real path), only works in the window that loaded it and is closed when the window closes. SQL can itself name files, so every connection also runs under an authorizer: `ATTACH` is allowed only for in-memory/temp databases (a file can't be named from SQL now that windows don't know real paths), `PRAGMA temp_store_directory`/`data_store_directory` and `load_extension` are denied, and `VACUUM INTO` (which SQLite doesn't route through the authorizer) is refused by a token scan of the statement. (Without these, `ATTACH DATABASE '…/admin/data.db'` read straight past the path check.) `sqlite_execute(db, query, values)` → `{rowsAffected, lastInsertId}`; `sqlite_select(db, query, values)` → array of `{column: value}` (BLOBs as byte arrays).

**Filen.io lives entirely in Rust** (`src/filen/`: `crypto.rs`, `api.rs`, `ops.rs`, `mod.rs`; ported from the Ayran Notes app's Rust client). No credential ever reaches a webview: the connected-accounts list (user id + email) is a table in `data.db`, and every account's session (API key, master keys, name-hash key; the RSA private key is used once at login and never kept) is in one encrypted file in the data folder, `layout::FILEN_SESSIONS_FILE` (`admin/filen-sessions.enc`), so it travels with `data.db` when the folder is relocated and is gone when the folder is wiped. Web apps identify an account by its numeric `userId` and call, with Filen paths (`/`, `/Folder/file.txt`): `filen_list_accounts` → `[{userId, email}]`, `filen_readdir` → `[{name, isDirectory, size, mtimeMs}]`, `filen_stat`, `filen_read_file` (returns an `ArrayBuffer`), `filen_write_file` (creates or replaces; the bytes are the raw request body, the account and path go in headers: `invoke('filen_write_file', bytes, { headers: { userId: String(id), path: encodeURIComponent(path) } })`), `filen_mkdir` (recursive), `filen_rm` (to trash), `filen_rename` (also moves). `src/lib/filen.ts` is the reference wrapper. Crypto is tested against vectors from Filen's own JS SDK (`@filen/sdk`); accounts on auth version 3 salt name hashes with an HMAC key derived from the RSA private key (fetched at login). 

The backend exposes no system information (CPU, memory, OS, paths…) to any window.

## Secrets at rest (`secure_store.rs`)

One random 32-byte key, generated the first time it's needed and kept in the platform key store (desktop: the OS keychain via the `keyring` crate — Credential Manager / Keychain / Secret Service, entry `app-encryption-key` under the service name from `layout::keychain_service()`; Android: the Android Keystore, see "Android"), encrypts everything sensitive that we persist. The sensitive data itself lives in ordinary AES-256-GCM files (`nonce(12) || ciphertext+tag`, written atomically) inside the data folder: the Filen sessions file (above) and the small pointer file (`data-location.enc`, in the *default* data folder) that records a relocated data folder. The key store therefore only ever holds 32 bytes (no entry-size limits), and the only platform-specific code is `platform::resolve_key`. **iOS is not implemented yet** — `resolve_key` returns an error there (rather than keeping the key unprotected); implement it with the iOS Keychain and nothing else in the module changes. (`keyring` is a desktop-only dependency in `Cargo.toml` for that reason.) New secrets should be added the same way: a JSON structure written with `secure_store::write_json`.

## The file scope (`fs_scope.rs`, `fs_commands.rs`)

Which files the file commands and SQLite may touch is decided in one place, our own `FsScope` — replacing the fs plugin's, whose runtime scope can only grow (paths can be allowed or forbidden, never taken back), so "forget this folder" couldn't revoke anything until a restart. Ours: the **user folder** is always allowed and can't be revoked; **picked folders** are allowed until revoked, at once, and can be picked again in the same session; the app's own **`admin/` folder** (database, Filen sessions), the Notes cache in **`files/`** and the data-location pointer file are **never** reachable, even inside a picked folder (so picking a folder that contains them exposes nothing). Every path is resolved before it is judged: it is a root plus a relative path (below) which becomes an absolute one, `..` is refused, symlinks/junctions are followed to the real location (also for a file that doesn't exist yet, by resolving its nearest existing folder — which closes the plugin's old gap where a link planted in `user/` let a web app *create* files outside), a dangling link is refused, and the command then operates on the resolved path. Removing or renaming an entry acts on the entry itself (a link pointing outside is removed, never its target). Picking is done in Rust (`pick_folder`: the OS folder dialog on desktop, `FolderPicker.kt` on Android), which adds the folder to the scope and remembers it in `data.db` (`picked_roots`); `allow_saved` allows the remembered ones again at every start, and `remove_picked_root` revokes one. The frontend's `src/lib/fs.ts` wraps the commands with the shapes the plugin had (each takes the root id first). The dialog plugin remains only for message boxes (`confirm`) and Rust-side dialogs (folder picking, "save as", the data-folder chooser); a web app can't get a path out of a dialog and use it, because only `pick_folder` adds to the scope. Tested with real symlinks/junctions, `..`, protected paths and revocation (Rust unit tests), and live on desktop and the Android emulator.

## No real paths for web apps

**A window — a user web app, a system app — never learns where anything is on the device.** The one thing that could hand it a real path is the file access it legitimately has, so that is where it is closed:

- **Roots and relative paths.** Files are addressed as a *root* plus a path relative to it (`fs_scope::FsScope::check_in`): the root `user` is the user folder; every picked folder gets an **opaque random id** (12 hex characters, made in `picked_roots.rs`, remembered in `data.db`'s `picked_roots.id` so it survives restarts and stays the same when the folder is picked again). Every `fs_*` command, `sqlite_load` and the upload/copy commands that name a local file take `(root, path)`; `pick_folder`/`list_picked_roots` answer `{id, label}` (the folder's own name), `remove_picked_root` takes the id. Only the scope maps an id to the real folder. `..`, backslashes and (on Windows) drive letters in a relative path are refused, and a root itself can't be removed or renamed from inside.
- **Nothing it says contains a real path.** The scope's refusals name the relative path (`resolve_shown`/`check_shown`), the SQLite database handle is the virtual name `<root>/<path>` (it used to be the real file path), `ATTACH` of a file is refused (SQL can't name a root), `save_to_device`/exports answer only the saved file's *name*, `get_user_folder` no longer exists, and the tab resource ids and tags that used to embed `ext:<path>` now embed the id (`picked_roots::migrate_path_based_ids` moved the old ones on first start). Tested: every refusal is checked for the real path in Rust, and live (a user web app's view of `list_secondary_windows`, `list_picked_roots`, every refusal and the SQLite handles was scanned).
- **Drag and drop.** Tauri hands a page the *real paths* of files dropped on its window; secondary windows are built with `disable_drag_drop_handler()` (the main window always was), so a dropped file arrives as a plain HTML5 `File` — a name and its bytes, no path. The device's file chooser (`<input type=file>`) is the same.
- **Where paths still exist.** Only the admin-app may ask where a root really is (`fs_root_path`, `require_admin` — the Files tab's tooltips), and Settings shows the data folder (`get_data_folder_info`, also admin-only). The backend of course holds real paths; it just never says them to a window.

If a new command takes or returns a location on the device, it takes `(root, path)` and answers with names, never a path — and its refusals must not quote one.

## Keyboard

Shared code is in `src/lib/keyboard.ts` (and `components/Pagination.tsx`, `components/TabSwitcher.tsx`). Shortcuts use Ctrl (⌘ on a Mac) and are shown in tooltips. **The list of every shortcut, for the people who use them, is `docs/keyboard-shortcuts.md` — a new shortcut is added there in the same change.**

- **Two-key shortcuts (chords)** (`lib/chords.ts`, `components/ChordHost.tsx`, mounted once per page beside the clipboard menu): **Ctrl+K, then a letter** (within 3 s; a hint at the bottom — **glowing**, above every dialog, and lighting the entry of the shortcut that was just pressed — lists the letters that apply *here*; Esc or a wrong letter cancels). The owner of an action registers it while it is on screen (`useChord(letter, label, run, enabled?)`): **T** — the admin-app's tab switcher (a popover listing the tabs with a number in front of each, and a box that has the focus and takes digits — Enter goes to that tab, a number that isn't one turns the box red, a press on a row goes there, Escape closes it; it used to be Ctrl+K on its own, which a chord prefix can't also be); **M** — maximize/restore the popup on top (`lib/modalStack.ts`; `Modal` and `EditorPanel` register: the window less a margin `clamp(6px, 2.1vw, 40px)`, and each has a button); **C**/**V** — copy to / paste from the app's clipboard in the text box that has the focus (`TextFieldMenu`); **X** — clear the app's clipboard. Ctrl+G (the page list) stays a single-key shortcut. A new shortcut is a chord.
- **Lists** (`useListKeyboard` + `kbdItem`): **Up/Down** move the focus by one item, **Home/End** go to the first/last, **PageUp/PageDown** move it by 10 (**in a paginated list these three stay inside the page the focus is on** — `useListKeyboard` takes `pageSize` and `page`: Home/End are the page's first/last item, PageUp/PageDown stop at the page's start/end and, pressed there, go on to the next page's first / previous page's last item; the first arrow with nothing focused focuses the shown page's first item), **Left** goes to the parent and **Right** into the focused item (a folder, a file to edit, an app → its windows → its tab groups → its tabs → a tab's external web sites; on an external web site, Right brings its window to the front or opens it again), **Enter** for the focused item's own action (on a tab: show it, opening its window if need be; elsewhere the same as Right; not heard while a button or link has the focus, which Enter presses). The keys are heard on the whole window, so nothing has to be focused first; a text box or menu keeps its own keys and so does an open dialog or the editor (`overlayOpen`); pressing on an item moves the focus there. The focused item is drawn with `[data-kbd-focused]`. In a paginated list the focus is an index into *all* the items and the page shown follows it; going Left puts the focus on the folder just left, Right on the first item of the one opened — but only for a move made with the keys (after a click nothing is focused until a key is pressed). Covered: the four levels of the System/User Apps tabs, the Files and Filen tabs, Notes' file list and its notebooks list (Right shows the notebook's folder, Left goes to the home page), the SQLite tab's databases and tables, the Storage tab's IndexedDB databases → object stores → records. Not covered: the Local/Session storage key-value tables, Settings, tag editing.
- **Paginated lists — all pages.** The page indicator (`3 / 12`) is a button: pressed with a finger or the mouse it opens a **popover listing every page number** (the current one highlighted) and a press on one goes to that page. **Ctrl+G** opens the same popover *with* a numeric box (focused; Enter goes to that page, an invalid number turns it red) — the box is only there when it was opened with the shortcut, not by pressing the button. Escape or a press outside closes it. Every paginated list uses the one `Pagination` component, so every one has it (Files, Filen, Notes). **The popover is as tall as the screen allows and its list of pages scrolls** (the popover is `position: fixed`, placed by `Pagination` against the screen — above the button when it fits there, else slid down — with `max-height` the screen's height less an 8px margin and the system bars' insets; the list inside takes what is left and has `overflow-y: auto`, so it fits a phone however many pages there are) **and has a keyboard cursor** (`.cursor`, an outline apart from the current page's highlight): Left/Right ±1, Home/End first/last, Up/Down the same column of the previous/next *row*, PageUp/PageDown half the list's height in rows, Enter goes to the cursor's page (a typed number wins, and typing moves the cursor). Rows are not assumed: `cursorFor` reads them from where the buttons really are (the ones sharing the first button's `offsetTop`), so it holds for any width or font; with a single row Up/Down/PageUp/PageDown do nothing.

**A web app's window never changes its own address** (desktop; `FROZEN_ADDRESS_INIT_SCRIPT` in `code_snippets.rs` and `navigation_verdict` in `lib.rs`, both from `lock_down_navigation`'s `own` argument — the page the window was built for). The init script makes `history.pushState`/`replaceState` **ask** for an address instead of changing it (one of this app's origin becomes a navigation the backend sees — `location.assign` —; another origin throws a `SecurityError`; not writable, not configurable) and removes `window.navigation`; `on_navigation` lets through only the page's own path and query (so a reload, and a changed *fragment*, an in-page `#link`, are fine), sends links to the web (http/https) to the OS browser, refuses `javascript:`, `data:` and `file:`, refuses every other page of a *system app's* window and the admin-app, and treats another page of a *web app's* kind as a **request** (`Nav::Request`: the window stays, and the person is asked — "Links between pages of web apps", next). So a page can't turn itself into a "single page" that wanders off its address, nor be taken to another page of ours by a link or `location.href` without the person choosing it. This is a guard against pages, not a boundary against hostile code — the CSP and the capabilities are. Consequences: an app **reports** which resource a tab shows (the query string in the address it gives `init_window_tab`/`add_window_tab` — `TabLib.urlFor(params)` builds it without navigating), the resource id is **owned by the backend** (a reload gets the stored one back in the init response), and "start the page over" is `location.reload()`, never `location.href = …`. Notes and the markdown bootstrap follow this. **Android** applies the same rule to every window's WebView (see "Windows on Android"); the main webview shows only the admin-app.

## Details, clipboards and paths

**Details popup** (`components/DetailsModal.tsx`). Every listing of records has an *Info* button per record that opens one: the record's fields (`DetailField`: label, value, `mono`, `copy`, `hidden`), **each copyable value with two buttons — copy to the OS clipboard and copy to the app's own clipboard** —, a field marked `hidden` shown as dots behind an eye button (a Filen item id: it can be viewed, unhidden and copied), and the record's tags with the "add tag" button (see "Tags"). Where it is: the System/User Apps tabs (an app, a window, a tab group, a tab, an external web site or opened app, a root header — beside the existing `#` resource-id button), the Files tab (an entry, the folder shown — toolbar —, and each root's pill, whose tags are edited there), the Filen tab and Notes (an entry, the folder shown), Notes' notebooks page. The listings that are only lists of links (SQLite's databases and tables, Storage's databases and stores) don't have one.

**Paths in a file manager.** A file or folder's details show its **path** (relative to its root, `/a/b/file.txt`, never a real one — the Files tab, admin-app only, adds "Location on this device" as it does in tooltips), copyable to both clipboards. A **Filen** entry also has its **item id** (Filen's uuid: `filen::ops::Entry.id`; the cache keeps it as `entries.remote_id`, filled by the next listing for a cache made before — a branch-made file has none until committed), hidden until asked for. Every file manager (Files, Filen, Notes) has **Go to a path…** (`components/GoToPathModal.tsx`, `lib/pathInput.ts`): a popup with a text box — the two paste buttons put what is on the OS or the app's clipboard in it — that takes `/a/b` or `a\b` (either slash; `..` refused), checks that it names something in the current root/account/branch and goes there; a file opens its folder with the file focused; otherwise the box says why and stays open.

**The app's own clipboard** (`internal_clipboard.rs`, `lib/clipboard.ts`): one text (16 MiB at most) kept by the backend and shared by every window of the app — the admin-app, the system apps and web apps — not persisted, nothing copied to it reaches the OS clipboard. **Every window may read and write it, a user web app included** (decided on purpose: what one window copies another can paste; `TabLib.internalClipboard` in the samples) — so what is copied to it is readable by any web app that is open. The admin-app's **Settings** tab shows what it holds (a character count; the text on request) and has **Clear the app's clipboard** — as does the chord Ctrl+K, X — and web apps can clear it too (`internal_clipboard_clear`, `TabLib.internalClipboard.clear()`). `lib/clipboard.ts` also has the OS clipboard (`copyToOsClipboard`: `execCommand` first, then the Clipboard API; `readOsClipboard`: the Clipboard API, with a readable error when the webview won't say). **Android's WebView refuses to read the OS clipboard** — the menu and the paste buttons then say so and point to the system's own paste — while writing to it works. Verified on the emulator, by real taps: the text menu, select paragraphs, the app's clipboard between the admin window and a Notes window (through the window bridge), details, go to a path.

**Text editors and single-line boxes** (`components/TextFieldMenu.tsx`, mounted once in the admin-app and in Notes): while a `textarea` or a text-like `input` (text, search, url, tel) has the focus, a small "…" button sits at its corner and opens a menu — **Select paragraphs** (a single-line box: **Select all**), **Copy to / Paste from the app's clipboard**, **Copy to / Paste from the clipboard** (the OS's). Pasting replaces the selection. A **paragraph** (`lib/paragraphs.ts`) is a run of text between blank lines; selecting takes the paragraph(s) the selection touches — or the caret is in — without the whitespace around them (a caret in a gap takes the paragraph before it). The box keeps its focus and selection throughout (the button and items don't take the focus). A box that closes when something else is pressed opts out with `data-no-text-menu` (the page-list popover). A new text editor needs nothing: the menu finds it.

**Popups can be maximized** (`components/Modal.tsx`, `components/EditorPanel.tsx` — the editors' popup —, `lib/modalStack.ts`): a button in the header and the chord Ctrl+K, M make the popup on top take the window less a margin (`clamp(6px, 2.1vw, 40px)`: thin on a phone, 40px at Full HD), so it still reads as a popup.

**The file editor** (`components/CodeEditor.tsx`, used by the Files tab and by Notes — a new editor of a file uses it too). It is a `textarea` — so the clipboard menu, selection, drafts and the on-screen keyboard are unchanged — with a **syntax-highlighted copy of its text drawn behind it**: Markdown, HTML, **CSS and JavaScript** by the file's name (`lib/highlight.ts`: `languageOf`, `highlight`; `lib/highlightCode.ts` has the CSS and JavaScript scanners, also used for a `<style>`/`<script>` in HTML and for ```css / ```js fences in Markdown; any other file is plain; a text over `HIGHLIGHT_LIMIT` characters is left plain). The box has a transparent text and the same font, padding and wrapping as the copy; it is as tall as its text and the frame around both scrolls, so nothing is kept in step but the height. `highlight` keeps one rule — **the text content of its result is exactly its input** (escaped, only wrapped in `<span class="tok-…">`), checked on 4 000 random texts — because the two layers must line up character for character (no italics, whose synthesized slant misaligned one glyph run on Android; checked visually with the box's text made visible over the copy, wrapped lines included). The colours are the `--tok-*` variables of `App.css` (light and dark); `data-text-menu-anchor` on the frame puts the clipboard menu's button at the frame's corner rather than the (tall) box's.

**Open link** (`lib/textLinks.ts`, in the clipboard menu of a `CodeEditor` that is given `onOpenLink`): when the caret — or the selection — is inside an address, the menu offers **Open link**. An address is a web address (`http`/`https`, bare or in `<…>`), the target of a Markdown link, image or reference, or the value of an `href`/`src` attribute; a **web** address is asked about first and then opened — in Notes as an external web site of its window (the same box and rules as a web app's, `open_external_site`), in the admin-app's Files tab in the OS browser after a native box (`open_web_address`, admin only: it has no tab to list a site under) —, a **path** is resolved against the file being edited (relative to its folder, or absolute from the root of its folder or account, `resolveLinkedPath`) and opens what it names: a page (html, markdown) as a web app in Notes, another file in the editor, a folder in the listing. Changes held in the editor must be saved first (the linked file takes their place), a missing target is said next to the menu. A note's address (a query with the key `note`) opens that note, as a link in a page does (below).

**Slim windows.** Under 600 px wide (a phone, a narrowed window) a record's row of action buttons falls **below its text and tags** (`App.css`, the last block: `display: contents` on the row's header lets the buttons take `order` last; file tables become a block per entry). New listings use the existing classes (`window-item`, `row-actions`, `file-table`) and get it.

**Huge folders.** The Files tab asks for sizes only for the entries of the page on screen (as Notes always did for a local source), never for the whole folder — a folder of 100 000 files used to take over four minutes to show (a call per entry) and now takes about 0.2 s. What a listing costs — the entries all travel, in one JSON message, and sit in memory in Rust, in the webview and, for Filen, in the cache — is measured and analysed in `docs/huge-listings.md` (limits, what a failure looks like, and the paged-listing design that would remove them).

## External web sites

A user web app or a system app can ask to open an **external web site** — a page of the web, http or https — in a window of this app. It is **not a tab** (an external page has no `init_window_tab`/`update_tab_resource` to call, and can't be told anything): it is listed as a **child of the tab whose page asked for it**, one level below the tabs in the window manager (`external_sites.rs`, the `external_pages` table in `data.db`: guid, `tab_guid`, `window_guid`, `initial_url`, `url`, `title`, `created_at`; its tags are ordinary `window_tags` on its guid).

**Asking.** `open_external_site(url)` (granted to every window; `openExternalSite` in `src/lib/secondaryWindows.ts`, `TabLib.openExternalSite` in the samples) needs a caller that is a web app or system app with a registered tab. The address is checked first (`external_sites::check_url`): absolute, **http or https only**, with a host, **no user name or password in it**, at most 2048 characters, and **not one of this app's own origins** (`window_host::is_own_origin`: the frontend, `csuser`, or any `*.localhost` name — those have access to the backend). Then an **OS native confirmation box** shows *who* asks and the address, with **Open** and **Cancel**. **Only one such box can be showing at a time, and nothing is queued**: a request that arrives while one is up is refused at once (the command rejects). The command answers immediately with a request id; what the person chose arrives as an event, **to the window that asked and to no other** (listen with `getCurrentWebviewWindow().listen`, as for `tab-navigate`, and before asking):
- `external-site-response` `{ requestId, url, confirmed, pageGuid, error }` — the answer (`pageGuid` names the site in the events below; `error` says why it wasn't opened when the person said yes);
- `external-site-changed` `{ pageGuid, url, initialUrl, title }` — the site's address or title changed (the title as the page sets it, when it has one; the address also when a single-page site changes it without loading);
- `external-site-closed` `{ pageGuid }` — its window was closed (its entry stays in the window manager).

**The site has no way into the backend.** On desktop it is an OS window labelled with the page's guid, showing the address as an external URL: no capability names a remote page, so every command is refused for it (verified live: a site calling `get_app_state` gets "not allowed on window…"), and it has no Tauri globals. Its window may only navigate to what `may_navigate_to` accepts — what `check_url` accepts, or `about:blank` — checked on **every** navigation, so a link, a redirect or a script can't take it to `tauri://`, `csuser://`, `*.localhost`, `file:` or `javascript:`, where a page *would* have access; and it can't open windows of its own (new-window requests are denied). On **Android** it is shown full screen in a plain `WebView` in an activity of its own (`ExternalSiteActivity.kt`, started through `ExternalSites.kt`; an activity rather than a dialog, because a dialog never got the keyboard focus and Back went to the app instead of the site), **not** the app's webview, so it has no JavaScript interface or Tauri bridge either, with the same navigation rule; **Each site is a task of its own in the Recents screen**, like a window (`csdrive-site://<id>`, `intoExisting`; *focus* starts it again to bring it forward). Rust starts it over JNI and **polls** `drain()` for its address/title/closed events every 300 ms while any site is open, as it does for the folder picker. Back goes back in the site's history, then closes it (the entry stays, suspended). The confirmation box is shown **by the window that asks** (`android_windows::ask`). A release build of the Android app blocks **cleartext http** (the manifest's `usesCleartextTraffic`), so there only https sites load; a debug build allows both. iOS: not implemented (the command answers with an error).

**Listed as children of the tab.** The address and the title are learnt from outside — desktop: page-load, navigation and document-title events, plus a look at the window's address every 1.5 s for single-page sites (no event is raised when those change it); the address at the start is kept as `initial_url`. In the admin-app's Apps tabs (`AppsTab`, both kinds) each **tab item** has a globe button (with a count) that opens the **external web sites level**; the level is one more in the navigation (apps → windows → tab groups → tabs → external web sites), saved like the others (`…navigation.tab`). An item shows the **globe icon**, the **title on the top row** (or "No title" until the page has one) and the **address on the bottom row**, with tags (`TagList`, as everywhere), a status dot (open/suspended), **Copy the address** and **Copy the address it was first opened at** (the two differ once the site redirects or the person navigates), bring-to-front, **Suspend**, **Reopen** and **Close**. **They can be reordered within their tab** (Sort, saved per tab as `…externalOrder`, as the other levels' orders are) and **nowhere else** — there is no cut/paste or "move to" for them, so a site can never sit under a tab other than the one that opened it (and `move_tab_to_group` takes the tab's sites along: their `window_guid`, who hears about them, follows the tab).

**Lifecycle — suspend and close, as for windows** (see "Suspending vs closing"). **Suspending** a site (`suspend_external_site`) closes only its window: the entry stays, as *suspended*, and **Reopen** (`reopen_external_site`, no confirmation — the person is asking in the admin-app itself) brings the window back at the address it was at. **Closing** it (`close_external_site`) closes the window *and* removes the entry with its tags. The same follows the tab it was opened from: **suspending the window a tab belongs to suspends all the sites opened from its tabs** (`handle_window_destroyed`, so every route to a suspend does it — the buttons, "suspend all", closing the tab being shown, Android leaving the app), while **closing** a tab, deleting its tab group or closing/removing its window entry **closes** its sites (`close_tab`, `delete_tab_group`, `delete_window_and_tags`; the DB work is `external_sites::delete_for_tabs/_for_window`, the windows are closed by the caller). Entries survive a restart, as suspended. (An app can have sites open for one tab at a time only in practice — a window shows one tab.)

## Links between pages of web apps (`link_navigation.rs`)

A web app's window never moves itself, so a click on an **anchor** to another page of its own storage (a path, with or without a query), a `GET` form, `target=_blank` / `window.open` and `history.pushState('…')`/`replaceState('…')` (turned into `location.assign` by the guard script) all reach the window's navigation rule as a **request** (`Nav::Request`, `OwnPage.on_request` on desktop, `nativeNavigation` on Android). The window stays where it is and the person is asked, in native boxes that belong to the window (`window_host::choose`: the dialog plugin on desktop — with **no parent**, a box with the window as its parent never showed —, `android_windows::ask` on Android). A native box has **at most three buttons** and one closed with its X/Esc answers as its last button, so every box ends in **Cancel**: *Open… / Copy… / Cancel*, then *In this tab / In a new tab / Cancel* or *To the clipboard / To the app's clipboard / Cancel*. The first box says what the link is: **Type** (Web page (HTML), Markdown document, Note, File or folder), **Path** (in its storage — `/docs/a.md`, the address that is copied and that a "Go to a path" box takes; a query is shown with it) and **In** (the user folder, "the folder X", the Filen account and branch). A link that can't be opened in a window (a picture, a folder) goes straight to *To the clipboard / To the app's clipboard / Cancel*. **A note's address is opened like a page**: `Open…` → *In this tab / In a new tab* — its markdown file is looked for when the person chooses (`link_navigation::note_page`: the file in the note's short folder whose name ends with `[note].md`, in the user folder, a picked folder or a Filen account/branch) and the tab shows that page; a note with no markdown says so.

**Addresses.** The browser already resolved a relative link against the page's own address, so it is relative to the file that was opened as a web app. An **absolute** path is relative to the root of the page's **storage** — a picked folder's root or the Filen account's (branch's) root — not the user folder the browser took it for: `link_navigation::resolve` puts it back under the page's `@device/<root>` / `@filen/<user>/<branch>` prefix (in the user folder an absolute path is just a path). A link can't lead out of the storage its page is in (another folder, account or branch, or from the user folder into one): refused with a box saying so. A query with the key **`note`** makes the address a note's — not a folder's or a file's (`classify`; opening notes comes with the notes themselves). Copying uses `tauri-plugin-clipboard-manager` for the OS clipboard (Rust only: no capability grants its commands to a page; retried a few times, as another program can hold the clipboard for a moment) and the app's own clipboard (`internal_clipboard`).

**In this tab / in a new tab** (`secondary_windows::open_link_in_window`). A web app's window has tab groups and tabs, and until now every tab of it was the same page (the app itself decided what a tab showed). A tab can now show **another page** (which does not stop it being a tab of its window's *app*: `tabs.relative_path` is not changed, so it can still be moved to another window of the same app with `move_tab_to_group` and goes on showing its page there): `tabs.link_page` (the page's path as a URL has it, and its query) is set when the person opens a link in it — the tab keeps `relative_path`, its window's app, which is what lets it be moved to another window of the same app (`move_tab_to_group`; it goes on showing its page there), its `resource_id` is that of the new page and its label is cleared until the page registers itself — or a new tab of the same tab group is made with it (it becomes the window's current tab); then the window is **taken there** (`window_host::navigate`: the window's navigation rule is told first — desktop keeps the page each window is at in `OwnPage.url`, Android in its window state — and the webview navigates). `page_to_show` says which page a window shows for a tab (`link_page`, else the page the window was made for): it decides what `reopen_secondary_window` and `activate_tab` open, and `activate_tab` on an **open** window whose tab shows another page takes the window there (a tab with no `link_page` still gets the `tab-navigate` event, as before). `link_page` follows the resource id the page reports with `update_tab_resource`, and `init_window_tab`'s answer names the file of the tab (`relativePath`: its path in the storage) rather than the window's (`fill_origin`). A page that never registers a tab (a plain html file) still works: its window's pending tab is the one that is used. The window's app (its entry's `relative_path`, the key of its app state) stays that of the page it was made for. This holds for **every kind of window, a system app's too**: Notes shows a note's page in a tab of its own window (see "The note pages"); a tab may also carry `tabs.syncs` (the served path of a file it follows — only such tabs are reloaded by `notify_file_saved`).

Tested live on desktop (isolated data folder; the boxes pressed with `TDM_CLICK_BUTTON`): a `#fragment` and `pushState('#h')` ask nothing, `pushState` to another origin throws, a relative / absolute / query link and a `pushState` path each show the box with the right type, path and place, *In this tab* and *In a new tab* (one tab / two tabs of one group; activating each takes the window to its page), the two clipboards' box (the app's clipboard checked), a picture and `target=_blank`, Cancel, a markdown link, and suspending and reopening (the window comes back at the tab's page). Not verified live: the OS clipboard's content — this machine's session had no access to the OS clipboard at all (`Set-Clipboard` fails there too), only that a refusal is reported in a box.

## No network access for any window (CSP)

The policy is written once, in `src-tauri/tauri.conf.json` (`app.security.csp`; `devCsp` is the same plus the Vite dev server's websocket). Tauri applies it to the admin-app's own pages (adding hashes for the inline scripts in `index.html`), and `respond` in `lib.rs` sends the very same string, read back from the config, as a header with every `csuser://` page — so user web apps and the admin-app alike are under it. A script can reach only its own origin's files, `data:`/`blob:` URLs, and the IPC channel to this backend (`ipc:` / `http://ipc.localhost`, depending on the OS): `fetch`, XHR, WebSocket, EventSource, beacons, external scripts/styles/images/fonts/frames and form posts to anything else are all blocked, and `default-src` is `'none'` so anything not listed is too. Inline scripts/styles remain allowed (`style-src-attr` is spelled out because Tauri's script/style hashes make `'unsafe-inline'` inert for `style-src`, which would otherwise break inline `style=""` attributes); `eval` is not. **A click on a link to the web opens the OS default browser**, not this app: `lock_down_navigation` hands every http/https address a window would navigate to (an anchor, `location.href`) or open in a new window (`target=_blank`, `window.open`) to `external_sites::open_in_browser` (desktop: `rundll32 url.dll,FileProtocolHandler` / `open` / `xdg-open`; Android: an `ACTION_VIEW` intent, `ExternalSites.openInBrowser`) and the window stays where it is; only what `check_url` accepts is opened. Opening a site *inside* this app happens only programmatically, with `open_external_site` (below). CSP doesn't cover navigating the window itself, so `lock_down_navigation` (`on_navigation` + denying `window.open`) confines every window to our own origins — web app windows to `csuser` only, the main window also to the admin-app's (`tauri://localhost`; `http://tauri.localhost` on Windows and Android; the dev server under `tauri dev`) — applied to the main window and every secondary window, so any new window builder must use it. A web app that needs anything from outside talks to it through a backend command (as Filen does), never directly. To add an exception, edit `tauri.conf.json` and the test that reads it (which asserts the policy names no external host).

## Android (and every other platform)

**Standing rule: everything in this app — what exists and everything added from now on — must work on Android as well as on desktop.** Check each new feature on the emulator, and keep desktop-only code behind `#[cfg(desktop)]` with a real Android counterpart (or an honest "not available on this platform" that the UI hides).

**Building.** The crate is a lib (`src/lib.rs`, `pub fn run()`, `#[cfg_attr(mobile, tauri::mobile_entry_point)]`) plus a two-line `src/main.rs`. The Android Studio project is `src-tauri/gen/android` — generated by `cargo tauri android init` but **committed and hand-edited**: `MainActivity.kt` (edge-to-edge + the safe-area bridge), `SecureKey.kt` and `DeviceFiles.kt` (Kotlin helpers Rust calls over JNI), `WindowActivity.kt` + `WindowBridge.kt` (the windows of web apps and system apps — see "Windows on Android"), `ExternalSites.kt` + `ExternalSiteActivity.kt` (external web sites) and `FolderPicker.kt`. From `csdrive-webhost-tauriapp`: `cargo tauri android build --debug --target x86_64 --apk` (it runs `npm run build` itself; needs `ANDROID_HOME`, `NDK_HOME`, and **JDK 17** as `JAVA_HOME` — Android Studio's bundled JDK 25 breaks Gradle). Testing without a device: an emulator (`quick_notes_pixel_34`, headless), `adb install -r` (keeps app data), and Chrome DevTools remote debugging (`adb forward tcp:9222 localabstract:webview_devtools_remote_<pid>`, then the CDP HTTP/WebSocket API) to run `window.__TAURI__.core.invoke(...)` in the pages. In Git Bash set `MSYS_NO_PATHCONV=1` for adb. The emulator's app data is its own — nothing touches the desktop data.

**Windows on Android** — every window is an activity of its own (`android_windows.rs`, `WindowActivity.kt`, `WindowBridge.kt`; the reasoning is in `docs/strategies/android-windows-strategy.md`). Tauri creates exactly one webview on Android (the one in `MainActivity`, which shows the admin-app and nothing else), so each secondary window is a plain `android.webkit.WebView` in a `WindowActivity`, with a bridge of our own to the backend. Each is **its own task in the Recents screen** (`documentLaunchMode="intoExisting"`, the task keyed by the intent's data `csdrive-window://<guid>`; opening a window that is showing brings it to the front), so the person switches between windows with the system's task switcher, and opening app B never disturbs app A. A window entry is **open** while its activity exists; **Back** — or swiping it away in Recents — **suspends** it (entry, tabs and tags kept, its task removed; an accidental swipe must not delete a tab group), the admin-app's *Suspend*/*Close* finish the activity from Rust (*Close* also deletes the entry), and the cascade rules of "Suspending vs closing" apply as on desktop (suspending a window suspends the external sites and the web apps opened from its tabs). If the process is killed, entries are suspended at the next start; a task the system brings back whose window the (restarted) backend doesn't know starts the app and finishes itself. All the commands (`open_new_/reopen_/suspend_/close_/close_all_/suspend_all_secondary_window(s)`, `focus_`, `activate_tab`) keep their signatures on both platforms.

- **How a page reaches the backend.** `window.CsdriveBridge` is a JavaScript interface `WindowActivity` attaches to *its* WebView for *its* guid; `scripts/window-bridge.js` builds `window.__TAURI_INTERNALS__` on it (invoke, callbacks, metadata) and the crate's build copies Tauri's own `window.__TAURI__` bundle (`build.rs` → `window_scripts.rs`), so `__TAURI__.core.invoke`, `getCurrentWebviewWindow().listen` and `@tauri-apps/api` work as on desktop. `invoke` goes `CsdriveBridge.invoke` → `WindowBridge.nativeInvoke` (JNI) → `android_windows::dispatch` → Tauri's own dispatcher (`Webview::on_message` of `main`), so every command runs exactly as if its page had called it; the answer returns as `runCallback` (or, for raw bytes — an `ArrayBuffer` — the page fetches them once from `http://ipc.localhost/raw/<key>`, so a big file isn't base64ed). Request bodies are JSON only (bytes as base64 in a JSON object, `invokeWithBytes`'s Android form). `plugin:event|*` is kept in the page (listeners live there; Rust delivers with `window_host::emit_if_open` → `__csdriveEmit`, to that window only), `plugin:dialog|message` is a native dialog on the window's activity; **every other `plugin:` command is refused**.
- **Who is calling.** Commands that need to know take `window_host::CallerWindow` instead of `WebviewWindow` (it derefs to it): on desktop it says what the window's label says; on Android it says what the *activity* said — `dispatch` puts `x-csdrive-caller: <secret>:<guid>` on the request (the secret is made at startup, so no script, the admin-app's included, can forge it; a claim that doesn't check out is an error, never the admin-app). `caller_guid`/`caller_key` give web apps and system apps their identity (app state, SQLite handles, upload sessions), `require_admin` gates admin-only commands, `require_trusted` those the system apps may use too. A page's *address* is never consulted on Android. A window may call only the commands the capability files grant to windows (`window_host::window_commands`; a unit test keeps it disjoint from `admin.json` and inside `build.rs`' list).
- **Serving.** The WebView loads `http://csuser.localhost/…` (web apps) or `http://tauri.localhost/system/<id>/index.html` (system apps) — the addresses wry uses — and `shouldInterceptRequest` answers **every** request from Rust (`nativeServe`): the user folder, `@device`, `@filen` and markdown as ever (`lib.rs`' `serve_user_path`), a system app's files from Tauri's asset resolver (only under `system/` and `assets/`, checked against the embedded keys — the resolver would answer an unknown address with the admin-app's `index.html`), always with the CSP header. **A request to any other host is refused.** A system app's window may also load files of the user origin — its pictures and media, which its CSP allows as `img-src`/`media-src` only (Notes' viewer and thumbnails). `nativeServe` is given the request's `Range` and `Origin` headers, so a media file is answered a piece at a time (`file_serving.rs`, below) and never held whole by the JVM either. `/@csdrive/window.js` (the bridge, Tauri's global, the frozen-address guard) is answered before anything else and put first in every html document's `<head>` (`window_scripts::with_script_in_head`).
- **Frozen address.** `shouldOverrideUrlLoading` asks `navigation_verdict` (the desktop rule): the window's own page (a reload, a fragment) goes ahead, a link to the web goes to the OS browser, a request for another page of the app is put to the person (`link_navigation`; the box is `android_windows::ask`, on the window's activity) and the rest is blocked; the guard script turns `pushState`/`replaceState` into such a request and removes `navigation`.
- **Dialogs and the file chooser.** `alert`/`confirm` and plugin-dialog's `message`/`ask`/`confirm` are native dialogs on the window's activity; `<input type="file">` opens the system chooser (`onShowFileChooser`). Rust asks the person things in a window with `android_windows::ask` (the external-site confirmation) — a dialog of the app's main activity would be invisible over a window.
- **Insets.** A window pads its root by the system bars, the cutout and the keyboard (no `--csdrive-safe-area-*` variables there, so the code snippet's padding is 0).
- Tested on the emulator: a user web app and Notes as their own tasks, the bridge (identity, refusals of admin-only and `plugin:` commands, raw bytes, events, state), Back / Suspend / Reopen / Close, a second open bringing the task to the front, an external site as its own task with the confirmation on the asking window, the suspend cascade, and the frozen address.

**Custom protocols.** On Windows and Android the scheme `x://localhost/...` is served as `http://x.localhost/...`. `WebviewUrl::CustomProtocol` converts it when a window is built, but `navigate()` does not — always go through `window_host::navigation_url` (Android showed `chrome-error://chromewebdata` without it). Custom-protocol pages count as local, so capabilities can't scope by URL (hence `require_admin`). On Android the windows' WebViews are served by our own `shouldInterceptRequest` (above), which uses the same addresses. The admin-app is served by Tauri itself, not by us: `http://tauri.localhost` on Android (`tauri://localhost` elsewhere), recognised by `window_host::is_admin_url`.

**System bars and the safe area** (the admin-app's webview; a window's activity pads itself, see above). Tauri apps fill the whole screen on Android, under the status bar and the gesture/navigation bar. Android's WebView reports `env(safe-area-inset-bottom)` as 0, so `MainActivity.kt` measures the real insets (system bars + display cutout, in CSS px) and publishes them as CSS variables `--csdrive-safe-area-inset-top/right/bottom/left` on `<html>` (an initialization script on every page reads them from the `CsdriveSafeArea` JS interface and `__csdriveApplySafeArea` keeps them current). They are 0 when the bars are hidden, so a full-screen mode simply gets the whole screen. A window's **page** can go full screen (`element.requestFullscreen()` — the media viewer does): `WindowActivity`'s `WebChromeClient.onShowCustomView` puts the element over the whole window and hides the system bars (they come back with a swipe; Android shows its own one-time "Viewing full screen" notice the first time, which takes the first Back), and **Back leaves full screen first** — only then does it suspend the window. There is still no full-screen mode for the admin-app itself. The css that consumes them (`SAFE_AREA_CSS` in `code_snippets.rs`: pad `<html>` by the four variables, `height:100%`) reaches every page not because each web app copies it but as a **code snippet**: `init_window_tab`'s response has a `codeSnippets` list of `{ code, type }` entries (`type`: `css`, `html` or `javascript`; today one css entry), and `get_code_snippets` returns the same list. **Web apps must apply the snippets they receive** (`sample-apps/qwer/_tab-lib.js` does — `TabLib.applySnippets`, also called automatically for `openTab`'s response and on load; the admin-app does it before its first render, `src/lib/codeSnippets.ts`). Anything platform-specific that every page needs should be added to that list rather than asked of each web app. Layout inside the admin-app therefore uses `height:100%`, not `100vh`.

**Loading indicator.** Nothing web-side can be shown until a page exists, so startup has two spinners. (1) From the first paint: `index.html` contains a spinner inside `#root` (styles `.app-splash` in `App.css`, same markup as `components/Splash.tsx`, which `App` shows while the saved tab loads). (2) Android only, for everything before that: `MainActivity.showSplash` puts a native spinner (`SplashSpinnerView`, app background/accent colours, light and dark) over the whole window from `onCreate`, on the decor view because wry later installs the WebView with `setContentView`, which would discard anything added to the content area; the window theme's `windowBackground`/splash background (`csdrive_bg`, `res/values{,-night}`) avoids a white flash before it. The admin-app removes it (`hideNativeSplash` in `src/lib/nativeSplash.ts`, via the `CsdriveSplash` JS interface) when its first screen is ready; it also removes itself after 10 s so a page that fails to load is never hidden behind it (`adb logcat -s CsdriveSplash` shows when it appeared and how long it stayed). The spinner draws itself from the clock rather than using Material's indicator or any `Animator`, because Android's "remove animations" / animator-scale-0 setting turns those into a static icon or nothing at all. On desktop the blank stretch is native startup (release build, warm profile: ~0.45 s for WebView2 before any page can exist, then ~0.13 s to first paint; a debug build adds ~0.4 s of unoptimised runtime start), which page content can't cover. The database setup is ~30 ms and not a factor.

**Secrets.** `secure_store` on Android keeps the 32-byte key wrapped by an Android Keystore key (`SecureKey.kt`; the wrapped blob is in the private `csdrive_secure_store` preferences); Rust reaches it through `android_jni.rs` (`on_activity`, `helper_class` — the activity's class loader is required to find our own classes). Verified: same key across restarts.

**Admin-app differences** (`src/lib/platform.ts`: `isMobile` from the user agent). No custom data folder (`pick_and_set_custom_data_folder` errors; `DataFolderInfo.canRelocate` is false and Settings hides it). "Add root folder" uses our own picker — see "Picked folders" below. Uploads use the webview's own `<input type="file">` chooser (`pickFilesFromDevice`) because the native dialog returns content URIs the fs scope can't cover. Exports go through `save_to_device` (`device_files.rs` + `DeviceFiles.kt`): admin-app and system apps only (`require_trusted`), the bytes are the request body and the name a header, stored in the public Downloads folder via MediaStore (no permission needed on Android 10+; a name collision gets ` (1)`); on desktop `exportToDevice` first asks the backend for a location (`choose_save_location` shows the native "save as" dialog and returns a one-time token) and only then reads the data and sends it with the token (`save_to_device` writes it there — so a big Filen file isn't fetched before the person has chosen where it goes). Byte payloads to the backend go through `invokeWithBytes` (see "Sending bytes to the backend"); a file that is already on the device is not sent at all — the page names it (`export_local_file`, `filen_cache_upload_from_path`) and Rust copies it. "Delete app data" ends the process on mobile (`app.restart()` can't relaunch there) — the next launch starts fresh.

**Picked folders (the Files tab's "Add root folder"; see also "The file scope").** On desktop this is the OS folder dialog. Android has no folder-picking dialog that hands back a real path (the official dialog plugin has none on mobile, and the system one gives `content://` URIs that path-based code can't use), so the app ships its own, `FolderPicker.kt`: a dialog that browses the real filesystem — storage volumes (internal storage, SD card/USB) and their folders, Up, New folder, Cancel, Use this folder — and hands back a real absolute path — *to Rust only*. From then on a picked folder is the same on both platforms: `picked_roots.rs` adds it to our scope and remembers it in `data.db`; the Files tab lists it again after a restart (`loadSavedRoots`, by root id — the opaque id `picked_roots.rs` made for it — so tags keyed by root id persist); SQLite databases in it and web apps use it through the ordinary file commands. **Persistent on both platforms** (desktop picks used to last one session). The ×/`remove_picked_root` **revokes it at once**. Rust starts the Android dialog over JNI and **polls** a static result string (`pending` → `picked:<path>` / `cancelled` / `error:<message>`) — no native callback needed. It needs Android's **All files access** (`MANAGE_EXTERNAL_STORAGE`, Android 11+; on 10 and older the classic READ/WRITE_EXTERNAL_STORAGE with `requestLegacyExternalStorage`), asked for the first time a folder is picked: the app opens that system settings page and on coming back continues, or reports "Storage access wasn't granted…". **Google Play restricts this permission** (a declaration and approval are needed); for sideloaded or personal builds it is fine. Verified on the emulator (API 34): the first-use permission flow, browsing, New folder, cancel/back, denied access, read/write/mkdir/rename, SQLite in a picked folder, the scope boundary, immediate revocation (read, list, write and SQLite all refused right after forgetting) and picking the same folder again in the same session, persistence across restarts. Not run: the Android 10-and-older permission path. Real deletes are permanent, as on desktop.

**Sending bytes to the backend.** Android's WebView can't hand a POST body to a custom protocol, so Tauri's IPC there falls back to postMessage, where a `Uint8Array` becomes a JSON array of numbers — 20 MB is tens of millions of JSON values (11 s and a huge memory spike in testing). Commands that take a file's bytes (`filen_write_file`, `filen_cache_write`, `save_to_device`) therefore read them through `ipc.rs` (`body_bytes`, `field`), which accepts the raw body + percent-encoded headers (desktop), or a JSON object `{ ...arguments, data: "<base64>" }` (Android; ~1 s for 20 MB), and the frontend calls them through `invokeWithBytes` (`src/lib/ipcBytes.ts`). A new upload-style command must do the same, and web apps sending big files on Android should send base64 that way too. (The fs plugin's own writes — the Files tab on the user folder — still use the plugin's array path on Android.) Responses are unaffected: raw `ArrayBuffer` responses work everywhere. **Big files don't use these at all** — see "Big files" in "The Filen cache": a file is sent in pieces (`filen_cache_upload_chunk`, 4 MiB at a time, so this base64 detour is per piece) or never leaves Rust.

**Not done:** iOS (`secure_store` has an error stub; the Xcode project doesn't exist).

## System apps and Notes

A **system app** is an app that ships inside this one: a page of the admin-app's own Vite project under `system/<id>/index.html` (its React code in `src/system/<id>/`), listed in the Rust catalog `system_apps::APPS` (`id`, `name`, `entry`) and as a `rollupOptions.input` entry in `vite.config.ts` (the two must agree — the multi-page build puts each in `dist/system/<id>/`). The set is fixed: there is no way for a user to add one, and the System Apps tab (first tab, the default) lists the catalog by name — `list_system_apps`, so an app shows there even before it has a window. **Adding a system app** means: the folder above, the catalog entry, the `input` entry, and a `cargo build` after `npm run build`.

The whole window machinery is the user apps' one, kept separate by a `kind` (`user`|`system`) on `secondary_windows` rows: the `list_/open_new_/add_…entry/close_all_/suspend_all_` commands take an optional `kind` (all kinds when omitted — the data-wipe path closes everything), `reopen_secondary_window` needs only the guid (the row says what to show), and the admin-app's `AppsTab` is one component with a `kind` prop and its own saved orderings (`systemAppsTab.*` vs `windowsTab.*`). A system window stores `system:<id>` as its relative path (also the key of its app state, tab icons and app version), so nothing can be confused with a user app's html path. Tabs work identically — `init_window_tab`, `update_tab_resource`, `submit_resource_icons`, `activate_tab`, the `codeSnippets` in the init response. **Closing a tab** (`close_tab`, the × on a tab item in either tab page) deletes the tab and its tags; if it is the tab an *open* window is showing, that window is also **suspended** (entry and other tabs kept, `reopen_secondary_window` brings it back showing the tab it showed before, or its first remaining one, or a new blank one if none is left), and closing any other tab leaves windows alone. "The tab a window is showing" is `SecondaryWindowsState::current_tabs`: set when the page binds to a tab (`init_window_tab`, `add_window_tab`) or is sent one (`activate_tab`), **kept when the window is suspended** (so reopening it shows the same tab) and dropped when the entry is.

**Who creates tabs.** Tab entries are made by the **admin-app side first**, and a page only *binds* to one:
- **Opening a window** (`open_new_secondary_window`, `add_secondary_window_entry`, `reopen_secondary_window`) first decides which tab the window will show (`tab_for_opening`): the tab it showed before, else its first tab, else a new blank placeholder (in its first group, or a new "Tab Group N" if it has none) — so the entry is in the list before the page exists. That tab is left *pending* for the window.
- **`init_window_tab`** — called by the page as it loads — **never creates a tab** (`tab_for_init`): it binds to the tab left pending for it (echoing the tab's stored resource id, except for a placeholder that was just created, which is filled in from the page's URL); with nothing pending it is a **reload** (or a second call), and binds to the window's current tab. So refreshing a window doesn't add a tab, and neither does calling init again.
- **`new tab` / `clone` in the admin-app** (`add_blank_tab`, `clone_tab`) create an entry there; `activate_tab` then shows it (below).
- **`add_window_tab`** is the one request with which a **web app adds a tab itself** — a second document, a new view. Same parameters and answer as `init_window_tab` (`addWindowTab` in `src/lib/secondaryWindows.ts`, `TabLib.addTab` in the samples); the new tab is placed in the group of the tab the window is showing and **becomes the window's current tab** (the page is showing it now, so a reload binds to it).

**What a page is told about itself** — the answer to `init_window_tab` / `add_window_tab` and the payload of `tab-navigate` (`TabInitResponse`): besides `tabGuid`, `resourceId` and `codeSnippets`, its own **`relativePath`** (from the user folder for a web app, `system:<id>` for a system app; for a file opened from Filen, its path in the drive), **`openedBy`** (`AdminApp` — opened from the admin-app itself — or `NotesApp`) and **`storage`** (`UserFolder`, `DeviceFolder`, `FilenCloud` or `Bundled` for a system app), and — when `storage` is `FilenCloud` — **`filen`**: `{ accountId, email, branch, branchIndex }` (the branch's name and index, or null). These are strings named after enum members, not booleans, so more can be added. Where they come from: `secondary_windows.origin` (JSON, `Origin` in `secondary_windows.rs`), recorded when the window entry is made; an entry with none is the ordinary case (`AdminApp` + `UserFolder`/`Bundled`, its own path). `fill_origin` adds them to every response.

**Tab labels and window titles** (`update_tab_resource`, `TabLib.updateTab`). A page tells what its tab shows with `tabText` — `{ firstRow, secondRow }`, each a list of pieces `{ text, bold?, italic?, mono? }` (`mono`: written in a monospaced font, like code; the flags are optional and a label stored before `mono` existed reads as not mono) — and, optionally, `appTitle`, a string. The window manager draws the two rows (`TabTextRow`: a bullet between the pieces of a row). **The title of the window** — the OS window's title on desktop, the card in the Recents screen on Android — is the tab the window is showing: its `appTitle` when it has a non-empty one, else **the pieces of the first row joined with ` • `** (the bullet the window manager draws between them; empty pieces left out, the second row not used), else what it was opened with (the page's path, or the system app's name). It is one plain line: no styles, line breaks become spaces. Both the label and the title are **replaced by every call** (sending no `appTitle` takes it back, so send it every time), and `secondary_windows::refresh_window_title` puts the result on the window whenever it may have changed: an update of the tab, a page binding to its tab (`init_window_tab`, `add_window_tab`) and switching tabs (`activate_tab`) — through `window_host::set_title` (`WebviewWindow::set_title`; `WindowBridge.title` → `setTaskDescription` on Android). Stored per tab: `tabs.app_title`, and `appTitle` in the tab's record.

**A tab's resource identifier can be read and copied** in the admin-app: the tab item's **#** button opens a dialog with it (and the app's page path) and a copy button.

**Suspending vs closing (windows), and deleting (tab groups, tabs).** A window entry in the list is either *open* (its window is showing) or *suspended* (only its entry exists). The two ways of getting rid of a window differ in what happens to the **entry**:
- **Suspend** (`suspend_secondary_window`, `suspend_all_…`) closes **only the actual window**. The entry stays in the list — with its tab groups, tabs and tags — as *Suspended*, and **Reopen** (`reopen_secondary_window`) brings the window back.
- **Close** (`close_secondary_window`, `close_all_…`) closes the window **and removes its entry** from the list, with its tab groups, tabs and tags. It works on a suspended window too — that is how a suspended entry is removed (there is no window to close, so only the entry goes).

**Closing the main window** (desktop) first suspends everything: `secondary_windows::main_window_close_requested` — on the main window's close request — **first** raises `shutting_down` (a flag on `SecondaryWindowsState`, not persisted: it only matters until the app is gone), then holds the close back while every secondary window is suspended (windows and the external web sites' windows closed, entries kept) and only then closes the main window for real (the second request is let through). While the flag is up `handle_window_destroyed` treats *any* window that goes away — ours, the person's, the OS's — as suspended, so even if the OS ends the app before the suspending is done no entry has been removed. (Tested: two secondary windows open, WM_CLOSE to the main window — both entries kept, the process exited.) On Android there is one window; nothing to do.

**Reload** (`reload_tab`, `reload_secondary_window`; a *Reload* button on a tab item — offered only while an open window is showing that tab (`TabRecord.showing`) —, on an open window's row and on an opened-from-this-tab app): the same as `location.reload()` in the page the window shows; a tab that no window shows has nothing to reload and the command says so. **A reload keeps the page's scroll** (the webview restores it; checked with a 220-line page on desktop and Android — a syncing note tab reloading on save stays where it was read).

The admin-app's buttons say which is which in their tooltips (Suspend (or Reopen) / Close on a window row, and — acting on the whole window — at the top of both its tab groups view and the tabs view of any of its groups, and "Suspend all" / "Close all" at the top level and per app). Below a window: **deleting a tab group** (`delete_tab_group`, 🗑 on its row) removes the group with its tabs and their tags, and **closing a tab** (`close_tab`) removes that tab; when what goes includes the tab an *open* window is showing, that window is **suspended** (not closed — its entry survives, minus the deleted tabs), and otherwise windows are left alone.

**Switching tabs is an event** — the same for system apps and user apps. `activate_tab` on a tab of an *open* window sends that window (only) the **`tab-navigate`** event (`secondary_windows::EVENT_TAB_NAVIGATE`), whose payload is exactly what `init_window_tab` answers with — `{ tabGuid, resourceId, codeSnippets }`, the tab's own stored resource id (empty for a tab never used) — and the page **shows that tab in place; it is not reloaded**. An app with several tabs must therefore handle it (`onTabNavigate` in `src/lib/secondaryWindows.ts`; `TabLib` for the samples: it listens from the moment it loads, its default reaction is to start the page over (`location.reload()`), and `TabLib.onNavigate(handler)` replaces that; `TabLib.openTab` binds the page, `TabLib.addTab` adds a tab). **Attach the listener before calling `init_window_tab`** (`await onTabNavigate(…)` first) so no event can be missed. A window that isn't open is simply opened with that tab left pending, and its page's init response says which tab it is. For an open window the activated tab becomes the window's current tab, so if its page loads again (a reload the app does itself in response, or the person pressing reload) its init binds to that tab — it can't create another. **Listen on the page's own webview window** (`getCurrentWebviewWindow().listen(…)`, `webviewWindow.getCurrentWebviewWindow()` in the samples), never the global `listen`: a global listener also hears events sent to *other* windows (found live: it made another window reload and create an extra tab). Notes handles it by switching to the tab's place (`system:notes?s=…` in its resource id), keeping each tab's own place; its editor keeps the source of the file it holds, so a switch can't redirect a save.

**A system app is not the admin-app.** Admin identity is **path-based**, not origin-based: `window_host::is_admin_url` is true only for the frontend's root page (`/`, `/index.html`), `is_system_url` for pages under `/system/`, and navigation is confined per kind (`Allowed{user,system,admin}`: a user window reaches only `csuser`, a system window only its own pages, the main window the admin-app's). A system window gets exactly the user apps' capabilities (+ `system-apps.json`), never `filen_login`, data-folder or deploy commands — verified live: Notes is refused `filen_logout`/`delete_app_data` like a user app. On Android, where a window's WebView is not Tauri's, who is calling is what its activity says (`CallerWindow`), and a system window is one whose page is a system app's.

**Notes** (`src/system/notes/`) is a *unified file manager* whose sources are folders on this device (the user folder and picked folders, through the ordinary `fs_*` commands) and the connected Filen accounts (through the cache below), behind one `FileSource` interface (`sources.ts`) — so copy/cut/paste works between any two of them (read + write; same-source cut is a rename). It lists **paginated** (client-side, the page size being the global one), fetches a local folder's sizes/dates only for the page on screen, edits text files (≤ 2 MB, UTF-8), uploads, exports (`save_to_device`), renames, deletes. Per Filen account it shows the **cache interval** selector (incl. "Never (available offline)"), the cache's freshness (or "Offline — showing the listing as it was"), "Clear the cache", and the **branch** bar (switch, new, changes, commit — asking before overwriting on conflict — discard). Each Notes tab is a *place* (`Place` in `tabs.ts`) — one of three **views**: the **home page**, the page for **managing notebooks**, or the **file manager**. Its resource id names it: `system:notes?v=home`, `system:notes?v=notebooks`, or — for the file manager — `system:notes?s=<source>&b=<branch>&p=<path>`; it is updated as the person navigates (a page can't change its own address — the window manager stores the resource id), so activating, cloning or reloading a tab returns to it; the window manager's tab icon distinguishes home / notebooks / local / Filen / branch. **A tab that names no place starts at the home page** (`NotesRoot.tsx` chooses the view; the file manager, `NotesApp.tsx`, is what it was, with a *Notes home* button added). Notes also remembers the last place of the file manager in its own app state — where the home page's *File manager* link goes.

**Notebooks** (`notebooks.ts`, `notebookFile.ts`, `NotebooksPage.tsx`, `LocationPicker.tsx`; the format and the idea are in `docs/strategies/notes-strategy.md`). The **home page** has two links: *Manage notebooks* and *File manager*. A notebook *is* its `[note-book].json` file (`{ "Title", "CreatedAt", "NoteBookGuid" }`) and its folder is the notebook's root; the app keeps only **a list of the notebooks it knows** — `notes.notebooks` in the Notes app's own state (`data.db`), entries `{ guid, title, sourceId, folder, fileName, addedAt }`, where `sourceId` is a folder of this device or a Filen account (never a branch). **Listed** (in that list) and **found** (the file exists on this device or in Filen, the app hasn't been told) are told apart by the GUID in the file. The *Manage notebooks* page lists them — each checked against its file when the page opens (unreachable, or no longer a notebook, is shown with the reason; a title changed outside the app is taken into the list, the file being the truth) — with: **show its folder** in the file manager, **change its title** (written to the file first, every other key of the file kept, then to the list) and **take it out of the list** (asks; nothing is deleted, the files stay). **Add a notebook…** asks whether to *add an existing notebook* (the person chooses its `[note-book].json`, in a place picker that marks every notebook file it shows with its title and **"in your list" / "not in your list yet"**; a file that isn't a valid notebook is refused with a reason, one that is listed already is reported, with where) or *create a new one* (a title, then the root folder in the same picker — which can also make folders and add a folder of this device — and the file is written; the folder need not be empty). **Warning:** a folder that already holds a file whose name is or ends with `[note-book].json` is flagged in the picker, and choosing it opens a dialog listing those files (with their titles) — a notebook's notes live in its root folder, so a second notebook there would share them — to *choose another folder* (the picker comes back to that folder), *cancel*, or *create it here anyway*; a new notebook's file is named `[note-book].json`, or, when that name is taken, after its title (`<title> [note-book].json`, never overwriting). **Notes** (`noteModel.ts`; the format and the idea are in `docs/strategies/notes-strategy.md`): a notebook's root folder — and every note's short folder — holds child notes as pairs of folders `NNN` + `NNN-<title>` (numbered *after the largest*, gaps stay; the marker holds a `.keep`), each with its markdown (`0-<title>[note].md`, starting with the title as a heading), `[note].json`, `[note-children].json` (the list read to show the children; rebuilt from the folders when missing or damaged) and, on demand, the two-digit internals pair `01` + `01-Note files` for the note's files. Operations (over any `FileSource`, so on this device or in Filen, in a branch too): `createNote`, `renameNote` (marker folder, markdown file, heading and both JSON files follow), `touchNote`, `deleteNote`, `readChildren`, `ensureNoteFiles`. **A note's address** is the path of its short folder with the query key `note` (`/Book/001/002?note`; `noteAddress`, `isNoteQuery`). Not built: sections, the notebook's reserved pair (`03-[note-book]`), moving notes.

**The note pages** (each a *place* of the Notes tab — `Place` in `tabs.ts`: `v=notes|noteEdit|noteFiles` with `s` (source) and `f` (the note's or notebook's folder), the window manager labelling it with the note's title):
- **`NotePage`** (`notes`): the notes in a notebook's root or in a note's folder — one page for both, with breadcrumbs (Notebooks › notebook › ancestor notes). **Clicking a note opens it as a web app in a tab of the same window** (`openNoteTab(file, sync = true)`, below): its markdown, as a page of the note's storage, in a new tab of the Notes tab's group — the **syncing tab**; clicking the same note again brings that tab back rather than making another. Each row shows the note's **index** (`001`; hidden by the Notes setting) and has icon buttons — *edit its markdown*, *its child notes*, *its files*, *show its folder in the File Manager*, *change its title*, *delete* — and a **three-dots** button; the same menu opens by a right click or a long press on the row (`components/ContextMenu.tsx`, kept inside the window whatever its width). The menu: **Edit the index…** (`changeNoteIndex`: 001–999, a used one refused; the short folder and its marker are renamed and the parent's list follows; tabs already showing the note keep their old address), **Select** / **Deselect** (a selection bar: N selected, select all, delete selected, clear), **Open as a web app in a new tab** (`openNoteTab(file, false)`: a tab of the same group that does **not** follow the editor), and **Show / Suspend / Close that tab** for the syncing tab (`note_tab_state`, `note_tab_action`; off when the note has none; *Suspend* takes the window back to the Notes tab when the syncing tab is being shown — a window shows one tab, so a tab that is not shown is already unloaded — and *Close* also deletes the tab). Under a note the page has the same buttons for the note itself. *Go to a path or a note's address*: a `?note` address opens that note, the path of a note's folder shows its children, anything else is shown in the File Manager. (Reached from the notebooks page's *Open the notebook* button.)
- **`NoteEditPage`** (`noteEdit`): a page of its own for editing the note's markdown (`CodeEditor`, "Open link" included) — files of the File Manager are edited in a popup, a note has a page. Ctrl+S or the button saves; what isn't saved is kept as a draft (`notes.noteDrafts`) that comes back with the page; a Filen note is checked against Filen first; **the title follows the first heading** (a changed heading renames the note as above); saving tells the windows that show the note (`notify_file_saved`, below).
- **`NoteFilesPage`** (`noteFiles`): the **Note Files Explorer** — the File Manager (`NotesApp` with a `scope`) working inside the note's `01` folder through `scopedSource` (`sources.ts`: every path relative to that folder, nothing above reachable; `rootPrefix` keeps disk-to-disk copies on the Rust side right), made when the note has none; each entry has *Open in File Manager*, which shows it at its place in the whole source.
- **Live refresh belongs to one tab per note — the syncing tab.** `notify_file_saved(file)` (`notes_pages.rs`, system apps and the admin-app only) reloads only the open windows whose **current tab** has `tabs.syncs` = that file's served path (`secondary_windows::syncing_windows`); any other window showing the same file (a separate tab, a window opened from the File Manager, a link) is left alone — it shows what it loaded. `open_note_tab(file, sync, new_window)` (system apps only) makes it: with `sync` it finds this window's tab with that `syncs` or adds one (`add_page_tab`, in the group of the tab being shown), then `activate_tab`; without, a new tab with no `syncs`; with `new_window`, a window of its own opened with the page (`open_notes_window_with_page` — the editor's *Open it as a web app* uses it so the editor stays on screen and the page follows it). The Notes editors, the File Manager's editor and the admin-app's Files tab call `notify_file_saved` after saving (`FileSource.notifySaved`).
- **A web page inside a system window.** A tab of a Notes window can show a web page (`tabs.link_page`, see "In this tab / in a new tab") and *what the window is follows what it shows*: the page gets a web page's rights, not Notes' — the navigation rule and `is_system_page` are recomputed from the page's current address (`lock_down_navigation`), `open_file_as_web_app` and the trusted commands (`require_trusted`) are refused for it, it has the app's clipboard like every window, and its app state and tab icons are its own (`app_state::hosted_page_id`: never `system:notes`). Its `init_window_tab` answer says `openedBy: NotesApp` with the storage of the page. Only one page of the window is loaded at a time: switching tabs navigates the window (`activate_tab`), so a page not shown is not running.
- **Notes settings** (`NotesSettingsPage.tsx`, `settings.ts`, key `notes.settings`; a place `v=settings`, reached from the home page): *show the notes' indexes* (on by default) and the app's own clipboard — how many characters it holds, and **Clear** (`internal_clipboard_clear`, which every window may call).
- **Go to a path** (`GoToPathModal`) keeps a query (`parsePathInput` → `{ segments, query }`): a file's address shows the view of its kind — the editor for a text file — and a note's address opens the note.
- Tested live on desktop (isolated data folder): a notebook made by hand, creating a note (its pair of folders and files on disk), editing and saving with the heading changed (marker folder, markdown file and both JSON files renamed), the note as a web app in a window, saving from the editor reloading that window, then (tab-hosted, isolated data folder, desktop and the Android emulator) a click on a note showing it in a second tab of the same window, a second click bringing that tab back (still two tabs, no window added), the page refused `open_file_as_web_app` and `save_to_device` yet allowed the clipboard and an app state of its own, the three-dots menu (index changed on disk with its marker, select by menu and by right click / long press, a separate tab, show/suspend/close of the syncing tab), the settings page (indexes hidden, clipboard cleared), and — desktop — a save in an editor in another window reloading the syncing tab and not the separate one; a child note, the note's files explorer (`01` made, a file made inside it, *Open in File Manager*), a note's address in *Go to a path*.

In a **Filen** source Notes also does the following (all through the cache commands below): **saving asks Filen first** (`filen_cache_check_version`) — if the file is no longer the version that was opened, nothing is written and a dialog offers *Overwrite*, *Discard changes* (the edits are lost and the file is read again) or *Cancel* (back to the editor, as if Save had not been pressed); the editor has a **New branch…** button (makes a branch and carries on in it: an unchanged file is checked out there, an edited one is saved into it with the next Save); each Filen file has a **lock** button (locked against caching) and, in a branch, a **check out** button (and *let go* for a file that was checked out and not changed) — see "Versions, locks and checkouts" below. The admin-app's own Filen tab has no editor; when an upload would replace a file of the same name it says so first.

**Editing a text file is part of the tab's place**: a tab whose editor is open has `&e=<file>` in its resource id (the file, relative to its source's root), its resource type is `editing` (its own icon), and its second row reads "Editing /file" plus, in italics, "unsaved changes" — so the window manager shows what each Notes tab is doing. Activating such a tab (or reloading the window) opens the editor on that file again, and switching to a tab that isn't editing closes it. **The unsaved text is kept as a draft** (`notes.drafts` in the app state: tab guid → source, branch, path, text, version), written a moment after the last key and when the tab is left, restored with the editor and dropped when the file is saved, its changes are discarded or the person closes the editor; the version check before saving still applies to a restored draft. A tab that names no place of its own starts from the last place but never in the editor.

## The Filen cache (`files/`)

`files_cache.rs` (the `Cache`, in `HostState`-style managed state), with `filen_cache.rs` as its commands (`filen_cache_account/_set_interval/_clear/_list/_read/_write/_mkdir/_rm/_rename/_branches/_create_branch/_branch_changes/_commit_branch/_discard_branch`, same shapes as the `filen_*` ones, plus an optional `branch`; no credential ever reaches a window). Layout inside `files/` (built with folder pairs — see below):

```
files/data.db                     listings, metadata, per-account settings, branch changes
files/a/NNN/c/…                   cached CONTENT of account NNN, at its Filen paths
files/a/NNN-filen@@<email>@@<id>/ only a .keep: says whose NNN is
files/b/NNN/MMM/…                 what branch MMM of account NNN has changed
files/b/NNN/MMM-<branch name>/    only a .keep: says which branch MMM is
files/t/NNN/…                     thumbnails of account NNN's files (see "Media")
files/tb/NNN/MMM/…                thumbnails of the files branch MMM changed (goes with the branch)
```

- **A cache, not a sync.** Nothing is fetched until asked: listing a folder fetches and remembers that listing; opening or exporting a file fetches and remembers its content. Everything remembered — listings, metadata and contents — expires after the account's **cache interval** (default 1 hour, chosen per account in Notes) and is then fetched again; with the interval turned off (`ttlSecs` = `null`) nothing ever expires, which is how a person makes things available offline. If Filen can't be reached, an expired listing/file is served marked *stale* rather than failing. Writes to the account itself go straight to Filen and update the cache.
- **Branches** are the git-like alternative: a set of local changes (files written, folders made, things deleted) kept under `b/` and in `data.db` until *committed* (applied to Filen, then the branch is deleted) or *discarded*. Reading through a branch shows Filen's cached state with the branch's changes on top. A commit first checks that Filen still looks as it did when each change was made; if not, it applies nothing and returns the `conflicts` unless `force`. A branch's name is any valid file name of ≤ 100 characters and is its folder's readable half.
- **Versions, locks and checkouts** (`files_cache.rs`, commands `filen_cache_version/_check_version/_rebase/_set_locked/_checkout/_release`):
  - A file's **version** is what Filen's listing says: whether it exists, its size and modification time (`FileVersion`). `filen_cache_version` gives the one the cache knows — what a window that has just opened the file is working on (in a branch that changed or checked out the file: the version *that* was based on). **`filen_cache_check_version` asks Filen itself, not the cache** (a locked file would keep the cache frozen), and compares it with the version the caller remembers: `{ upToDate, problem, current }` (*newer*, *different*, *deleted after you started*, *created after you started*); it fails when Filen can't be reached — the account can't be written to then anyway, and Notes lets a save into a *branch* go ahead (it stays local, and the commit checks again). In a branch, a person who chose to overwrite calls `filen_cache_rebase`, which bases the change on what Filen has now so the commit doesn't warn about the same thing again.
  - **Commit asks Filen directly too** (a fresh listing of each folder involved, no longer through the cache), and it now verifies **every** file in the branch, checkouts included: a file that changed or was deleted in Filen after it was changed *or checked out* is a conflict, reported unless `force`.
  - A **lock** (`file_locks` table, kept apart from `entries` so it survives its row being dropped and made again) freezes a file of the account: its cached copy is served as it is — no check that it is current, so it opens offline too — and neither the cache interval, a newer listing, a deletion in Filen, nor "Clear the cache" touches it (the folders above it stay too, their rows name it). Locking fetches the file first if it isn't cached (there has to be a copy to keep). It belongs to the **account's** file, so a branch that reads it through sees the same frozen copy, and the lock is available in the account and in every branch; writing to a locked file (or uploading over it) keeps it locked, on the new content, and deleting or moving it, or disconnecting the account, drops the lock. `Entry.locked` says so in listings.
  - A **checkout** (`filen_cache_checkout`, in a branch) takes a file into the branch *without changing it*: its content is copied into the branch and recorded as a change of kind `checkout`, based on the version that was copied, so it appears among the branch's pending changes. Editing it turns it into an ordinary `put` that keeps that base; `filen_cache_release` lets go of one that was never changed. Committing applies nothing for a checkout — it only had its version verified.
- **Lifecycle.** Connecting an account creates its two folders (`ensure_account`); disconnecting it (`filen_logout`) deletes its folders in `a`, `b`, `t` and `tb` — its cached files, every branch and their thumbnails — and its rows in `files/data.db` (`forget_account`); "Delete app data" and "clear the custom data folder" remove `files/` with the rest (after closing the cache's database — `Cache::close` — since Windows can't delete an open file), and relocating the data folder switches to the `files/` inside the new one, exactly as it does for `admin/`.
- The whole thing is tested without a network (`Remote` trait, in-memory remote): TTL expiry, offline stale serving, write-through, branch overlay/commit/conflict/discard, lifecycle. Live-verified on desktop **against a real Filen account** (the cache commands and the Notes UI, inside a throwaway folder in the account): folder/file write-through checked against Filen directly, a cache hit versus a forced refresh, the interval expiring and "never", rename, a branch that is committed, a real conflict (refused without `force`, the branch wins with it), a discarded branch, gap-filled branch indexes and the resulting `files/a` / `files/b` layout on disk. Also driven through the Notes UI with the `filen_*` IPC faked (the stale/offline indicator, which needs Filen to be unreachable). **Not** run live: disconnecting an account (it would log the person out; covered by unit tests), offline serving, and the Android build against a real account.

**Big files never sit in memory** (one chunk at a time is the most anything holds), on the way up, down and out:
- **Down.** A file is fetched from Filen chunk by chunk (`filen::ops::read_file_chunks`, 1 MiB at a time) into a `.part` file beside its cache location and **renamed into place only when complete** (`Cache::cached_file`); an interrupted download leaves no partial file and nothing marked as cached. `Cache::read` (the bytes API, for the editor's ≤ 2 MB) is built on it; Notes doesn't even fetch a file above 2 MB to edit it.
- **Up.** `begin_upload` / `upload_bytes` / `finish_upload` (`filen::ops::UploadSession`) cut whatever is pushed into exact 1 MiB Filen chunks, encrypt and send each as it completes, and only `finish_upload` makes the file exist (replacing an existing file by trashing the old one once the new one is readable). The cache wraps it in an `UploadJob` that also writes every piece to a temporary file in the account's `tmp/` folder, which *becomes the cached copy* when the upload finishes — Filen and the cache get each piece at the same moment. Dropping an unfinished job deletes its temporary file, and anything in flight when the app stopped is cleared at the next start (`remove_leftover_uploads`).
- **Two ways to feed an upload.** (1) *From the page*, for a `File` from the device's file chooser (which has no path): `filen_cache_upload_begin` → `filen_cache_upload_chunk` (the piece is the request body, any size) → `filen_cache_upload_finish` / `_abort`; a session belongs to the window that began it (another window's push, finish or abort is refused/ignored) and lapses after an hour. (2) *From a file the app may already read*: `filen_cache_upload_from_path(…, root, source)` — Rust reads it piece by piece; the file never goes through the window. Into a branch, either way, the file stays local until the branch is committed, and `commit_branch` streams each changed file from disk too.
- **Out.** `filen_cache_export` (to the device) and `filen_cache_download_to(…, root, dest)` (into a folder the app may use) fetch into the cache as above, then `fs::copy` on this side; `export_local_file` does the same for a local file. On Android the export streams into Downloads through MediaStore (`DeviceFiles.saveFileToDownloads`). Notes' copy/paste between sources uses these when one side is local and the other Filen, and `fs_copy` (a plain `std::fs::copy` between two places the scope allows, refusing to copy a file onto itself) when both are local — the Files tab's copy too; only the admin-app's own Filen tab (which doesn't use the cache) still moves a whole file through the page.
- **Into a local folder** the same idea, for a `File` from the device's file chooser (`fs_upload.rs`, the local counterpart of the Filen sessions): `fs_upload_begin(root, path)` → `fs_upload_chunk` (4 MiB pieces, request body + `id`) → `fs_upload_finish` / `_abort`, in `src/lib/fs.ts` `uploadFile` (used by Notes' local sources and the Files tab). Pieces are appended to a temporary file in `files/local-uploads/` — the app's own folder, never the person's — and renamed (or, across drives, copied) into place at the end, so the file appears only when complete; the destination is judged by the scope at the start *and* at the end (a folder forgotten meanwhile is refused), the upload belongs to its window, and the folder is emptied at every start. Verified live with a 96 MiB file into the user folder and a picked folder: byte-identical, 1.4 s each, and the backend's memory rose by a fixed ~25 MB (the pieces in flight), not with the size.
- Verified live against a real account with a 48 MiB file: byte-identical round trips through both upload routes and the streamed download, and the backend process's memory stayed within a few MB of idle (working set 41 → 47 MB during the upload, 45 MB during the download) instead of growing with the file.

**Folder pairs** (`folder_pairs.rs`; the strategy is in `docs/strategies/folder-pairs-strategy.md`): to make a folder that a program can address by a short name and a person can identify by a long one, create two siblings — `NNN` (the data folder; three digits, zero-padded) and `NNN-<full name part>` (a marker whose name says what `NNN` is, holding nothing but a `.keep` file with one dash in it, so it is never an *empty* folder — copying, mirroring and archiving tend to lose those; `create` and `ensure` write it, and the cache's `open` gives it to every pair at each start, which is how pairs made before the rule got theirs). `NNN` is worked out from a listing of the parent (never remembered), by the **`Numbering`** the caller uses (`Numbering::DEFAULT`: no prefix, upward from `001` with three digits, first free — in general a constant **prefix**, an **interval** of indexes going up or down, or a single constant index, and an **`Indexing`** option; `rename`/`reassign` renumber many pairs in two phases through the temporary prefix `t_`; see the strategy document, "Generalising the way the index is computed") — its **`Indexing`** option: `AfterLargest` (one more than the highest `NNN-…`; gaps are left, only an index freed by deleting the newest pair returns) or **`FillGaps`** (the lowest index, from 1, that isn't in use — `001` and `003` are followed by `002`; a bare short folder `NNN` with no full folder beside it counts as in use). **Everything we create now fills gaps** (`files_cache::NUMBERING`): accounts in `files/a`, account folders in `files/b` and branches — so deleting a pair leaves no permanent hole. One consequence to remember: a branch's index is what a Notes tab's resource id names (`b=<index>`), and a discarded branch's index can be handed to a *new* branch, so a stale tab that still names it would open the new one (a tab whose branch vanished, and whose index wasn't reused, falls back to the account). For accounts the part is `filen@@<email>@@<user id>`; for branches it is the branch's name. Use it for anything new that follows the same need.

## Media: the viewer, thumbnails, and serving files in pieces

**Serving a file in pieces** (`file_serving.rs`; used by the `csuser` protocol and, on Android, by `nativeServe`). A `<video>`/`<audio>` asks for its file with a `Range` header and seeks by asking for other ranges, so a request with a range is answered `206 Partial Content` with **at most 4 MiB** read from the file at that place (`Content-Range`, `Accept-Ranges: bytes`; a range past the end is `416`); the player asks again as it goes, so nothing bigger than a piece is ever held — in Rust, in the webview or (Android) in the JVM. A request with no range gets the whole file, as before (a picture, a script, a page). Every source is a file on disk by then: the user folder, a picked folder, or — for Filen — the cache's copy (`Cache::cached_file` fetches it there piece by piece first, so playing a Filen video starts once it is downloaded, and never holds it in memory). **Across origins**: Notes (`tauri.localhost`) loads files from the web apps' origin (`csuser`), so the CSP's `img-src` and `media-src` — and only those — name `csuser:` and `http://csuser.localhost` (the CSP test allows them for those two directives only), and an answer carries `Access-Control-Allow-Origin` **only for this app's own frontend origins** (`allowed_origin`; on Android, where the WebView doesn't always say where a request comes from, a request with no `Origin` is taken as the app's own) — so a thumbnail can be read back from a canvas, while a web page of the web, in an external site's window, can read nothing. `media_url(file)` (`system-apps.json`, `require_trusted`) gives a system app the address for a `FileRef` — segment by segment, so a `#` or `?` in a name is part of the name, and never a real path. Tested with a 600 MB file: opening it moves the process's memory by nothing.

**The media viewer** (`components/MediaViewer.tsx`, `lib/media.ts`: `mediaKindOf` by extension — pictures png/jpg/gif/webp/bmp/svg/avif/ico, video mp4/m4v/webm/ogv/mov, sound mp3/m4a/aac/wav/ogg/opus/flac, as far as the webview plays them). In Notes' **File Manager and Note Files Explorer** (both are `NotesApp`) a click on such a file — or its *View* button (an svg also has *Edit as text*) — opens it over the whole window, with the folder's other media a step away (arrows in the bar, PageUp/PageDown, ← → for pictures). The file is never read into the page: it is an address the webview loads itself.
- **Picture**: opens showing the whole of it. Zoom by the wheel (about the pointer), a two-finger pinch, the buttons, +/−/0 or a double click; drag it when it is bigger than the window — it is kept from being dragged off (`clamp`: centred while smaller than the window on an axis, no gap at either edge once larger), so zoomed in enough it fills the window. **One press on it hides the bars, the next brings them back.**
- **Video / sound**: a bar with play/pause, **back and forward 10 seconds — acting on `pointerdown`**, the time, a draggable progress, sound on/off. Playing a video **hides the bars**; a press on the video brings them back and, if it keeps playing, they go again after 3 s (the timer restarts with any touch of the bar); pausing keeps them. A sound keeps its bar.
- **Full screen** for any of them (F, or the button; Esc leaves it): `requestFullscreen()` on the viewer — on Android through `WindowActivity`'s `onShowCustomView` (see "Android").
- Tested live on desktop and the Android emulator (isolated data): the whole picture at first, the wheel/buttons zooming to 7×+, a drag (synthetic pointer events on desktop, a real swipe on Android) that stops at the edges, the bars toggling by presses, the next media, full screen (and Back leaving it first on Android), a sound playing and seeking through ranges, ±10 s, a recorded video playing with its bars hiding/returning/staying when paused.

**Thumbnails** (*View thumbnails* in the File Manager's toolbar, `ThumbnailGrid.tsx`; the choice is `viewThumbnails` in Notes' settings). A grid of cards — the small image of a picture or of a video's first moments, an icon for everything else; a press opens (folder, viewer, editor), the card's three dots / right click / long press offer details, export, copy, cut, rename, delete (`menuFor`). A card makes its thumbnail when it comes into view (`thumbnails.ts`: the webview decodes the file — a picture, or a video seeked a moment in — and draws it to a 256 px JPEG; three at a time; a file that can't be decoded, or a Filen file over 32 MiB that isn't cached yet, keeps its icon).
- **On this device** thumbnails live for the session only (blob addresses, keyed by path, date and size); the files are right there.
- **In a Filen account** they are kept on disk with the cache, beside `a` and `b`: `files/t/NNN/…` (**t**humbnails of the account's files) and `files/tb/NNN/MMM/…` (of the files **b**ranch `MMM` changed), folder pairs like theirs (`layout::FILES_THUMBNAILS_FOLDER`, `FILES_BRANCH_THUMBNAILS_FOLDER`; `Cache::thumb_get/_put`, commands `filen_cache_thumb_get`/`_put`, the latter with the JPEG as the body via `invokeWithBytes`, ≤ 512 KiB). A thumbnail is laid out like its file and named `<name>.<modified ms>-<size>.jpg`, so **a changed file simply has none until one is made for its new version, which replaces the old**. In a branch a file the branch has *not* changed shows the account's thumbnail; one it changed keeps its own in `tb`. **Committing or discarding a branch deletes both places** — its `b/NNN/MMM` pair and its `tb/NNN/MMM` pair (`delete_branch_files_and_rows`); "Clear the cache" clears the account's `t` folder, and disconnecting the account removes `t`, `tb`, `a` and `b` for it. (Rust unit tests: versions, replacement, branch/account separation, both deletions.)
- Not done: thumbnails aren't refreshed by the file's *content* changing with the same date and size; a Filen thumbnail is made from the file as the cache has it.

## Links planted in `user/`

A directory junction or symlink planted inside `user/` (web apps can't create one — no command does — but the OS user, an unzip or a `git clone` can) is **refused in every direction**: the scope follows it to its real location, so listing, reading or creating files through a link that leads outside is an error (this used to be a gap with the fs plugin, which only resolved paths that already existed). The link itself can still be removed or renamed from inside, and its target is never touched. Tested with real symlinks (unit tests) and a Windows junction (live). On Android the `user` folder is in the app's private storage, so only `adb run-as` on a debug build (or root) can plant a link at all.

## Building and running (the admin-app is the frontend)

`csdrive-webhost-tauriapp` is a standard Tauri project: the frontend (the admin-app: React + Vite + TypeScript) at its root and the Rust backend in `src-tauri/`. `tauri.conf.json` points `frontendDist` at `../dist`, which Tauri embeds into the binary at compile time, so it is in every installer with no separate file and no network access — and there is no way for a user or a web app to swap it out, because it isn't a file in the data folder. (Its saved UI state is keyed by `layout::ADMIN_APP_ID`.)

- **Develop:** `cd csdrive-webhost-tauriapp && npm install && cargo tauri dev` — Vite on `:1420` with hot reload (`devUrl`), the app loading it, `devCsp` in force.
- **Installer:** `cargo tauri build` (runs `npm run build` first, via `beforeBuildCommand`, and turns on Tauri's `custom-protocol` feature so the embedded frontend is used). Android: `cargo tauri android build …` (see "Android").
- **Multi-page build:** `vite.config.ts` builds one html page per app — the admin-app (`index.html`) and each system app (`system/<id>/index.html`, see "System apps and Notes") — into `dist/`; Tauri embeds them all.
- **Run the embedded frontend without an installer:** `npm run build`, then in `src-tauri`: `cargo run --features tauri/custom-protocol`. A plain `cargo run` is Tauri's *dev mode*: it loads `devUrl` and needs Vite running — that is Tauri's normal behaviour.
- `cargo build`/`check`/`test` need `dist/index.html` to exist (Tauri embeds it at compile time); `build.rs` stops with the command to run if it doesn't.

## Web apps opened from Notes

Notes can open an **html or markdown file** as a web app — from the user folder, a folder the person picked, or a Filen account (in a branch too): the **Open as web app** button on such a file in its file list (`FileSource.openAsWebApp`, `open_file_as_web_app`; only Notes' pages may call it, and it needs a Notes tab to list the page under).
- **Serving** (`notes_pages.rs`; the `csuser://` protocol is now *asynchronous* and percent-decodes the path): besides the user folder, two address spaces — `/@device/<root id>/<path>` (a picked folder, judged by the file scope like any other path) and `/@filen/<user id>/<branch index or ->/<path in the drive>` (through the Filen cache: fetched if not cached or expired, then served from the cache; a file the branch changed is served as the branch has it). A page's **relative references** (a stylesheet, an image, a script, a link — `../` included) resolve against its own address, so they are answered from the same place; an address in the reserved `/@…` space that names nothing valid is refused. Markdown is rendered as described below whatever it is served from. Nothing in these addresses is a real path.
- **The window** (when it is a window of its own — see below for a tab of the Notes window) is an ordinary window entry (`kind` user) whose path is `@device/…` or `@filen/…` (`validate_relative_html_path` lets those through — they are judged when served) and whose `origin` records how it came to be opened (`Origin`: `openedBy` `NotesApp`, `storage`, the path in that storage, the picked folder's root id, the Filen account with the branch's name and index), told to the page in its init response. It has a `parent_tab`: the Notes tab that opened it.
- **Listed under the Notes tab that opened it**, not among the apps (`list_secondary_windows` leaves children out; "close all"/"suspend all" and the shutdown include them): in the admin-app the tab's level of *opened from this tab* lists them together with the external web sites (`TabRecord.openedApps` next to `externalPages`, oldest first, reorderable within the tab; an item shows an app-window icon, the page's own label — its first tab's — and its storage and path, with tags on the window's guid and focus / suspend / reopen / close of the window).
- **Siblings — any web page can open another page, in a window of its own.** `open_related_web_app(path)` (`openRelatedWebApp`; `TabLib.openPage(path)` in the samples): `path` is relative to the page's own — the page its window is showing now, which a link may have changed (`join_relative`: `.`, `..`, query and fragment handled, never above the root; a leading `/` is from the root of its storage), resolved in the same storage (folder, picked folder, drive and branch). A page that was opened from Notes gives the new page **the same parent tab** — it appears beside the page that asked, under the Notes tab; any other page of the user folder gives it a window of the apps list (`secondary_windows::open_page_window`, like one opened from the admin-app). Nothing asks the person: it is a page's own doing — unlike a *link*, which the person is asked about (`link_navigation`). (A note's page can also be a *tab of the Notes window itself* — see "A web page inside a system window"; the window's rights then follow the page it shows.)
- **External web sites** asked for by such a page (or by Notes itself) are listed **directly under that Notes tab** (`open_external_site` uses the caller window's `parent_tab` when it has one; the events still go to the asking page).
- **Lifecycle.** They are children: **suspending the Notes window suspends them** (and, through their own destruction, their external sites); **closing/deleting the Notes tab, its group or its window closes and deletes them** — recursively, with their tabs, tags and external sites (`delete_window_and_tags` → `notes_pages::Closing`).
- **Links.** A click on a link to the web in such a page opens the OS browser (see "No network access…"); a link to another page of the same folder, picked folder or drive is put to the person — open it in this tab, in a new tab, or copy its address (next section).
- Tested live on desktop: a markdown file of a picked folder (its `../theme.css`, an image and a script), a sibling, an external site from such a page listed under the Notes tab, a link click that left the window where it was, suspending and closing the Notes tab; and, on the real Filen account with a scratch folder, an `.md` file whose stylesheet came from the cache, a sibling `.html` using `../style.css`, and the same page opened from a branch (the branch's text, `branch: "selftest-pages"`).

## Markdown web apps

A `.md` / `.markdown` file can be opened as a web app exactly like an `.html` file (Files tab → "Open as web app", the User Apps tab) — `validate_relative_html_path` accepts it. Unlike an html file, whose bytes are served as they are, the `csuser://` handler (`serve_file` in `lib.rs`) turns a markdown file into html on the Rust side first (`markdown.rs`, `pulldown-cmark` with tables, footnotes, strikethrough and task lists) and sends the resulting **whole page**: a charset, a viewport, a small default stylesheet (light/dark), the document, and a script at the end.
- **Raw html passes through untouched** (markdown is html-compatible), so `<style>` and `<script>` tags in the file work — under the same policy as every web app (inline script and style allowed, no `eval`, no network).
- **Relative references** (a `<link rel=stylesheet href>`, `@import`, `<script src>`, an image, a link to another `.md`) are ordinary requests for a path relative to the page's address, answered by the same handler from the same folder — for html pages as much as markdown ones. (An address outside the app — a CDN — is refused by the CSP: an app needing network goes through a backend command.) Following a link to another `.md` shows that page in the same window.
- **The page is a tab** like a hand-written app: the last script registers it (`init_window_tab`), applies the code snippets, and labels it with the document's title (its first heading, else the file name) and path, and sets its resource id to the page's path plus query — so what the window manager shows follows the page. A tab switched to while it is showing starts the page over.
- Tested: title, table, an inline `<style>` and `<script>`, a relative stylesheet, a relative link, the tab label and the init response, on desktop.

## Deploying apps

`csdrive-webhost-userapps/<name>/index.html` (none exist yet — the registry is currently empty, and the Deploy dialog says so) is source for a small standalone app that the admin-app's Files tab can *deploy*: pick "Deploy apps…" from the toolbar (available in any folder browsable by the file manager, not just the root), choose an app from the list, confirm or edit the destination folder name (defaults to `<name>`, the folder it sits under in `csdrive-webhost-userapps/`; rejected if a file/folder of that name already exists at the current location), and the admin-app creates that folder under the current location and writes the app's `index.html` into it — using the same generic `mkdirRoot`/`writeRootTextFile` root-relative file operations as the rest of the Files tab, not a separate Rust-side "deploy" command.

Each deployable app's `index.html` is embedded into the Tauri binary at compile time (`csdrive-webhost-tauriapp/src-tauri/src/deployable_apps.rs`, via `include_str!`) and exposed to the frontend via two read-only commands, `list_deployable_apps` and `get_deployable_app_html`. Adding a new deployable app means: create `csdrive-webhost-userapps/<name>/index.html`, add an entry to `deployable_apps::REGISTRY` (plus an `include_str!` for its `index.html`), and `cargo build`.

## Tags

Tags (`window_tags` table) are not specific to windows: `guid` is any opaque id — a window, tab group, tab, or, in the Files tab, a file-manager root (keyed `root:<rootId>`, e.g. `root:user`; picked roots are remembered and keyed by their opaque id, so their tags persist with them; forgetting a root leaves its tags in the database, and they reappear if the same folder is picked again). **Everywhere tags appear they must be editable and sortable**, which is why every place renders them through the one shared `components/Tags.tsx` `TagList` component rather than its own markup: click a badge to edit its text/colors, drag badges (or use the arrows in the edit dialog) to reorder, × to remove. Backend commands: `list_tags`, `add_window_tag`, `update_window_tag`, `reorder_window_tags`, `remove_window_tag`; order is the `sort_order` column (new tags go last). Any new place that shows tags should use `TagList` too.

**A row of tags is shown only when the record has at least one tag** (`TagList` renders nothing for an empty list unless it is given `showWhenEmpty`), so a listing isn't padded with empty tag rows. The first tag is added from the record's **details popup** (below), which is the one place that passes `showWhenEmpty` — the "add tag" button — so every record that can have tags has a details popup, and a new listing with tags gets one too.

**Root tags** are the tags of a guid derived from a root (`src/lib/rootTags.ts`): `root:<rootId>` for a folder on this device (`root:user`, or `root:<id>` for a picked one — an opaque id, never a path), `root:filen:<userId>` for a Filen account. Every place that shows the root shows the same tags — the Files tab's root switcher and the **tab items in the System Apps tab**: a Notes tab (its resource id names its source, `rootOfTab`) shows two captioned lines, **Root** (the root's tags) and **Tab** (its own), so the two sets can't be mistaken for each other. Both are editable from there. A tab that shows no root keeps the single tag line. **Group by root** (System Apps tab only, at the tabs level; saved as `systemAppsTab.groupByRoot`): the tabs of the group are shown under a header per root (its name, and its tags when it has any; a button for its details) — a root's tabs are together, the tabs with no root last under "Tabs that show no root" — and the root is no longer repeated on each tab. Sorting by hand is off while grouped.

## Seeding demo data for the User Apps tab

`csdrive-webhost-tauriapp/src-tauri/examples/seed_demo_data.rs` populates the real `data.db` with demo data for the 9 sample apps in `user/qwer/` (`index1.html`-`index9.html`), for stress-testing the User Apps tab's nested windows/tab-groups/tabs UI at scale. To run it after a reset (or any time):

```
cd csdrive-webhost-tauriapp/src-tauri
cargo run --example seed_demo_data
```

It requires `data.db` to already exist and `user/qwer/index1.html`..`index9.html` to already be deployed (run the app once, and copy `sample-apps/qwer/` into the real `user/qwer/` folder, before running the script). It finds the real data folder itself the same way the app does, including a relocated custom data folder. Layout it creates: one `secondary_windows` entry per app, except `index1.html` which gets 10; the first of those 10 windows gets 10 `tab_groups`; the first of those groups gets 100 `tabs`. Safe to re-run — every row it creates is tagged `seeded:qwer-demo-data`, and each run starts by deleting only rows carrying that tag before recreating them, so it never touches any other window/tab/tag you created yourself.
