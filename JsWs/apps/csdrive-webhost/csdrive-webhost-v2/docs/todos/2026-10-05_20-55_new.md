Regarding the code editor (applies to markdown editors too, and also applies to both the default editor and the experimental editor we implemented in the previous todo file) - or any text editor that has a background worker for recomputing the code highlighting on keypress: continuously recalculating the entire highlighting of the file can be fine on desktop but on mobile I'm worried it might drain the battery really fast. So what I'm proposing is to add an optimization regarding when to recalculate the entire file highlight and when to simply insert the typed character in the current text piece: most of the time (especially if the user types plain text, that is mostly letters, like in markdown docs) recalculating the highlight on every keystroke is not actually needed, as the text piece where the caret is will remain the same after the typed characters are inserted. So we should detect such instances in advance. The simplest case is that which I just mentioned: when surrounded by letters (or at the start or end of a letters-only word) and the next typed character is also a letter, in the vast majority of situations the current text piece will keep its visual properties after inserting the typed characters. Exception to these rules are code blocks where the word where the caret is constitutes a programming language specific keyword (like "fun" in Rust, or "int" in C#), in which case inserting letters in the middle (or at the start or end) of such a word will change not only the current word highlighing but potentially the highlighting of surrounding pieces of text. But we can still know in advance if such is the case. Inside all the markdown/html text blocks that I can think of (and correct me if I'm wrong) inserting letters inside a word will not change the highlighting. Likewise, when inside a code block, typing anything inside a string literal except the string literal end token will not change the highlight. Or when inside a comment block, the highlight will not change unless the end of comment token is typed. Or when inside a code identifier (variable name, property name etc) typing letters (or even numbers or underscore in most languages) will again not change the highlighting. These are examples I could think of for not triggering the recalculating of entire file highlighting.
