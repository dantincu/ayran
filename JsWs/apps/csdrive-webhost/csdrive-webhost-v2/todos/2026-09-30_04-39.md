1. The keystrokes in the text editor still have the same lag. Just to make things easy: All the keystroke javascript event handlers from the text editor should start with a setTimeout instruction and the actual handling code should be put inside the callback to the setTimeout. The exception will be the keyboard shortcut handlers (that are global) which should execute synchronously only the code that establishes whether an actual shortcut has been hit or not. And then, if an actual shortcut has been hit, the next instruction should be one that prevents the default of the keystroke and the very next instruction should be yet another call to setTimeout whose callback will contain the handler for the keyboard that was hit (if one was hit of course). Lastly, show me the place in code where keystrokes events are handled. Also, a question: since we highlight code, I assume that we have an overlay that updates text as we type instead of seeing directly the typed text like we would if we edited an editable div (please confirm whether this is the case). In this case, in order to highlight to code correctly, I saw that our app first waits for a pause in the stream of strokes and only then reparses the code file and redraws the highlighted code. So while the user types fast, no characters are printed, they're only printed at the first break in the typing. Let's use a different approach: update the text instantly on every stroke by using the same text properties are being applied where the caret is while the user types. In the meanwhile, the reparsing of the code file should be done in a background worker on every stroke (but only one reparsing operation should take place at any moment, and after a reparsing has launched a new keystroke has fired before the reparsing finished, a new reparsing will take place when the current one finishes). And we update the text everytime a reparsing has finished.

3. There are 2 bugs related to the auto-hiding header:
   - when it's hidden, there is still some unnecessary space between the top margin of the view port and the editor header. That unnecessary space might correspond to the vertical padding (and margin, if any) applied to the auto-hiding header. And if you just varied the header's height or max-height css property to smooth its hiding, you should also vary its padding (and margin, if any).
   - There are cases when the auto-hiding header shows and hides rapidly, making the entire page "shake" continuously. This happens when I quickly scroll to the end of the editor. Why I think it happens: first, I assume that you listen to the scroll event, and when the scroll is positive you hide the header, when its negative you show it. Then, hiding/showing the header changes the height of the scrolling container, which then might change the position of the scroll, so itself might trigger another, scroll in the opposite position, which triggers showing the header back, that now triggers yet another scroll in the other position, the header gets hidden again and so on. My suggestion: while the header hiding/showing animation happens, set up a bitflag somewhere so as to do nothing on the scroll event. So any scroll event triggered while the header hides or shows will not itself cause the header to hide or show as it's already doing that.
