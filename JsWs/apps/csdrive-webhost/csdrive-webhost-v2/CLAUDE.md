# Ayran CsDrive WebHost

The Tauri app in `csdrive-webhost-tauriapp` has exactly one frontend, the **admin-app** — a React/Vite project living at the root of that same folder (`src/`, `index.html`, `package.json`, `vite.config.ts`, with the Rust backend in `src-tauri/`). It is the Tauri app's own compiled-in frontend (`frontendDist` in `src-tauri/tauri.conf.json`, embedded into the binary and so into every installer), it always occupies the main window, and nothing — neither the user nor a web app — can replace it. It manages a machine-wide *data folder* (below) holding an `admin` folder for the app's own database and secrets, a `user` folder meant purely for arbitrary user-authored content, and a `files` folder for the Notes app's cache. The user can write their own `.html` files anywhere under `user` (e.g. `user/index.html`, `user/myapp/index.html`), but those are only ever opened as *secondary* windows (via the admin-app's own Files tab or User Apps tab — "Open as web app"/"add a new window entry"). Besides those *user apps* the app ships **system apps** — more pages of the same compiled-in frontend, **Notes** being the first — which are opened the same way and managed in the System Apps tab (see "System apps and Notes" below).

## Folder layout

**Where all of this lives is defined in exactly one place: `csdrive-webhost-tauriapp/src-tauri/src/layout.rs`** — `DEFAULT_DATA_FOLDER` (the default data folder; `%APPDATA%\com.ayran.csdrive-webhost-tauriapp` today), the `admin`/`user`/`files` folder names (and inside `files`: `a`, `b`, `c`, the thumbnails `t` and `tb`, and `data.db`, see "The Filen cache" and "Media"), `FILEN_SESSIONS_FILE`, and `ADMIN_APP_ID` (the admin-app's key for its saved UI state). Nothing else hardcodes them: the backend, the keychain entry names (the last component of `DEFAULT_DATA_FOLDER`), the `seed_demo_data` example (`#[path]`-includes that file) and the admin-app (which names the user folder as the root `user`, never by path) all derive from it. To run the app **completely isolated** from real data (e.g. for tests), set `DEFAULT_DATA_FOLDER` to a scratch absolute path (`r"C:\Temp\csdrive-isolated-test"`) and rebuild: the run gets its own data folder, database and keychain entries, and can't reach the real one. (The WebView2 browser-storage profile is still shared, as it is keyed by the app identifier; the app keeps no state there.) Remember to set it back. **The person uses the custom data folder (Settings → "Change data folder") for the app they really use on this machine, and its pointer file (`data-location.enc`) sits in the *default* data folder — the very place a test run reads — so a run that is not isolated opens the production data, reads and writes.** Never run tests, the demo seeder or "Change data folder" / "Delete app data" against it: isolate the run first (above), and if the isolation isn't in force, stop and say so rather than carry on (see `README.md`).

The folders sit directly under the data folder (the default above, or wherever Settings' "Change data folder" points):
- `admin/` — the app's own files, none of which is ever served to a window: `data.db` (this app's SQLite database — secondary windows/tab groups/tabs/tags, the generic `app_state` table, the `global_settings` table, remembered device folders, connected Filen accounts; see `secondary_windows::init_db`) and `filen-sessions.enc` (below). The admin-app itself is **not** in the data folder: it's the Tauri app's compiled-in frontend, so there is no `admin/dist` and nothing on disk to tamper with.
- `user/` — arbitrary user-authored `.html`/`.js`/`.css`/etc., served to secondary windows via the `csuser://` custom protocol. The backend never reads anything from here except in response to the admin-app explicitly asking to open/list something in it.

- `files/` — the Notes app's cache of Filen accounts and their branches, and the branches and thumbnails of the folders of this device (see "The Filen cache", "Branches of a folder of this device" and "Media"). **Everything directly inside `files/` is one of: `a` and `data.db`** — nothing else lives at the top level. `a` holds one `NNN` folder pair per account or per folder of this device that has branches or thumbnails; **inside an account's or a root's own `NNN`**: `c` (its cached content — accounts only), `tmp` (an account's uploads in flight), `b` (its branches), `t` (its thumbnails) and `tb` (its branches' thumbnails) — each keeping the owner's own folder hierarchy. **`tmp`** (`a/NNN/tmp`) is where a Filen upload is assembled while it goes up — the pieces are written there as they are sent and the file *becomes the cached copy* when it finishes; anything left by an interrupted upload is deleted at the next start. `files/local-uploads` is the same idea for a file arriving from the device's file chooser into a *local* folder (`fs_upload.rs`): its pieces are appended there and the finished file is moved into the destination, so the person's own folders never hold a half-written file; it is emptied at every start. A Filen account is `NNN-filen@@<email>@@<id>` / `NNN`, a folder of this device `NNN-local-fs@@<root guid>` / `NNN`, both numbered together in `a`; a branch is `MMM-<name>` / `MMM` inside the owner's own `b` (and `tb`, for its thumbnails). Like `admin/`, it is a **protected path** (`data_location::protected_paths`): no file command or SQLite call can reach it, even inside a picked folder — only the `filen_cache_*` commands read and write it.

The three folders are created unconditionally at startup (`lib.rs`'s `.setup()`), regardless of which files inside them do or don't already exist. Whenever a folder needs a short name a program can rely on and a long one a person can read, the app uses **folder pairs** (`folder_pairs.rs`, strategy in `docs/strategies/folder-pairs-strategy.md`; `docs/strategies/` is where the app's strategies are written down, one `.md` each).

**The admin-app** is a React app (TypeScript, built by Vite into `dist/`, embedded by Tauri — see "Building and running"). It is a file manager for the `user` folder and any folders the user picks, a file manager for connected filen.io accounts (any number of them), a SQLite management studio for `.db` files in those places, the manager of the apps' windows/tabs/tags (the System Apps tab, first and the default, and the User Apps tab — the same component, `AppsTab kind="system" | "user"`), a browser-storage inspector, and the settings.

`csdrive-webhost-userapps/` holds source for small standalone apps that can be *deployed* — copied as a new folder of `.html`/etc. content into the `user` root — via the admin-app's own Files tab (see "Deploying apps" below), as opposed to the admin-app, which is the one privileged app: always built into the installer and always the main window.

## App state storage: data.db, not browser storage

An app's own UI-state persistence (active tab, last-browsed folder, collapsed groups, ...) belongs in the app-owned `data.db` (see the generic `app_state` table in `secondary_windows`'s crate — `get_app_state`/`set_app_state`), *not* IndexedDB or Web Storage. Reason: the data folder can be relocated (see the Settings tab / `data_location`) precisely so testing can switch between profiles, but browser storage lives in the fixed WebView2 profile rather than wherever the data folder currently points — so it never actually switched with the rest of the app's data. Rows are namespaced by an `app_id` — the relative path of the html file the window was opened from (from `user/`, for a secondary-window app; `system:<id>`, e.g. `system:notes`, for a system app; `layout::ADMIN_APP_ID` for the admin-app itself) — which the **backend** works out from the calling window itself (`get_app_state`/`set_app_state` take no app id; any one a caller sends is ignored), so an app can only ever reach its own state — so the same app keeps separate state when copied to more than one location on disk, and multiple apps sharing this one database never collide. This applies to every app in `csdrive-webhost-userapps/`, present and future; the admin-app's own `src/lib/appState.ts` is the reference implementation. It does not apply to browser storage a user explicitly creates through a generic inspection tool (e.g. admin-app's Storage tab) — those are arbitrary by design and named by the user, not the app, and have nothing to do with an app's own settings. If an app used browser storage for this before switching to `data.db`, it's fine to just abandon the old IndexedDB database/keys rather than migrate their contents, unless they hold data too valuable to lose.

**A paginated list's position is saved as the number of records skipped, never as a page number** (`src/lib/pagedPosition.ts`: `offsetOfPage`, `pageOfOffset`, `validOffset`). The page size is one setting for the whole app (below), so it can change between saving a position and restoring it, and "page 3" only means the same records for the same size; "50 records skipped" means the same records under any size — restored with a size of 10 the page shown is the 6th, which holds the record that was first on screen. Files, Filen.io and Notes save it with their place (`offset` in `filesTab.location` / `filenTab.location`, `o=` in a Notes tab's resource id and its last place), and **nothing is saved over a position until the listing it belongs to has loaded** (a `restoringPage` flag), or the page still saying 0 would overwrite it; a folder that can't be listed drops its position. A new paginated list that keeps its position does the same.

**Global settings** are the exception to "an app only reaches its own state": the `global_settings` table (`get_global_setting`/`set_global_setting`, granted to every window) holds the few preferences that are deliberately shared by every app — today the list **page size** (`listPageSize`, `src/lib/listPageSize.ts`), so paging 10 rows a page in the Files tab does so in Notes too. Keep it to genuinely global preferences.

**The admin-app writes nothing to browser storage.** Verified against a pristine WebView2 profile after using every tab: `localStorage`, `sessionStorage`, IndexedDB, cookies, the Cache API, service workers and OPFS are all empty, and the profile holds no data for the admin origin beyond the engine's own bookkeeping (navigation history, site-interaction and preference records, which any webview keeps for any page). The only code that touches these APIs is the Storage tab, on the user's explicit action. Keep it that way: new admin-app state goes through `appState.ts` (`data.db`).

**Each tab page of the admin-app keeps its own place**, independently of the others: going to another tab page and coming back — or restarting the app — finds the page where it was left. A page saves its navigation under keys of its own (`filesTab.location`, `filenTab.location`, `sqliteTab.navigation`, `storageTab.panel` and `storageTab.indexedDb`, and — one per kind — `systemAppsTab.navigation` / `windowsTab.navigation`), written on every change; `src/lib/tabState.ts` (`usePersistedState`) is the helper for a plain value. **What was saved is never trusted blindly**: a saved shape is checked before use, and whether it still leads anywhere is judged once the page has what it needs — the Apps tabs fall back to the deepest level that still exists (and wait until both the saved place and the list of windows have loaded, or they would reset a perfectly good place against an empty list), the Files and Filen tabs go to the top of the root/account when the saved folder can't be listed, the SQLite tab to its list of databases when the saved database is gone, the Storage tab's IndexedDB panel to its database list. A new tab page with navigation gets the same: its own key, a shape check, a check against reality.

## What the backend exposes to web apps (capabilities)

User-provided web apps run in secondary windows (label = the window guid); the admin-app is the window labelled `main`. Tauri capabilities are per window label, so `src-tauri/capabilities/` has three files, and **every new command must be listed in `build.rs` and granted in exactly one of them**:

- `user-apps.json` (`windows: ["*"]`, so it covers the admin window too) — everything a web app is meant to be able to do: files under the user folder and folders the user picks with a native folder picker, through **our own file commands** (`fs_read_dir`, `fs_stat`, `fs_exists`, `fs_read_file`, `fs_write_file`, `fs_mkdir`, `fs_remove`, `fs_rename`), which obey our own scope (see "The file scope" below) — the fs plugin isn't used at all. **No window ever sees a real path** (see "No real paths for web apps" below): every file command names a *root* — `user`, or the opaque id of a picked folder, from `list_picked_roots` — and a path *relative* to it; `pick_folder` asks the person to choose a folder and answers with its id and name. SQLite on `.db` files in those same places (below); Filen.io file operations on the accounts the user has connected (below); managing app windows, tab groups, tabs and their tags (and reloading the page an open window shows: `reload_secondary_window`, `reload_tab`); binding itself to its tab (`init_window_tab`) and adding another (`add_window_tab`, see "Who creates tabs" below); asking to open an external web site (`open_external_site`, see "External web sites" below) and managing the ones listed (`reopen_/focus_/suspend_/close_external_site`); `get_appearance`, `set_appearance` and `list_themes` (the theme and light/dark mode: **any window may choose them**, see "Appearance"), `get_window_state`/`set_window_state` (state of *this window* only, gone with its entry: the branch a Notes window works in), `root_guid`, the `local_branch_*` and `local_thumb_*` commands (branches of the folders of this device), `filen_cache_hard_refresh`/`filen_cache_clear_item`, the `user_action_*` commands (below), `open_related_web_app`, with which **any web page opens another page in a window of its own** (see "Web apps opened from Notes"), and `open_file_as_web_app` (a page — Notes or any web app that has registered a tab — opens a file as a web app, listed under its own tab); **the app's own clipboard** (`internal_clipboard_get`/`_set`, see "Details, clipboards and paths"); its own `get_app_state`/`set_app_state`; the shared `get_global_setting`/`set_global_setting`; `list_system_apps`; the Filen *cache* commands (`filen_cache_*`, below) and `fs_read_dir_detailed` (a folder's entries with size, modified and created time in one call, for searching and sorting). System apps are pages of the admin-app's own frontend but are **not** the admin-app: they run in ordinary secondary windows and have **exactly the same rights as a user web app** — decided on purpose, there is no tier between them: what Notes may do, any web app may (open a file or a note as a web app or a tab — `open_file_as_web_app`, `open_note_tab`, `note_tab_state`, `note_tab_action` —, tell the windows that show a file that it was saved — `notify_file_saved` —, ask the address of a picture or a video — `media_url` —, and **export a file to the device**, see "Exporting" below). What tells them apart is only their own state (`system:<id>`) and where their page is served from. Deliberately **not** granted: system/OS/app/window introspection (`core:default` — app version, monitors, paths…), event emitting, connecting/disconnecting Filen accounts.
- `admin.json` (`windows: ["main"]`) — extras only the admin-app gets: `set_appearance_rotation` (the rotation through the themes: a page that recolours the whole app every half minute isn't a page's business — the generic `set_global_setting` refuses all the `appearance.` keys), `filen_login`/`filen_logout` (the only place a Filen password is ever typed), data-folder relocation and "Delete app data", the bundled-app deploy commands, and `show_top_bar` (tells a page to show its own top bar — see "The top bar" — one open window or every one at once; the person triggers this from the admin-app, never a page on its own behalf). On Android every call reaches Tauri through the one webview (see "Windows on Android" below), so the capability files can't tell the admin-app from a window there: the bridge applies the same list itself (`window_host::window_commands`, read from `user-apps.json`) and those commands also call `window_host::require_admin` on the *real* caller, which is what actually enforces it there — and on desktop too. (Path joining is our own `joinPath` in `src/lib/localFs.ts`; Tauri's `path.join` permission isn't granted to anything.)
- `prompt-dialog.json` (`windows: ["prompt-*"]`, Windows only) — the window that shows **a page's own JavaScript dialog** (see "Prompts and windows"): `prompt_dialog_info` (the one question it shows) and `prompt_dialog_answer`. No other window is granted them.
- **Exporting a file to the device** (`choose_save_location`/`save_to_device`, and the two that copy a file already on disk on the Rust side, `export_local_file` and `filen_cache_export` — granted in `user-apps.json` like the rest) is **every window's, user web apps included, because the person is asked every time** (`device_files.rs`; it used to be the admin-app's and the system apps' alone, and `require_trusted` is gone). Desktop: a native "save as" dialog gives the one-time token, and nothing is written without one. Android has no such dialog, so the window that asks first gets a native confirmation on itself (`device_files::confirm_export`): who asks — the window's page as the app knows it, never anything the page wrote — and the file's name, *Save* / *Cancel*; declining answers `Cancelled.`, which the frontend takes for "nothing was saved" (`platform.ts`). The admin-app's own buttons are not asked on Android: they are the interface itself, not a page. Verified live on desktop: a user web app gets past the caller check and stops at the save-location check, where it used to be refused as "Only the admin-app and the system apps can do that."

**SQLite** is our own (`sqlite_db.rs`), not `tauri-plugin-sql` (which opens any path on disk): `sqlite_load(root, path)` takes a root and a path relative to it, resolves symlinks/`..`, and refuses anything outside the file scope; the returned handle is the virtual name `<root>/<path>` (never a real path), only works in the window that loaded it and is closed when the window closes. SQL can itself name files, so every connection also runs under an authorizer: `ATTACH` is allowed only for in-memory/temp databases (a file can't be named from SQL now that windows don't know real paths), `PRAGMA temp_store_directory`/`data_store_directory` and `load_extension` are denied, and `VACUUM INTO` (which SQLite doesn't route through the authorizer) is refused by a token scan of the statement. (Without these, `ATTACH DATABASE '…/admin/data.db'` read straight past the path check.) `sqlite_execute(db, query, values)` → `{rowsAffected, lastInsertId}`; `sqlite_select(db, query, values)` → array of `{column: value}` (BLOBs as byte arrays).

**Filen.io lives entirely in Rust** (`src/filen/`: `crypto.rs`, `api.rs`, `ops.rs`, `mod.rs`; ported from the Ayran Notes app's Rust client). No credential ever reaches a webview: the connected-accounts list (user id + email) is a table in `data.db`, and every account's session (API key, master keys, name-hash key; the RSA private key is used once at login and never kept) is in one encrypted file in the data folder, `layout::FILEN_SESSIONS_FILE` (`admin/filen-sessions.enc`), so it travels with `data.db` when the folder is relocated and is gone when the folder is wiped. Web apps identify an account by its numeric `userId` and call, with Filen paths (`/`, `/Folder/file.txt`): `filen_list_accounts` → `[{userId, email}]`, `filen_readdir` → `[{name, isDirectory, size, mtimeMs}]`, `filen_stat`, `filen_read_file` (returns an `ArrayBuffer`), `filen_write_file` (creates or replaces; the bytes are the raw request body, the account and path go in headers: `invoke('filen_write_file', bytes, { headers: { userId: String(id), path: encodeURIComponent(path) } })`), `filen_mkdir` (recursive), `filen_rm` (to trash), `filen_rename` (also moves). `src/lib/filen.ts` is the reference wrapper. Crypto is tested against vectors from Filen's own JS SDK (`@filen/sdk`); accounts on auth version 3 salt name hashes with an HMAC key derived from the RSA private key (fetched at login). 

The backend exposes no system information (CPU, memory, OS, paths…) to any window.

## Secrets at rest (`secure_store.rs`)

One random 32-byte key, generated the first time it's needed and kept in the platform key store (desktop: the OS keychain via the `keyring` crate — Credential Manager / Keychain / Secret Service, entry `app-encryption-key` under the service name from `layout::keychain_service()`; Android: the Android Keystore, see "Android"), encrypts everything sensitive that we persist. The sensitive data itself lives in ordinary AES-256-GCM files (`nonce(12) || ciphertext+tag`, written atomically) inside the data folder: the Filen sessions file (above) and the small pointer file (`data-location.enc`, in the *default* data folder) that records a relocated data folder. The key store therefore only ever holds 32 bytes (no entry-size limits), and the only platform-specific code is `platform::resolve_key`. **iOS is not implemented yet** — `resolve_key` returns an error there (rather than keeping the key unprotected); implement it with the iOS Keychain and nothing else in the module changes. (`keyring` is a desktop-only dependency in `Cargo.toml` for that reason.) New secrets should be added the same way: a JSON structure written with `secure_store::write_json`.

## The file scope (`fs_scope.rs`, `fs_commands.rs`)

Which files the file commands and SQLite may touch is decided in one place, our own `FsScope` — replacing the fs plugin's, whose runtime scope can only grow (paths can be allowed or forbidden, never taken back), so "forget this folder" couldn't revoke anything until a restart. Ours: the **user folder** is always allowed and can't be revoked; **picked folders** are allowed until revoked, at once, and can be picked again in the same session; the app's own **`admin/` folder** (database, Filen sessions), the Notes cache in **`files/`** and the data-location pointer file are **never** reachable, even inside a picked folder (so picking a folder that contains them exposes nothing). Every path is resolved before it is judged: it is a root plus a relative path (below) which becomes an absolute one, `..` is refused, symlinks/junctions are followed to the real location (also for a file that doesn't exist yet, by resolving its nearest existing folder — which closes the plugin's old gap where a link planted in `user/` let a web app *create* files outside), a dangling link is refused, and the command then operates on the resolved path. Removing or renaming an entry acts on the entry itself (a link pointing outside is removed, never its target). Picking is done in Rust (`pick_folder`: the OS folder dialog on desktop, `FolderPicker.kt` on Android), which adds the folder to the scope and remembers it in `data.db` (`picked_roots`); `allow_saved` allows the remembered ones again at every start, and `remove_picked_root` revokes one. The frontend's `src/lib/fs.ts` wraps the commands with the shapes the plugin had (each takes the root id first). The dialog plugin remains only for the admin-app's own message boxes (`confirm`) and Rust-side dialogs (folder picking, "save as", the data-folder chooser — the ones a window can ask for run under the prompt rules, see "Prompts and windows"); a web app can't get a path out of a dialog and use it, because only `pick_folder` adds to the scope. Tested with real symlinks/junctions, `..`, protected paths and revocation (Rust unit tests), and live on desktop and the Android emulator.

## No real paths for web apps

**A window — a user web app, a system app — never learns where anything is on the device.** The one thing that could hand it a real path is the file access it legitimately has, so that is where it is closed:

- **Roots and relative paths.** Files are addressed as a *root* plus a path relative to it (`fs_scope::FsScope::check_in`): the root `user` is the user folder; every picked folder gets an **opaque random id** (12 hex characters, made in `picked_roots.rs`, remembered in `data.db`'s `picked_roots.id` so it survives restarts and stays the same when the folder is picked again). Every `fs_*` command, `sqlite_load` and the upload/copy commands that name a local file take `(root, path)`; `pick_folder`/`list_picked_roots` answer `{id, label}` (the folder's own name), `remove_picked_root` takes the id. Only the scope maps an id to the real folder. `..`, backslashes and (on Windows) drive letters in a relative path are refused, and a root itself can't be removed or renamed from inside.
- **Nothing it says contains a real path.** The scope's refusals name the relative path (`resolve_shown`/`check_shown`), the SQLite database handle is the virtual name `<root>/<path>` (it used to be the real file path), `ATTACH` of a file is refused (SQL can't name a root), `save_to_device`/exports answer only the saved file's *name*, `get_user_folder` no longer exists, and the tab resource ids and tags that used to embed `ext:<path>` now embed the id (`picked_roots::migrate_path_based_ids` moved the old ones on first start). Tested: every refusal is checked for the real path in Rust, and live (a user web app's view of `list_secondary_windows`, `list_picked_roots`, every refusal and the SQLite handles was scanned).
- **Drag and drop.** Tauri hands a page the *real paths* of files dropped on its window; secondary windows are built with `disable_drag_drop_handler()` (the main window always was), so a dropped file arrives as a plain HTML5 `File` — a name and its bytes, no path. The device's file chooser (`<input type=file>`) is the same.
- **Where paths still exist.** Only the admin-app may ask where a root really is (`fs_root_path`, `require_admin` — the Files tab's tooltips), and Settings shows the data folder (`get_data_folder_info`, also admin-only). The backend of course holds real paths; it just never says them to a window.

If a new command takes or returns a location on the device, it takes `(root, path)` and answers with names, never a path — and its refusals must not quote one.

## Keyboard

Shared code is in `src/lib/keyboard.ts` (and `components/Pagination.tsx`, `components/TabSwitcher.tsx`). Shortcuts use Ctrl (⌘ on a Mac) and are shown in tooltips. **The list of every shortcut, for the people who use them, is `docs/keyboard-shortcuts.md` — a new shortcut is added there in the same change.**

- **Two-key shortcuts (chords)** (`lib/chords.ts`, `components/ChordHost.tsx`, mounted once per page beside the clipboard menu): **Ctrl+K, then a letter** (within 3 s; a hint at the bottom — **glowing**, above every dialog, and lighting the entry of the shortcut that was just pressed — lists the letters that apply *here*; Esc or a wrong letter cancels). The owner of an action registers it while it is on screen (`useChord(letter, label, run, enabled?)`): **T** — the admin-app's tab switcher (a popover listing the tabs with a number in front of each, and a box that has the focus and takes digits — Enter goes to that tab, a number that isn't one turns the box red, a press on a row goes there, Escape closes it; it used to be Ctrl+K on its own, which a chord prefix can't also be); **M** — maximize/restore the popup on top (`lib/modalStack.ts`; `Modal` and `EditorPanel` register: the window less a margin `clamp(6px, 2.1vw, 40px)`, and each has a button); **C**/**V** — copy to / paste from the app's clipboard in the text box that has the focus (`TextFieldMenu`); **X** — clear the app's clipboard. Ctrl+G (the page list) stays a single-key shortcut. A new shortcut is a chord.
- **Lists** (`useListKeyboard` + `kbdItem`): **Up/Down** move the focus by one item, **Home/End** go to the first/last, **PageUp/PageDown** move it by 10 (**in a paginated list these three stay inside the page the focus is on** — `useListKeyboard` takes `pageSize` and `page`: Home/End are the page's first/last item, PageUp/PageDown stop at the page's start/end and, pressed there, go on to the next page's first / previous page's last item; the first arrow with nothing focused focuses the shown page's first item), **Left** goes to the parent and **Right** into the focused item (a folder, a file to edit, an app → its windows → its tab groups → its tabs → a tab's external web sites; on an external web site, Right brings its window to the front or opens it again), **Enter** for the focused item's own action (on a tab: show it, opening its window if need be; elsewhere the same as Right; not heard while a button or link has the focus, which Enter presses). The keys are heard on the whole window, so nothing has to be focused first; a text box or menu keeps its own keys and so does an open dialog or the editor (`overlayOpen`); pressing on an item moves the focus there. The focused item is drawn with `[data-kbd-focused]`. In a paginated list the focus is an index into *all* the items and the page shown follows it; going Left puts the focus on the folder just left, Right on the first item of the one opened — but only for a move made with the keys (after a click nothing is focused until a key is pressed). Covered: the four levels of the System/User Apps tabs, the Files and Filen tabs, Notes' file list and its notebooks list (Right shows the notebook's folder, Left goes to the home page), the SQLite tab's databases and tables, the Storage tab's IndexedDB databases → object stores → records. Not covered: the Local/Session storage key-value tables, Settings, tag editing.
- **Paginated lists — all pages.** The page indicator (`3 / 12`) is a button: pressed with a finger or the mouse it opens a **popover listing every page number** (the current one highlighted) and a press on one goes to that page. **Ctrl+G** opens the same popover *with* a numeric box (focused; Enter goes to that page, an invalid number turns it red) — the box is only there when it was opened with the shortcut, not by pressing the button. Escape or a press outside closes it. Every paginated list uses the one `Pagination` component, so every one has it (Files, Filen, Notes). **The popover is as tall as the screen allows and its list of pages scrolls** (the popover is `position: fixed`, placed by `Pagination` against the screen — above the button when it fits there, else slid down — with `max-height` the screen's height less an 8px margin and the system bars' insets; the list inside takes what is left and has `overflow-y: auto`, so it fits a phone however many pages there are) **and has a keyboard cursor** (`.cursor`, an outline apart from the current page's highlight): Left/Right ±1, Home/End first/last, Up/Down the same column of the previous/next *row*, PageUp/PageDown half the list's height in rows, Enter goes to the cursor's page (a typed number wins, and typing moves the cursor). Rows are not assumed: `cursorFor` reads them from where the buttons really are (the ones sharing the first button's `offsetTop`), so it holds for any width or font; with a single row Up/Down/PageUp/PageDown do nothing.

**A web app's window never changes its own address** (desktop; `FROZEN_ADDRESS_INIT_SCRIPT` in `code_snippets.rs` and `navigation_verdict` in `lib.rs`, both from `lock_down_navigation`'s `own` argument — the page the window was built for). The init script makes `history.pushState`/`replaceState` **ask** for an address instead of changing it (one of this app's origin becomes a navigation the backend sees — `location.assign` —; another origin throws a `SecurityError`; not writable, not configurable) and removes `window.navigation`; `on_navigation` lets through only the page's own path and query (so a reload, and a changed *fragment*, an in-page `#link`, are fine), sends links to the web (http/https) to the OS browser, refuses `javascript:`, `data:` and `file:`, refuses every other page of a *system app's* window and the admin-app, and treats another page of a *web app's* kind as a **request** (`Nav::Request`: the window stays, and the person is asked — "Links between pages of web apps", next). So a page can't turn itself into a "single page" that wanders off its address, nor be taken to another page of ours by a link or `location.href` without the person choosing it. This is a guard against pages, not a boundary against hostile code — the CSP and the capabilities are. Consequences: an app **reports** which resource a tab shows (the query string in the address it gives `init_window_tab`/`add_window_tab` — `TabLib.urlFor(params)` builds it without navigating), the resource id is **owned by the backend** (a reload gets the stored one back in the init response), and "start the page over" is `location.reload()`, never `location.href = …`. Notes and the markdown bootstrap follow this. **Android** applies the same rule to every window's WebView (see "Windows on Android"); the main webview shows only the admin-app.

## Details, clipboards and paths

**Details popup** (`components/DetailsModal.tsx`). Every listing of records has an *Info* button per record that opens one: the record's fields (`DetailField`: label, value, `mono`, `copy`, `hidden`), **each copyable value with two buttons — copy to the OS clipboard and copy to the app's own clipboard** —, a field marked `hidden` shown as dots behind an eye button (a Filen item id: it can be viewed, unhidden and copied), and the record's tags with the "add tag" button (see "Tags"). Where it is: the System/User Apps tabs (an app, a window, a tab group, a tab, an external web site or opened app, a root header — beside the existing `#` resource-id button), the Files tab (an entry, the folder shown — toolbar —, and each root's pill, whose tags are edited there), the Filen tab and Notes (an entry, the folder shown), Notes' notebooks page. The listings that are only lists of links (SQLite's databases and tables, Storage's databases and stores) don't have one.

**Paths in a file manager.** A file or folder's details show its **path** (relative to its root, `/a/b/file.txt`, never a real one — the Files tab, admin-app only, adds "Location on this device" as it does in tooltips), copyable to both clipboards. A **Filen** entry also has its **item id** (Filen's uuid: `filen::ops::Entry.id`; the cache keeps it as `entries.remote_id`, filled by the next listing for a cache made before — a branch-made file has none until committed), hidden until asked for. Every file manager (Files, Filen, Notes) has **Go to a path…** (`components/GoToPathModal.tsx`, `lib/pathInput.ts`): a popup with a text box — the two paste buttons put what is on the OS or the app's clipboard in it — that takes `/a/b` or `a\b` (either slash; `..` refused), checks that it names something in the current root/account/branch and goes there; a file opens its folder with the file focused; otherwise the box says why and stays open.

**The app's own clipboard** (`internal_clipboard.rs`, `lib/clipboard.ts`): one text (16 MiB at most) kept by the backend and shared by every window of the app — the admin-app, the system apps and web apps — not persisted, nothing copied to it reaches the OS clipboard. **Every window may read and write it, a user web app included** (decided on purpose: what one window copies another can paste; `TabLib.internalClipboard` in the samples) — so what is copied to it is readable by any web app that is open. The admin-app's **Settings** tab shows what it holds (a character count; the text on request) and has **Clear the app's clipboard** — as does the chord Ctrl+K, X — and web apps can clear it too (`internal_clipboard_clear`, `TabLib.internalClipboard.clear()`). `lib/clipboard.ts` also has the OS clipboard (`copyToOsClipboard`: `execCommand` first, then the Clipboard API; `readOsClipboard`: the Clipboard API, with a readable error when the webview won't say). **Android's WebView refuses to read the OS clipboard** — the menu and the paste buttons then say so and point to the system's own paste — while writing to it works. Verified on the emulator, by real taps: the text menu, select paragraphs, the app's clipboard between the admin window and a Notes window (through the window bridge), details, go to a path.

**Text editors and single-line boxes** (`components/TextFieldMenu.tsx`, mounted once in the admin-app and in Notes): while a `textarea` or a text-like `input` (text, search, url, tel) has the focus, a small "…" button sits at its corner and opens a menu — **Select paragraphs** (a single-line box: **Select all**), **Copy to / Paste from the app's clipboard**, **Copy to / Paste from the clipboard** (the OS's). Pasting replaces the selection. A **paragraph** (`lib/paragraphs.ts`) is a run of text between blank lines; selecting takes the paragraph(s) the selection touches — or the caret is in — without the whitespace around them (a caret in a gap takes the paragraph before it). The box keeps its focus and selection throughout (the button and items don't take the focus). A box that closes when something else is pressed opts out with `data-no-text-menu` (the page-list popover). A new text editor needs nothing: the menu finds it.

**Popups can be maximized** (`components/Modal.tsx`, `components/EditorPanel.tsx` — the editors' popup —, `lib/modalStack.ts`): a button in the header and the chord Ctrl+K, M make the popup on top take the window less a margin (`clamp(6px, 2.1vw, 40px)`: thin on a phone, 40px at Full HD), so it still reads as a popup.

**The file editor** (`components/CodeEditor.tsx`, used by the Files tab and by Notes — a new editor of a file uses it too). It is a `textarea` — so the clipboard menu, selection, drafts and the on-screen keyboard are unchanged — with a **syntax-highlighted copy of its text drawn behind it**: Markdown, HTML, **CSS and JavaScript** by the file's name (`lib/highlight.ts`: `languageOf`, `highlight`; `lib/highlightCode.ts` has the CSS and JavaScript scanners, also used for a `<style>`/`<script>` in HTML and for ```css / ```js fences in Markdown; any other file is plain; a text over `HIGHLIGHT_LIMIT` characters is left plain). The box has a transparent text and the same font, padding and wrapping as the copy; it is as tall as its text and the frame around both scrolls, so nothing is kept in step but the height. `highlight` keeps one rule — **the text content of its result is exactly its input** (escaped, only wrapped in `<span class="tok-…">`), checked on 4 000 random texts — because the two layers must line up character for character (no italics, whose synthesized slant misaligned one glyph run on Android; checked visually with the box's text made visible over the copy, wrapped lines included). The colours are the `--tok-*` variables of `App.css` (light and dark); `data-text-menu-anchor` on the frame puts the clipboard menu's button at the frame's corner rather than the (tall) box's.

**Open link** (`lib/textLinks.ts`, in the clipboard menu of a `CodeEditor` that is given `onOpenLink`): when the caret — or the selection — is inside an address, the menu offers **Open link**. An address is a web address (`http`/`https`, bare or in `<…>`), the target of a Markdown link, image or reference, or the value of an `href`/`src` attribute; a **web** address is asked about first and then opened — in Notes as an external web site of its window (the same box and rules as a web app's, `open_external_site`), in the admin-app's Files tab in the OS browser after a native box (`open_web_address`, admin only: it has no tab to list a site under) —, a **path** is resolved against the file being edited (relative to its folder, or absolute from the root of its folder or account, `resolveLinkedPath`) and opens what it names: a page (html, markdown) as a web app in Notes, another file in the editor, a folder in the listing. Changes held in the editor must be saved first (the linked file takes their place), a missing target is said next to the menu. A note's address (a query with the key `note`) opens that note, as a link in a page does (below).

**Slim windows.** Under 600 px wide (a phone, a narrowed window) a record's row of action buttons falls **below its text and tags** (`App.css`, the last block: `display: contents` on the row's header lets the buttons take `order` last; file tables become a block per entry). New listings use the existing classes (`window-item`, `row-actions`, `file-table`) and get it.

**A `<td className="row-actions">` is a real table cell above 600px, not a `flex` box.** The narrow-window rule above needs `.row-actions` to be `display: flex` (a flex item of its now-flex `<tr>`, and a flex container for its own buttons at once) — but applying that at *every* width, directly on the `<td>`, silently breaks the ordinary case: a `flex`/`inline-flex` box doesn't get a table cell's automatic "stretch to fill the row" behavior, and `height: 100%` doesn't reliably resolve against a table row's height either (it's content-derived, not "explicitly specified" for percentage purposes) — so the cell sat at its own natural size, top-aligned, leaving a gap below the icons whenever the row was taller than the icons alone needed (found live, and only confirmed by measuring both cells' `getBoundingClientRect()` directly — a screenshot alone read as "only the first row is broken" when every row actually was, just less visibly for a shorter one). `@media (min-width: 601px)` — the exact inverse of the narrow breakpoint — puts `.file-table td.row-actions` back to `display: table-cell` with `vertical-align: middle`, laying the buttons out with plain inline flow (`text-align: right`, a margin between them standing in for `gap`, which only a flex/grid container provides) rather than `flex`; they still wrap, the same as text wrapping, when they don't fit on one line. Verified live (both widths): at normal width every row's two cells now measure the same height and top position; under 600px `row-actions` still measures `display: flex` exactly as before.

**Compact row actions** (`components/RowActions.tsx`, `lib/rowActionsCompact.ts`; Settings → Lists). Every list's per-record row of icon buttons — Files, Filen.io, the four levels of the System/User Apps tabs, Storage, and every list of Notes (the file manager, notes, notebooks, search results) — is built with `RowActions` in place of its own sequence of `IconButton`s: `<RowActions actions={[{ icon, label, onClick, disabled?, danger? }, …]} />`, rendered with **no wrapper of its own** so it drops straight into whatever the list already had (a `<td className="row-actions">`, a `<div className="row-actions">`), keeping every existing layout — the slim-window CSS above included — unchanged. One setting for the whole app (`rowActionsCompact` in `global_settings`, read/written through the ordinary `get_/set_global_setting` — no new backend command was needed) decides, **everywhere at once**, whether a row's buttons show inline as they always have (off, the default) or collapse behind a single **⋯** button that opens them as a menu (`ContextMenu`, the same component a right click/long press opens elsewhere) — never a per-row or per-list choice, and the **⋯** button itself always sits inline. `RowActions` subscribes to the setting itself (`subscribeRowActionsCompact`), so every mounted row updates the moment it's changed in Settings, in the same window; other windows pick it up next time they load (as `listPageSize` already works). Left deliberately outside `RowActions`, at a fixed position beside it, because each is its own self-contained trigger rather than a plain action: `CacheMenu` (its own dropdown; CLAUDE.md's "Cache options of one item") and NotePage's own three-dots "More…" button (a different, larger menu of its own, for things that were never icon buttons — Select, F2/Shift+F2 renaming, tab management). `IconButton` forwards its ref (`forwardRef`) for callers that need it, though `RowActions` itself computes the menu's opening position from the click event's own target — never a ref read during render. Verified live (isolated data folder): the Settings toggle, off by default with every list's buttons inline exactly as before; switched on, the Files tab's rows, the System Apps tab's app and window levels, and Notes' notebook list all collapsed to one **⋯** per row, each opening the right actions for its state (checked in particular against a suspended window, which offers *Reopen* rather than the open state's *Focus*/*Reload*/*Suspend*) — including the row that keeps `CacheMenu` at a fixed position beside `RowActions`. **Not separately exercised live**: Filen.io, Storage, the tab-groups/tabs/external-sites levels of the Apps tabs, and Notes' other lists (the file manager, search results) — they go through the identical component and pattern as what was checked, so they are expected to behave the same, but weren't clicked through one by one.

`ContextMenu` itself — used here and everywhere else a right click/long press opens one — **has a transparent backdrop under the menu** (`.context-menu-backdrop`, `position: fixed; inset: 0`, `z-index` just below the menu's): a press outside the menu used to both close it *and* reach whatever was behind it at those coordinates (found live: closing a row's overflow menu this way could press the row underneath it, e.g. opening another row's own menu). The backdrop is a real element that catches that press first — `onPointerDown` closes the menu — so the press never reaches the background at all; Escape and scroll/resize still close it the same way as before (a window-level listener, kept for that). Verified live (real data): opening a compact row's overflow menu, then pressing exactly where another row's own **⋯** button sits underneath the menu's open area — the menu closed and no second menu opened (`elementFromPoint` at that spot resolved to the backdrop, not the button).

**`Pagination`'s own "go to page" popover has the identical backdrop fix** (`.page-popover-backdrop`, `Pagination.tsx`) — it is a separate component from `ContextMenu` with its own popover markup, so the `ContextMenu` backdrop fix above didn't cover it: it used to close only via a plain `window`-level `mousedown` listener that checked whether the click landed outside the popover's own element, which — exactly like `ContextMenu`'s old behavior — let the same press also land on and activate whatever was underneath (a file/folder row, say). Replaced the same way: a `.page-popover-backdrop` (`position: fixed; inset: 0`, `z-index` just under the popover's) with `onPointerDown` closing it, in place of the old `mousedown` listener. Verified live on the Android emulator: `elementFromPoint` at a folder row's position that sits underneath the open popover resolved to the backdrop, not the row, and a press there closed the popover without navigating into that folder (the breadcrumb stayed put).

**Huge folders.** The Files tab asks for sizes only for the entries of the page on screen (as Notes always did for a local source), never for the whole folder — a folder of 100 000 files used to take over four minutes to show (a call per entry) and now takes about 0.2 s. What a listing costs — the entries all travel, in one JSON message, and sit in memory in Rust, in the webview and, for Filen, in the cache — is measured and analysed in `docs/huge-listings.md` (limits, what a failure looks like, and the paged-listing design that would remove them).

## External web sites

A user web app or a system app can ask to open an **external web site** — a page of the web, http or https — in a window of this app. It is **not a tab** (an external page has no `init_window_tab`/`update_tab_resource` to call, and can't be told anything): it is listed as a **child of the tab whose page asked for it**, one level below the tabs in the window manager (`external_sites.rs`, the `external_pages` table in `data.db`: guid, `tab_guid`, `window_guid`, `initial_url`, `url`, `title`, `created_at`; its tags are ordinary `window_tags` on its guid).

**Asking.** `open_external_site(url)` (granted to every window; `openExternalSite` in `src/lib/secondaryWindows.ts`, `TabLib.openExternalSite` in the samples) needs a caller that is a web app or system app with a registered tab. The address is checked first (`external_sites::check_url`): absolute, **http or https only**, with a host, **no user name or password in it**, at most 2048 characters, and **not one of this app's own origins** (`window_host::is_own_origin`: the frontend, `csuser`, or any `*.localhost` name — those have access to the backend). Then an **OS native confirmation box** shows *who* asks and the address, with **Open** and **Cancel**. **One such request waits for the person at a time** (a second `open_external_site` meanwhile is refused at once), and its box takes its turn in the app's prompt queue — see "Prompts and windows" — with the *Prevent this app from showing prompts* button. The command answers immediately with a request id; what the person chose arrives as an event, **to the window that asked and to no other** (listen with `getCurrentWebviewWindow().listen`, as for `tab-navigate`, and before asking):
- `external-site-response` `{ requestId, url, confirmed, pageGuid, error }` — the answer (`pageGuid` names the site in the events below; `error` says why it wasn't opened when the person said yes);
- `external-site-changed` `{ pageGuid, url, initialUrl, title }` — the site's address or title changed (the title as the page sets it, when it has one; the address also when a single-page site changes it without loading);
- `external-site-closed` `{ pageGuid }` — its window was closed (its entry stays in the window manager).

**The site has no way into the backend.** On desktop it is an OS window labelled with the page's guid, showing the address as an external URL: no capability names a remote page, so every command is refused for it (verified live: a site calling `get_app_state` gets "not allowed on window…"), and it has no Tauri globals. Its window may only navigate to what `may_navigate_to` accepts — what `check_url` accepts, or `about:blank` — checked on **every** navigation, so a link, a redirect or a script can't take it to `tauri://`, `csuser://`, `*.localhost`, `file:` or `javascript:`, where a page *would* have access; and it can't open windows of its own (new-window requests are denied). On **Android** it is shown full screen in a plain `WebView` in an activity of its own (`ExternalSiteActivity.kt`, started through `ExternalSites.kt`; an activity rather than a dialog, because a dialog never got the keyboard focus and Back went to the app instead of the site), **not** the app's webview, so it has no JavaScript interface or Tauri bridge either, with the same navigation rule; **Each site is a task of its own in the Recents screen**, like a window (`csdrive-site://<id>`, `intoExisting`; *focus* starts it again to bring it forward). Rust starts it over JNI and **polls** `drain()` for its address/title/closed events every 300 ms while any site is open, as it does for the folder picker. Back goes back in the site's history, then closes it (the entry stays, suspended). The confirmation box is shown **by the window that asks** (`android_windows::ask`). A release build of the Android app blocks **cleartext http** (the manifest's `usesCleartextTraffic`), so there only https sites load; a debug build allows both. iOS: not implemented (the command answers with an error).

**Listed as children of the tab.** The address and the title are learnt from outside — desktop: page-load, navigation and document-title events, plus a look at the window's address every 1.5 s for single-page sites (no event is raised when those change it); the address at the start is kept as `initial_url`. In the admin-app's Apps tabs (`AppsTab`, both kinds) each **tab item** has a globe button (with a count) that opens the **external web sites level**; the level is one more in the navigation (apps → windows → tab groups → tabs → external web sites), saved like the others (`…navigation.tab`). An item shows the **globe icon**, the **title on the top row** (or "No title" until the page has one) and the **address on the bottom row**, with tags (`TagList`, as everywhere), a status dot (open/suspended), **Copy the address** and **Copy the address it was first opened at** (the two differ once the site redirects or the person navigates), bring-to-front, **Suspend**, **Reopen** and **Close**. **They can be reordered within their tab** (Sort, saved per tab as `…externalOrder`, as the other levels' orders are) and **nowhere else** — there is no cut/paste or "move to" for them, so a site can never sit under a tab other than the one that opened it (and `move_tab_to_group` takes the tab's sites along: their `window_guid`, who hears about them, follows the tab).

**Lifecycle — suspend and close, as for windows** (see "Suspending vs closing"). **Suspending** a site (`suspend_external_site`) closes only its window: the entry stays, as *suspended*, and **Reopen** (`reopen_external_site`, no confirmation — the person is asking in the admin-app itself) brings the window back at the address it was at. **Closing** it (`close_external_site`) closes the window *and* removes the entry with its tags. The same follows the tab it was opened from: **suspending the window a tab belongs to suspends all the sites opened from its tabs** (`handle_window_destroyed`, so every route to a suspend does it — the buttons, "suspend all", closing the tab being shown, Android leaving the app), while **closing** a tab, deleting its tab group or closing/removing its window entry **closes** its sites (`close_tab`, `delete_tab_group`, `delete_window_and_tags`; the DB work is `external_sites::delete_for_tabs/_for_window`, the windows are closed by the caller). Entries survive a restart, as suspended. (An app can have sites open for one tab at a time only in practice — a window shows one tab.)

## Links between pages of web apps (`link_navigation.rs`)

A web app's window never moves itself, so a click on an **anchor** to another page of its own storage (a path, with or without a query), a `GET` form, `target=_blank` / `window.open` and `history.pushState('…')`/`replaceState('…')` (turned into `location.assign` by the guard script) all reach the window's navigation rule as a **request** (`Nav::Request`, `OwnPage.on_request` on desktop, `nativeNavigation` on Android). The window stays where it is and the person is asked, in native boxes that belong to the window (`window_host::choose`: the dialog plugin on desktop — with **no parent**, a box with the window as its parent never showed —, `android_windows::ask` on Android). A native box has **at most three buttons** and one closed with its X/Esc answers as its last button, so every box ends in **Cancel**: *Open… / Copy… / Cancel*, then *In this tab / In a new tab / Cancel* or *To the clipboard / To the app's clipboard / Cancel*. The first box says what the link is: **Type** (Web page (HTML), Markdown document, Note, File or folder), **Path** (in its storage — `/docs/a.md`, the address that is copied and that a "Go to a path" box takes; a query is shown with it) and **In** (the user folder, "the folder X", the Filen account and branch). A link that can't be opened in a window (a picture, a folder) goes straight to *To the clipboard / To the app's clipboard / Cancel*. **A note's address is opened like a page**: `Open…` → *In this tab / In a new tab* — its markdown file is looked for when the person chooses (`link_navigation::note_page`: the file in the note's short folder whose name ends with `[note].md`, in the user folder, a picked folder or a Filen account/branch) and the tab shows that page; a note with no markdown says so.

**Addresses.** The browser already resolved a relative link against the page's own address, so it is relative to the file that was opened as a web app. An **absolute** path is relative to the root of the page's **storage** — a picked folder's root or the Filen account's (branch's) root — not the user folder the browser took it for: `link_navigation::resolve` puts it back under the page's `@device/<root>` / `@filen/<user>/<branch>` prefix (in the user folder an absolute path is just a path). A link can't lead out of the storage its page is in (another folder, account or branch, or from the user folder into one): refused with a box saying so. A query with the key **`note`** makes the address a note's — not a folder's or a file's (`classify`; opening notes comes with the notes themselves). Copying uses `tauri-plugin-clipboard-manager` for the OS clipboard (Rust only: no capability grants its commands to a page; retried a few times, as another program can hold the clipboard for a moment) and the app's own clipboard (`internal_clipboard`).

**In this tab / in a new tab** (`secondary_windows::open_link_in_window`). A web app's window has tab groups and tabs, and until now every tab of it was the same page (the app itself decided what a tab showed). A tab can now show **another page** (which does not stop it being a tab of its window's *app*: `tabs.relative_path` is not changed, so it can still be moved to another window of the same app with `move_tab_to_group` and goes on showing its page there): `tabs.link_page` (the page's path as a URL has it, and its query) is set when the person opens a link in it — the tab keeps `relative_path`, its window's app, which is what lets it be moved to another window of the same app (`move_tab_to_group`; it goes on showing its page there), its `resource_id` is that of the new page and its label is cleared until the page registers itself — or a new tab of the same tab group is made with it (it becomes the window's current tab); then the window is **taken there** (`window_host::navigate`: the window's navigation rule is told first — desktop keeps the page each window is at in `OwnPage.url`, Android in its window state — and the webview navigates). `page_to_show` says which page a window shows for a tab (`link_page`, else the page the window was made for): it decides what `reopen_secondary_window` and `activate_tab` open, and `activate_tab` on an **open** window whose tab shows another page takes the window there (a tab with no `link_page` still gets the `tab-navigate` event, as before). `link_page` follows the resource id the page reports with `update_tab_resource`, and `init_window_tab`'s answer names the file of the tab (`relativePath`: its path in the storage) rather than the window's (`fill_origin`). A page that never registers a tab (a plain html file) still works: its window's pending tab is the one that is used. The window's app (its entry's `relative_path`, the key of its app state) stays that of the page it was made for. This holds for **every kind of window, a system app's too**: Notes shows a note's page in a tab of its own window (see "The note pages"); a tab may also carry `tabs.syncs` (the served path of a file it follows — only such tabs are reloaded by `notify_file_saved`).

Tested live on desktop (isolated data folder; the boxes pressed with `TDM_CLICK_BUTTON`): a `#fragment` and `pushState('#h')` ask nothing, `pushState` to another origin throws, a relative / absolute / query link and a `pushState` path each show the box with the right type, path and place, *In this tab* and *In a new tab* (one tab / two tabs of one group; activating each takes the window to its page), the two clipboards' box (the app's clipboard checked), a picture and `target=_blank`, Cancel, a markdown link, and suspending and reopening (the window comes back at the tab's page). Not verified live: the OS clipboard's content — this machine's session had no access to the OS clipboard at all (`Set-Clipboard` fails there too), only that a refusal is reported in a box.

## No network access for any window (CSP)

The policy is written once, in `src-tauri/tauri.conf.json` (`app.security.csp`; `devCsp` is the same plus the Vite dev server's websocket). Tauri applies it to the admin-app's own pages (adding hashes for the inline scripts in `index.html`), and `respond` in `lib.rs` sends the very same string, read back from the config, as a header with every `csuser://` page — so user web apps and the admin-app alike are under it. A script can reach only its own origin's files, `data:`/`blob:` URLs, and the IPC channel to this backend (`ipc:` / `http://ipc.localhost`, depending on the OS): `fetch`, XHR, WebSocket, EventSource, beacons, external scripts/styles/images/fonts/frames and form posts to anything else are all blocked, and `default-src` is `'none'` so anything not listed is too. The one place a page of ours is shown *inside* another is Notes' User Action popup (see "User Action"): `frame-src` names `csuser:` and `http://csuser.localhost` besides `'self'`, and the CSP test lets those two through for `img-src`, `media-src` and `frame-src` only. Inline scripts/styles remain allowed (`style-src-attr` is spelled out because Tauri's script/style hashes make `'unsafe-inline'` inert for `style-src`, which would otherwise break inline `style=""` attributes); `eval` is not. **A click on a link to the web opens the OS default browser**, not this app: `lock_down_navigation` hands every http/https address a window would navigate to (an anchor, `location.href`) or open in a new window (`target=_blank`, `window.open`) to `external_sites::open_in_browser` (desktop: `rundll32 url.dll,FileProtocolHandler` / `open` / `xdg-open`; Android: an `ACTION_VIEW` intent, `ExternalSites.openInBrowser`) and the window stays where it is; only what `check_url` accepts is opened. Opening a site *inside* this app happens only programmatically, with `open_external_site` (below). CSP doesn't cover navigating the window itself, so `lock_down_navigation` (`on_navigation` + denying `window.open`) confines every window to our own origins — web app windows to `csuser` only, the main window also to the admin-app's (`tauri://localhost`; `http://tauri.localhost` on Windows and Android; the dev server under `tauri dev`) — applied to the main window and every secondary window, so any new window builder must use it. A web app that needs anything from outside talks to it through a backend command (as Filen does), never directly. To add an exception, edit `tauri.conf.json` and the test that reads it (which asserts the policy names no external host).

## Android (and every other platform)

**Standing rule: everything in this app — what exists and everything added from now on — must work on Android as well as on desktop.** Check each new feature on the emulator, and keep desktop-only code behind `#[cfg(desktop)]` with a real Android counterpart (or an honest "not available on this platform" that the UI hides).

**Building.** The crate is a lib (`src/lib.rs`, `pub fn run()`, `#[cfg_attr(mobile, tauri::mobile_entry_point)]`) plus a two-line `src/main.rs`. The Android Studio project is `src-tauri/gen/android` — generated by `cargo tauri android init` but **committed and hand-edited**: `MainActivity.kt` (edge-to-edge + the safe-area bridge), `SecureKey.kt` and `DeviceFiles.kt` (Kotlin helpers Rust calls over JNI), `WindowActivity.kt` + `WindowBridge.kt` (the windows of web apps and system apps — see "Windows on Android"), `ExternalSites.kt` + `ExternalSiteActivity.kt` (external web sites) and `FolderPicker.kt`. From `csdrive-webhost-tauriapp`: `cargo tauri android build --debug --target x86_64 --apk` (it runs `npm run build` itself; needs `ANDROID_HOME`, `NDK_HOME`, and **JDK 17** as `JAVA_HOME` — Android Studio's bundled JDK 25 breaks Gradle). Testing without a device: an emulator (`quick_notes_pixel_34`, headless), `adb install -r` (keeps app data), and Chrome DevTools remote debugging (`adb forward tcp:9222 localabstract:webview_devtools_remote_<pid>`, then the CDP HTTP/WebSocket API) to run `window.__TAURI__.core.invoke(...)` in the pages. In Git Bash set `MSYS_NO_PATHCONV=1` for adb. The emulator's app data is its own — nothing touches the desktop data.

**Windows on Android** — every window is an activity of its own (`android_windows.rs`, `WindowActivity.kt`, `WindowBridge.kt`; the reasoning is in `docs/strategies/android-windows-strategy.md`). Tauri creates exactly one webview on Android (the one in `MainActivity`, which shows the admin-app and nothing else), so each secondary window is a plain `android.webkit.WebView` in a `WindowActivity`, with a bridge of our own to the backend. Each is **its own task in the Recents screen** (`documentLaunchMode="intoExisting"`, the task keyed by the intent's data `csdrive-window://<guid>`; opening a window that is showing brings it to the front), so the person switches between windows with the system's task switcher, and opening app B never disturbs app A. A window entry is **open** while its activity exists; **Back** — or swiping it away in Recents — **suspends** it (entry, tabs and tags kept, its task removed; an accidental swipe must not delete a tab group), the admin-app's *Suspend*/*Close* finish the activity from Rust (*Close* also deletes the entry), and the cascade rules of "Suspending vs closing" apply as on desktop (suspending a window suspends the external sites and the web apps opened from its tabs).

**Back undoes one navigation before it ever suspends** (`secondary_windows::go_back`, `WindowActivity.back()`, `WindowBridge.nativeGoBack`): a tab switch that shows another tab in the *same* window — `activate_tab`, and a link followed "in this tab" (`open_link_in_window`) — remembers what the window showed a moment ago (`SecondaryWindowsState::previous_shown`, one entry per window, in memory; a link "in this tab" also remembers the tab's previous `resource_id`/`link_page` so undoing it restores the exact page, not just the tab). Pressing Back calls `nativeGoBack` — a plain, synchronous JNI call Kotlin makes directly, the same trust model as `nativeServe`/`nativeAttach`, not a page-originated `invoke` — which pops that one entry (if any) and switches the window back to it, leaving the window **open**; a *second* Back press, with nothing left to undo, falls through to the ordinary suspend. This is Notes' and every web app's Back behavior alike (a note opened as a web app in a syncing tab, or a link followed within a tab), so no top bar or per-tab suspend/close buttons are needed for the common "go back one step" case (see Follow-up 3, item 5 — items 3/4's top-bar design stay postponed). `previous_shown` is cleared once used, so Back only ever undoes the *last* step, not a whole history. Verified live on the Android emulator (isolated app data): opening a note as a web app switched the window to the note's page in place (same activity, same task); the first Back returned it to the notes list with the window still `isOpen: true` and the note's tab kept (`showing: false`, not removed); the second Back suspended it as before (`isOpen: false`, task removed, entry kept). If the process is killed, entries are suspended at the next start; a task the system brings back whose window the (restarted) backend doesn't know starts the app and finishes itself. All the commands (`open_new_/reopen_/suspend_/close_/close_all_/suspend_all_secondary_window(s)`, `focus_`, `activate_tab`) keep their signatures on both platforms.

- **How a page reaches the backend.** `window.CsdriveBridge` is a JavaScript interface `WindowActivity` attaches to *its* WebView for *its* guid — it only says the window's label — and `window.CsdriveInvoke` is a **message port that only the window's main frame can use** (`WebViewCompat.addWebMessageListener`, offered to the window's own origins and told whether a message came from the main frame: a JavaScript interface is injected into *every* frame and can't tell which one calls, so a page shown in a frame — Notes' User Action popup — could have called as the window; a WebView that can't do this gets no bridge at all); `scripts/window-bridge.js` builds `window.__TAURI_INTERNALS__` on it (invoke, callbacks, metadata) and the crate's build copies Tauri's own `window.__TAURI__` bundle (`build.rs` → `window_scripts.rs`), so `__TAURI__.core.invoke`, `getCurrentWebviewWindow().listen` and `@tauri-apps/api` work as on desktop. `invoke` goes `CsdriveInvoke.postMessage` → `WindowBridge.nativeInvoke` (JNI) → `android_windows::dispatch` → Tauri's own dispatcher (`Webview::on_message` of `main`), so every command runs exactly as if its page had called it; the answer returns as `runCallback` (or, for raw bytes — an `ArrayBuffer` — the page fetches them once from `http://ipc.localhost/raw/<key>`, so a big file isn't base64ed). Request bodies are JSON only (bytes as base64 in a JSON object, `invokeWithBytes`'s Android form). `plugin:event|*` is kept in the page (listeners live there; Rust delivers with `window_host::emit_if_open` → `__csdriveEmit`, to that window only), `plugin:dialog|*` is refused (a window asks with `confirm_dialog`); **every other `plugin:` command is refused**.
- **Who is calling.** Commands that need to know take `window_host::CallerWindow` instead of `WebviewWindow` (it derefs to it): on desktop it says what the window's label says; on Android it says what the *activity* said — `dispatch` puts `x-csdrive-caller: <secret>:<guid>` on the request (the secret is made at startup, so no script, the admin-app's included, can forge it; a claim that doesn't check out is an error, never the admin-app). `caller_guid`/`caller_key` give web apps and system apps their identity (app state, SQLite handles, upload sessions), `require_admin` gates admin-only commands. A page's *address* is never consulted on Android. A window may call only the commands the capability files grant to windows (`window_host::window_commands`; a unit test keeps it disjoint from `admin.json` and inside `build.rs`' list).
- **Serving.** The WebView loads `http://csuser.localhost/…` (web apps) or `http://tauri.localhost/system/<id>/index.html` (system apps) — the addresses wry uses — and `shouldInterceptRequest` answers **every** request from Rust (`nativeServe`): the user folder, `@device`, `@filen` and markdown as ever (`lib.rs`' `serve_user_path`), a system app's files from Tauri's asset resolver (only under `system/` and `assets/`, checked against the embedded keys — the resolver would answer an unknown address with the admin-app's `index.html`), always with the CSP header. **A request to any other host is refused.** A system app's window may also load files of the user origin — its pictures and media, which its CSP allows as `img-src`/`media-src` (Notes' viewer and thumbnails) and `frame-src` (its User Action popup) only. `nativeServe` is given the request's `Range` and `Origin` headers, so a media file is answered a piece at a time (`file_serving.rs`, below) and never held whole by the JVM either. `/@csdrive/window.js` (the bridge, Tauri's global, the frozen-address guard) is answered before anything else and put first in every html document's `<head>` (`window_scripts::with_script_in_head`).
- **Frozen address.** `shouldOverrideUrlLoading` asks `navigation_verdict` (the desktop rule): the window's own page (a reload, a fragment) goes ahead, a link to the web goes to the OS browser, a request for another page of the app is put to the person (`link_navigation`; the box is `android_windows::ask`, on the window's activity) and the rest is blocked; the guard script turns `pushState`/`replaceState` into such a request and removes `navigation`.
- **Dialogs and the file chooser.** A page's `alert`/`confirm`/`prompt` are native dialogs on the window's activity, under the prompt rules (titled "A web page says", one at a time, with the option to prevent prompts); a window's own questions are `confirm_dialog`'s, shown the same way; `<input type="file">` opens the system chooser (`onShowFileChooser`). Rust asks the person things in a window with `android_windows::ask` (the external-site confirmation) — a dialog of the app's main activity would be invisible over a window.
- **Insets.** A window pads its root by the system bars, the cutout and the keyboard (no `--csdrive-safe-area-*` variables there, so the code snippet's padding is 0).
- Tested on the emulator: a user web app and Notes as their own tasks, the bridge (identity, refusals of admin-only and `plugin:` commands, raw bytes, events, state), Back / Suspend / Reopen / Close, a second open bringing the task to the front, an external site as its own task with the confirmation on the asking window, the suspend cascade, and the frozen address.

**Custom protocols.** On Windows and Android the scheme `x://localhost/...` is served as `http://x.localhost/...`. `WebviewUrl::CustomProtocol` converts it when a window is built, but `navigate()` does not — always go through `window_host::navigation_url` (Android showed `chrome-error://chromewebdata` without it). Custom-protocol pages count as local, so capabilities can't scope by URL (hence `require_admin`). On Android the windows' WebViews are served by our own `shouldInterceptRequest` (above), which uses the same addresses. The admin-app is served by Tauri itself, not by us: `http://tauri.localhost` on Android (`tauri://localhost` elsewhere), recognised by `window_host::is_admin_url`.

**System bars and the safe area** (the admin-app's webview; a window's activity pads itself, see above). Tauri apps fill the whole screen on Android, under the status bar and the gesture/navigation bar. Android's WebView reports `env(safe-area-inset-bottom)` as 0, so `MainActivity.kt` measures the real insets (system bars + display cutout, in CSS px) and publishes them as CSS variables `--csdrive-safe-area-inset-top/right/bottom/left` on `<html>` (an initialization script on every page reads them from the `CsdriveSafeArea` JS interface and `__csdriveApplySafeArea` keeps them current). They are 0 when the bars are hidden, so a full-screen mode simply gets the whole screen. A window's **page** can go full screen (`element.requestFullscreen()` — the media viewer does): `WindowActivity`'s `WebChromeClient.onShowCustomView` puts the element over the whole window and hides the system bars (they come back with a swipe; Android shows its own one-time "Viewing full screen" notice the first time, which takes the first Back), and **Back leaves full screen first** — only then does it suspend the window. There is still no full-screen mode for the admin-app itself. The css that consumes them (`SAFE_AREA_CSS` in `code_snippets.rs`: pad `<html>` by the four variables, `height:100%`) reaches every page not because each web app copies it but as a **code snippet**: `init_window_tab`'s response has a `codeSnippets` list of `{ code, type }` entries (`type`: `css`, `html` or `javascript`; today one css entry), and `get_code_snippets` returns the same list. **Web apps must apply the snippets they receive** (`sample-apps/qwer/_tab-lib.js` does — `TabLib.applySnippets`, also called automatically for `openTab`'s response and on load; the admin-app does it before its first render, `src/lib/codeSnippets.ts`). Anything platform-specific that every page needs should be added to that list rather than asked of each web app. Layout inside the admin-app therefore uses `height:100%`, not `100vh`.

**Loading indicator.** Nothing web-side can be shown until a page exists, so startup has two spinners. (1) From the first paint: `index.html` contains a spinner inside `#root` (styles `.app-splash` in `App.css`, same markup as `components/Splash.tsx`, which `App` shows while the saved tab loads). (2) Android only, for everything before that: `MainActivity.showSplash` puts a native spinner (`SplashSpinnerView`, app background/accent colours, light and dark) over the whole window from `onCreate`, on the decor view because wry later installs the WebView with `setContentView`, which would discard anything added to the content area; the window theme's `windowBackground`/splash background (`csdrive_bg`, `res/values{,-night}`) avoids a white flash before it. The admin-app removes it (`hideNativeSplash` in `src/lib/nativeSplash.ts`, via the `CsdriveSplash` JS interface) when its first screen is ready; it also removes itself after 10 s so a page that fails to load is never hidden behind it (`adb logcat -s CsdriveSplash` shows when it appeared and how long it stayed). The spinner draws itself from the clock rather than using Material's indicator or any `Animator`, because Android's "remove animations" / animator-scale-0 setting turns those into a static icon or nothing at all. On desktop the blank stretch is native startup (release build, warm profile: ~0.45 s for WebView2 before any page can exist, then ~0.13 s to first paint; a debug build adds ~0.4 s of unoptimised runtime start), which page content can't cover. The database setup is ~30 ms and not a factor.

**Secrets.** `secure_store` on Android keeps the 32-byte key wrapped by an Android Keystore key (`SecureKey.kt`; the wrapped blob is in the private `csdrive_secure_store` preferences); Rust reaches it through `android_jni.rs` (`on_activity`, `helper_class` — the activity's class loader is required to find our own classes). Verified: same key across restarts.

**Admin-app differences** (`src/lib/platform.ts`: `isMobile` from the user agent). **The data folder can be relocated on Android too** (`pick_and_set_custom_data_folder`, `data_location.rs`): it reuses the same folder-choosing mechanism as "Add root folder" (`picked_roots::choose_folder` — `FolderPicker.kt` on Android, which hands back a real absolute path unlike the system's own picker; see "Picked folders" below) wrapped in `prompt_guard::os_dialog`, like every other native prompt. `DataFolderInfo.canRelocate` is false only on iOS (no folder-picking dialog there yet). What Android still can't do is **restart itself** after picking a folder or wiping data (`DataFolderInfo.canRestart`, false on mobile: "Delete app data" ends the process instead — `app.restart()` can't relaunch there — and the next launch starts fresh; picking a new folder likewise needs the person to reopen the app by hand). **Caution for testing this on Android:** the debug and release builds share one `applicationId` (no `applicationIdSuffix` in `build.gradle.kts`), so they share the same private storage and thus the same default data folder and the same pointer file (`data-location.enc`) — the desktop production-data-folder danger (see `README.md`) applies on Android too once a custom folder is ever set there: isolate before testing relocation, as on desktop.

**The main window is built *first* in `lib.rs`'s `.setup()`, before anything that reads the data-location pointer file** — this used to be the other way around (the window was built at the very end, after `admin`/`user`/`files` were created and the database opened), which broke relocation on Android specifically: decrypting the pointer file goes through `secure_store`'s Android path (`resolve_key` → `android_jni::on_activity`), which needs the *main window* to already exist (`app.get_webview_window(...)`) — and with the window not yet built, that lookup failed outright with "The main window isn't available," every single time. `read_custom_dir` treats any failure as "no custom folder configured," so a real, correctly-saved custom folder was silently ignored at actual startup and every folder was created under the *default* location instead — while `get_data_folder_info`, called later once the app was fully up (and the window definitely existed by then), read the same pointer file successfully and reported the custom path, contradicting where things had actually been created. The bug reproduced 100% of the time and live-confirmed with a debug build: even a generous wait (`android_jni::on_activity`'s `WINDOW_WAIT_TIMEOUT`, kept as a defensive fallback) inside the *old* call site never helped, because the window-build line simply hadn't executed yet in the same synchronous closure — no amount of waiting *before* a later line in that closure makes it run sooner. Moving the window build to the top of `.setup()` is safe: `lock_down_navigation`'s callbacks only touch app-managed state when a real navigation happens, never synchronously during `.build()`, and the admin page's own JS doesn't start calling commands until well after `.setup()` has returned control to Tauri's event loop — verified live on desktop (isolated data folder: the app starts, every tab loads, no panic) and on the Android emulator (relocating to a real external folder and relaunching now creates `admin/data.db`, `files/data.db` and an empty fresh `user/` in the *custom* folder, confirmed both on disk via `adb shell` and through `get_data_folder_info`/`fs_read_dir` agreeing with it — previously the custom folder stayed completely empty forever while the UI insisted it was "currently in use"). Uploads use the webview's own `<input type="file">` chooser (`pickFilesFromDevice`) because the native dialog returns content URIs the fs scope can't cover. Exports go through `save_to_device` (`device_files.rs` + `DeviceFiles.kt`): every window may (asked first on Android, see "Exporting" above), the bytes are the request body and the name a header, stored in the public Downloads folder via MediaStore (no permission needed on Android 10+; a name collision gets ` (1)`); on desktop `exportToDevice` first asks the backend for a location (`choose_save_location` shows the native "save as" dialog and returns a one-time token) and only then reads the data and sends it with the token (`save_to_device` writes it there — so a big Filen file isn't fetched before the person has chosen where it goes). Byte payloads to the backend go through `invokeWithBytes` (see "Sending bytes to the backend"); a file that is already on the device is not sent at all — the page names it (`export_local_file`, `filen_cache_upload_from_path`) and Rust copies it. "Delete app data" ends the process on mobile (`app.restart()` can't relaunch there) — the next launch starts fresh.

**Picked folders (the Files tab's "Add root folder"; see also "The file scope").** On desktop this is the OS folder dialog. Android has no folder-picking dialog that hands back a real path (the official dialog plugin has none on mobile, and the system one gives `content://` URIs that path-based code can't use), so the app ships its own, `FolderPicker.kt`: a dialog that browses the real filesystem — storage volumes (internal storage, SD card/USB) and their folders, Up, New folder, Cancel, Use this folder — and hands back a real absolute path — *to Rust only*. From then on a picked folder is the same on both platforms: `picked_roots.rs` adds it to our scope and remembers it in `data.db`; the Files tab lists it again after a restart (`loadSavedRoots`, by root id — the opaque id `picked_roots.rs` made for it — so tags keyed by root id persist); SQLite databases in it and web apps use it through the ordinary file commands. **Persistent on both platforms** (desktop picks used to last one session). The ×/`remove_picked_root` **revokes it at once**. Rust starts the Android dialog over JNI and **polls** a static result string (`pending` → `picked:<path>` / `cancelled` / `error:<message>`) — no native callback needed. It needs Android's **All files access** (`MANAGE_EXTERNAL_STORAGE`, Android 11+; on 10 and older the classic READ/WRITE_EXTERNAL_STORAGE with `requestLegacyExternalStorage`), asked for the first time a folder is picked: the app opens that system settings page and on coming back continues, or reports "Storage access wasn't granted…". **Google Play restricts this permission** (a declaration and approval are needed); for sideloaded or personal builds it is fine. Verified on the emulator (API 34): the first-use permission flow, browsing, New folder, cancel/back, denied access, read/write/mkdir/rename, SQLite in a picked folder, the scope boundary, immediate revocation (read, list, write and SQLite all refused right after forgetting) and picking the same folder again in the same session, persistence across restarts. Not run: the Android 10-and-older permission path. Real deletes are permanent, as on desktop.

**Sending bytes to the backend.** Android's WebView can't hand a POST body to a custom protocol, so Tauri's IPC there falls back to postMessage, where a `Uint8Array` becomes a JSON array of numbers — 20 MB is tens of millions of JSON values (11 s and a huge memory spike in testing). Commands that take a file's bytes (`filen_write_file`, `filen_cache_write`, `save_to_device`) therefore read them through `ipc.rs` (`body_bytes`, `field`), which accepts the raw body + percent-encoded headers (desktop), or a JSON object `{ ...arguments, data: "<base64>" }` (Android; ~1 s for 20 MB), and the frontend calls them through `invokeWithBytes` (`src/lib/ipcBytes.ts`). A new upload-style command must do the same, and web apps sending big files on Android should send base64 that way too. (The fs plugin's own writes — the Files tab on the user folder — still use the plugin's array path on Android.) Responses are unaffected: raw `ArrayBuffer` responses work everywhere. **Big files don't use these at all** — see "Big files" in "The Filen cache": a file is sent in pieces (`filen_cache_upload_chunk`, 4 MiB at a time, so this base64 detour is per piece) or never leaves Rust.

**Not done:** iOS (`secure_store` has an error stub; the Xcode project doesn't exist).

## System apps and Notes

A **system app** is an app that ships inside this one: a page of the admin-app's own Vite project under `system/<id>/index.html` (its React code in `src/system/<id>/`), listed in the Rust catalog `system_apps::APPS` (`id`, `name`, `entry`) and as a `rollupOptions.input` entry in `vite.config.ts` (the two must agree — the multi-page build puts each in `dist/system/<id>/`). The set is fixed: there is no way for a user to add one, and the System Apps tab (first tab, the default) lists the catalog by name — `list_system_apps`, so an app shows there even before it has a window. **Adding a system app** means: the folder above, the catalog entry, the `input` entry, and a `cargo build` after `npm run build`.

The whole window machinery is the user apps' one, kept separate by a `kind` (`user`|`system`) on `secondary_windows` rows: the `list_/open_new_/add_…entry/close_all_/suspend_all_` commands take an optional `kind` (all kinds when omitted — the data-wipe path closes everything), `reopen_secondary_window` needs only the guid (the row says what to show), and the admin-app's `AppsTab` is one component with a `kind` prop and its own saved orderings (`systemAppsTab.*` vs `windowsTab.*`). A system window stores `system:<id>` as its relative path (also the key of its app state, tab icons and app version), so nothing can be confused with a user app's html path. Tabs work identically — `init_window_tab`, `update_tab_resource`, `submit_resource_icons`, `activate_tab`, the `codeSnippets` in the init response. **Closing a tab** (`close_tab`, the × on a tab item in either tab page) deletes the tab and its tags; if it is the tab an *open* window is showing, that window is also **suspended** (entry and other tabs kept, `reopen_secondary_window` brings it back showing the tab it showed before, or its first remaining one, or a new blank one if none is left), and closing any other tab leaves windows alone. "The tab a window is showing" is `SecondaryWindowsState::current_tabs`: set when the page binds to a tab (`init_window_tab`, `add_window_tab`) or is sent one (`activate_tab`), **kept when the window is suspended** (so reopening it shows the same tab) and dropped when the entry is.

**Who creates tabs.** Tab entries are made by the **admin-app side first**, and a page only *binds* to one:
- **Opening a window** (`open_new_secondary_window`, `add_secondary_window_entry`, `reopen_secondary_window`) first decides which tab the window will show (`tab_for_opening`): the tab it showed before, else its first tab, else a new blank placeholder (in its first group, or a new "Tab Group N" if it has none) — so the entry is in the list before the page exists. That tab is left *pending* for the window.
- **`init_window_tab`** — called by the page as it loads — **never creates a tab** (`tab_for_init`): it binds to the tab left pending for it (echoing the tab's stored resource id, except for a placeholder that was just created, which is filled in from the page's URL); with nothing pending it is a **reload** (or a second call), and binds to the window's current tab. So refreshing a window doesn't add a tab, and neither does calling init again.
- **`new tab` / `clone` in the admin-app** (`add_blank_tab`, `clone_tab`) create an entry there; `activate_tab` then shows it (below).
- **`add_window_tab`** is the one request with which a **web app adds a tab itself** — a second document, a new view. Same parameters and answer as `init_window_tab` (`addWindowTab` in `src/lib/secondaryWindows.ts`, `TabLib.addTab` in the samples); the new tab is placed in the group of the tab the window is showing and **becomes the window's current tab** (the page is showing it now, so a reload binds to it).

**What a page is told about itself** — the answer to `init_window_tab` / `add_window_tab` and the payload of `tab-navigate` (`TabInitResponse`): besides `tabGuid`, `resourceId` and `codeSnippets`, its own **`relativePath`** (from the user folder for a web app, `system:<id>` for a system app; for a file opened from Filen, its path in the drive), **`openedBy`** (`AdminApp` — opened from the admin-app itself — or `NotesApp`) and **`storage`** (`UserFolder`, `DeviceFolder`, `FilenCloud` or `Bundled` for a system app), and — when `storage` is `FilenCloud` — **`filen`**: `{ accountId, email, branch, branchIndex }` (the branch's name and index, or null). These are strings named after enum members, not booleans, so more can be added. Where they come from: `secondary_windows.origin` (JSON, `Origin` in `secondary_windows.rs`), recorded when the window entry is made; an entry with none is the ordinary case (`AdminApp` + `UserFolder`/`Bundled`, its own path). `fill_origin` adds them to every response.

**Tab labels and window titles** (`update_tab_resource`, `TabLib.updateTab`). A page tells what its tab shows with `tabText` — `{ firstRow, secondRow }`, each a list of pieces `{ text, bold?, italic?, mono? }` (`mono`: written in a monospaced font, like code; the flags are optional and a label stored before `mono` existed reads as not mono) — and, optionally, `appTitle`, a string. The window manager draws the two rows (`TabTextRow`: a bullet between the pieces of a row). **The title of the window** — the OS window's title on desktop, the card in the Recents screen on Android — is the tab the window is showing: its `appTitle` when it has a non-empty one, else **the pieces of the first row joined with ` • `** (the bullet the window manager draws between them; empty pieces left out, the second row not used), else what it was opened with (the page's path, or the system app's name). It is one plain line: no styles, line breaks become spaces. Both the label and the title are **replaced by every call** (sending no `appTitle` takes it back, so send it every time), and `secondary_windows::refresh_window_title` puts the result on the window whenever it may have changed: an update of the tab, a page binding to its tab (`init_window_tab`, `add_window_tab`) and switching tabs (`activate_tab`) — through `window_host::set_title` (`WebviewWindow::set_title`; `WindowBridge.title` → `setTaskDescription` on Android). Stored per tab: `tabs.app_title`, and `appTitle` in the tab's record.

**A tab's resource identifier can be read and copied** in the admin-app: the tab item's **#** button opens a dialog with it (and the app's page path) and a copy button.

**Suspending vs closing (windows), and deleting (tab groups, tabs).** A window entry in the list is either *open* (its window is showing) or *suspended* (only its entry exists). The two ways of getting rid of a window differ in what happens to the **entry**:
- **Suspend** (`suspend_secondary_window`, `suspend_all_…`) closes **only the actual window**. The entry stays in the list — with its tab groups, tabs and tags — as *Suspended*, and **Reopen** (`reopen_secondary_window`) brings the window back.
- **Close** (`close_secondary_window`, `close_all_…`) closes the window **and removes its entry** from the list, with its tab groups, tabs and tags. It works on a suspended window too — that is how a suspended entry is removed (there is no window to close, so only the entry goes).

**Closing the main window** (desktop) first suspends everything: `secondary_windows::main_window_close_requested` — on the main window's close request — **first** raises `shutting_down` (a flag on `SecondaryWindowsState`, not persisted: it only matters until the app is gone), then holds the close back while every secondary window is suspended (windows and the external web sites' windows closed, entries kept) and only then closes the main window for real (the second request is let through). While the flag is up `handle_window_destroyed` treats *any* window that goes away — ours, the person's, the OS's — as suspended, so even if the OS ends the app before the suspending is done no entry has been removed. (Tested: two secondary windows open, WM_CLOSE to the main window — both entries kept, the process exited.) On Android there is one window; nothing to do.

**Reload** (`reload_tab`, `reload_secondary_window`; a *Reload* button on a tab item — offered only while an open window is showing that tab (`TabRecord.showing`) —, on an open window's row and on an opened-from-this-tab app): the same as `location.reload()` in the page the window shows; a tab that no window shows has nothing to reload and the command says so. **A reload keeps the page's scroll** (the webview restores it; checked with a 220-line page on desktop and Android — a syncing note tab reloading on save stays where it was read).

The admin-app's buttons say which is which in their tooltips (Suspend (or Reopen) / Close on a window row, and — acting on the whole window — at the top of both its tab groups view and the tabs view of any of its groups, and "Suspend all" / "Close all" at the top level and per app). Below a window: **deleting a tab group** (`delete_tab_group`, 🗑 on its row) removes the group with its tabs and their tags, and **closing a tab** (`close_tab`) removes that tab; when what goes includes the tab an *open* window is showing, that window is **suspended** (not closed — its entry survives, minus the deleted tabs), and otherwise windows are left alone.

**Switching tabs is an event** — the same for system apps and user apps. `activate_tab` on a tab of an *open* window sends that window (only) the **`tab-navigate`** event (`secondary_windows::EVENT_TAB_NAVIGATE`), whose payload is exactly what `init_window_tab` answers with — `{ tabGuid, resourceId, codeSnippets }`, the tab's own stored resource id (empty for a tab never used) — and the page **shows that tab in place; it is not reloaded**. An app with several tabs must therefore handle it (`onTabNavigate` in `src/lib/secondaryWindows.ts`; `TabLib` for the samples: it listens from the moment it loads, its default reaction is to start the page over (`location.reload()`), and `TabLib.onNavigate(handler)` replaces that; `TabLib.openTab` binds the page, `TabLib.addTab` adds a tab). **Attach the listener before calling `init_window_tab`** (`await onTabNavigate(…)` first) so no event can be missed. A window that isn't open is simply opened with that tab left pending, and its page's init response says which tab it is. For an open window the activated tab becomes the window's current tab, so if its page loads again (a reload the app does itself in response, or the person pressing reload) its init binds to that tab — it can't create another. **Listen on the page's own webview window** (`getCurrentWebviewWindow().listen(…)`, `webviewWindow.getCurrentWebviewWindow()` in the samples), never the global `listen`: a global listener also hears events sent to *other* windows (found live: it made another window reload and create an extra tab). Notes handles it by switching to the tab's place (`system:notes?s=…` in its resource id), keeping each tab's own place; its editor keeps the source of the file it holds, so a switch can't redirect a save.

**A system app is not the admin-app.** Admin identity is **path-based**, not origin-based: `window_host::is_admin_url` is true only for the frontend's root page (`/`, `/index.html`), `is_system_url` for pages under `/system/`, and navigation is confined per kind (`Allowed{user,system,admin}`: a user window reaches only `csuser`, a system window only its own pages, the main window the admin-app's). A system window gets exactly the user apps' capabilities, never `filen_login`, data-folder or deploy commands — verified live: Notes is refused `filen_logout`/`delete_app_data` like a user app. On Android, where a window's WebView is not Tauri's, who is calling is what its activity says (`CallerWindow`), and a system window is one whose page is a system app's.

**Notes** (`src/system/notes/`) is a *unified file manager* whose sources are folders on this device (the user folder and picked folders, through the ordinary `fs_*` commands) and the connected Filen accounts (through the cache below), behind one `FileSource` interface (`sources.ts`) — so copy/cut/paste works between any two of them (read + write; same-source cut is a rename). It lists **paginated** (client-side, the page size being the global one), fetches a local folder's sizes/dates only for the page on screen, edits text files (≤ 2 MB, UTF-8), uploads, exports (`save_to_device`), renames, deletes. Per Filen account it shows the **cache interval** selector (incl. "Never (available offline)"), the cache's freshness (or "Offline — showing the listing as it was"), "Clear the cache", and the **branch** bar (switch, new, changes, commit — asking before overwriting on conflict — discard). Each Notes tab is a *place* (`Place` in `tabs.ts`) — one of three **views**: the **home page**, the page for **managing notebooks**, or the **file manager**. Its resource id names it: `system:notes?v=home`, `system:notes?v=notebooks`, or — for the file manager — `system:notes?s=<source>&b=<branch>&p=<path>`; it is updated as the person navigates (a page can't change its own address — the window manager stores the resource id), so activating, cloning or reloading a tab returns to it; the window manager's tab icon distinguishes home / notebooks / local / Filen / branch. **A tab that names no place starts at the home page** (`NotesRoot.tsx` chooses the view; the file manager, `NotesApp.tsx`, is what it was, with a *Notes home* button added). Notes also remembers the last place of the file manager in its own app state — where the home page's *File manager* link goes.

**Notebooks** (`notebooks.ts`, `notebookFile.ts`, `NotebooksPage.tsx`, `LocationPicker.tsx`; the format and the idea are in `docs/strategies/notes-strategy.md`). The **home page** has two links: *Manage notebooks* and *File manager*. A notebook *is* its `[note-book].json` file (`{ "Title", "CreatedAt", "NoteBookGuid" }` — only `Title` and `NoteBookGuid` are ever required of it, `parseNotebookFile` in `notebookFile.ts`: `NoteBookGuid` because it's what makes two files the same notebook wherever found, nothing standing in for it, but `CreatedAt` is cosmetic and simply left out when it's missing or not a valid date, never a reason to refuse the file) and its folder is the notebook's root; the app keeps only **a list of the notebooks it knows** — `notes.notebooks` in the Notes app's own state (`data.db`), entries `{ guid, title, sourceId, folder, fileName, addedAt }`, where `sourceId` is a folder of this device or a Filen account (never a branch). **Listed** (in that list) and **found** (the file exists on this device or in Filen, the app hasn't been told) are told apart by the GUID in the file. The *Manage notebooks* page lists them — each checked against its file when the page opens (unreachable, or no longer a notebook, is shown with the reason; a title changed outside the app is taken into the list, the file being the truth) — with: **show its folder** in the file manager, **change its title** (written to the file first, every other key of the file kept, then to the list) and **take it out of the list** (asks; nothing is deleted, the files stay). **Add a notebook…** asks whether to *add an existing notebook* (the person chooses its `[note-book].json`, in a place picker that marks every notebook file it shows with its title and **"in your list" / "not in your list yet"**; a file that isn't a valid notebook is refused with a reason, one that is listed already is reported, with where) or *create a new one* (a title, then the root folder in the same picker — which can also make folders and add a folder of this device — and the file is written; the folder need not be empty). **Warning:** a folder that already holds a file whose name is or ends with `[note-book].json` is flagged in the picker, and choosing it opens a dialog listing those files (with their titles) — a notebook's notes live in its root folder, so a second notebook there would share them — to *choose another folder* (the picker comes back to that folder), *cancel*, or *create it here anyway*; a new notebook's file is named `[note-book].json`, or, when that name is taken, after its title (`<title> [note-book].json`, never overwriting). **Notes** (`noteModel.ts`; the format and the idea are in `docs/strategies/notes-strategy.md`): a notebook's root folder — and every note's short folder — holds child notes as pairs of folders `NNN` + `NNN-<title>` (numbered *after the largest* **in the note items' interval, `999`→`401`, going down** — the first note is `999`, the next `998` —, gaps stay; the marker holds a `.keep`; notes numbered in the first versions of the app, `001`, `002`…, are *outside every interval*: they show and work as ever and can be converted into an interval, see "The indexes of the notes"), each with its markdown (`0-<title>[note].md`, starting with the title as a heading), `[note].json`, `[note-children].json` (`{ ChildNotes: { "NNN": { Title, CreatedAt, UpdatedAt } } }`, the list read to show the children; rebuilt from the folders when missing or damaged) and, on demand, the two-digit internals pair `01` + `01-Note files` for the note's files. **A note's `Title` is the only property of it ever required anywhere — `CreatedAt`/`UpdatedAt` are cosmetic and optional, everywhere they appear.** A `[note-children].json` entry without a usable `Title` of its own (missing, blank, or the whole entry damaged) doesn't drop the note from the list — a plain `Title`/`CreatedAt` requirement on every entry used to (a note without `CreatedAt` was silently left out of its parent's whole list, however many others were fine, the actual shape of a real bug reported live): `readChildren` recovers it instead (`recoverNoteTitle` in `noteModel.ts`), first from the note's own `[note].json`, then — when that has no usable `Title` either — from the first heading of its markdown, repairing `[note].json` when the markdown had to supply it and, once any entries needed recovering, writing the parent's `[note-children].json` back with what was found, so neither file is searched again next time; only a note with no title anywhere (not in the children entry, its own json, nor its markdown) is left out, as before. The same recovery backs `readNote` (single-note reads, e.g. the breadcrumbs) and the folder-rebuild fallback path alike. `CreatedAt`/`UpdatedAt` are carried along from wherever they're found and never invented, except a fresh `CreatedAt` stamp for a `[note].json` recovered from markdown with none at all (so a repaired note still sorts sensibly by age). **A `Title`-only repair still backfills a missing `CreatedAt`**: an entry whose `Title` is already fine but has **no `CreatedAt` key at all** (not present, not blank — an older note, from before it was tracked) is not treated as needing the full title-recovery above, but its own `[note].json` is checked for one, **once**: whatever is found — a real date, or nothing — is written back as an explicit value (`CreatedAt: ''` when there truly is none anywhere, `[note].json` included), so the key's mere *presence* afterward means "resolved" and this lookup is never repeated for that note. **This must write back even when nothing was found** — an earlier version of this fix only wrote back a date it actually found, so every note with no `CreatedAt` anywhere paid for a whole extra read of its `[note].json` on *every single load*, not just once; found live as several-seconds-long first loads of an ordinary list on Android, where each such read is a JNI/postMessage round trip rather than a plain local read, and real notebooks commonly have dozens of such notes. **Every entry that needs one of these looks is resolved concurrently** (`Promise.all` over the whole folder's entries, not a sequential `for`-`await` loop) rather than one note after another: for a Filen notebook each such look is a real network round trip through the cache (`resolve_dir` alone walks every path segment of the file with its own API call), so resolving them one at a time meant a first load's total wait was the *sum* of all of them; concurrently, it's closer to the slowest one alone (found live: even with the write-once fix in place, a Filen notebook with several dozen untracked notes still took "dozens of seconds" on Android, because that "once" was still sequential — and it wasn't slow at all doing the same on desktop against the same Filen notebook, pointing at the Android IPC bridge's per-call round-trip cost, not Filen's network latency, as the dominant factor `Promise.all` addresses). The full-folder-rebuild fallback path (`[note-children].json` itself missing) resolves its entries concurrently the same way, since it reads every entry's `[note].json`, not just the ones needing repair. (The `formatWhen` that shows the date next to a note's title also has its own fix, independent of this one: a block element with truly no text content collapses to zero height, so a note with no date — a legitimate, permanent state for some notes, not always a repairable gap — would sit in a visibly shorter row than its siblings; `formatWhen` now returns a non-breaking space rather than `''`, so every row is the same height whether or not it shows a date. The same unevenness existed in the notebooks list itself, for an unrelated reason: a notebook whose file has a problem showed a third line with the reason, taller than a normal notebook's two lines — removed, since the reason was already the "can't be opened" badge's tooltip, so nothing was lost.) Verified live (isolated data folder): a hand-built notebook with three notes — one entry missing only `CreatedAt`, one entry blank but a valid `[note].json`, one entry and `[note].json` both blank with only the markdown heading left — all three showed, and `[note].json`/`[note-children].json` were confirmed repaired on disk to match. Verified live again on real data (a Filen notebook and a notebook list with dozens of pre-existing notes and two real notebooks, one of them flagged "can't be opened"): every row the same height in both lists after the fixes, on a fresh install. Operations (over any `FileSource`, so on this device or in Filen, in a branch too): `createNote`, `renameNote` (marker folder, markdown file, heading and both JSON files follow), `touchNote`, `deleteNote`, `readChildren`, `ensureNoteFiles`. **A note's address** is the path of its short folder with the query key `note` (`/Book/001/002?note`; `noteAddress`, `isNoteQuery`). Not built: sections themselves (their intervals are in the config and a note can be *converted* into one); the notebook's reserved pair (`03` + `03-[note-book]`) holds only the User Action's setting so far (see "User Action").

**The note pages** (each a *place* of the Notes tab — `Place` in `tabs.ts`: `v=notes|noteEdit|noteFiles` with `s` (source) and `f` (the note's or notebook's folder), the window manager labelling it with the note's title):

Each row shows the note's **index** (`001`; hidden by the Notes setting) and has icon buttons — *edit its markdown*, *its child notes*, *its files*, *show its folder in the File Manager*, *change its title*, *delete* — and a **three-dots** button; the same menu opens by a right click or a long press on the row (`components/ContextMenu.tsx`, kept inside the window whatever its width). The rows are a keyboard list (Up/Down focus, Enter opens the note, Right its children, Left the parent). Cut and copy (from the menu, or the selection bar) and *Move / Copy here…* (in the header once something is on the notes clipboard, `noteClipboard.ts`) put notes under another parent — see "The indexes of the notes". *Go to a path or a note's address*: a `?note` address opens that note, the path of a note's folder shows its children, anything else is shown in the File Manager. (Reached from the notebooks page's *Open the notebook* button.)

Ctrl+S or the button saves; what isn't saved is kept as a draft (`notes.noteDrafts`) that comes back with the page; a Filen note is checked against Filen first; **the title follows the first heading** (a changed heading renames the note as above); saving tells the windows that show the note (`notify_file_saved`, below).

**The indexes of the notes** (`noteIndexes.ts` — pure functions —, `noteModel.ts`, `noteTransfer.ts`, `IndexesModal.tsx`, `PasteNotesModal.tsx`, `DeleteNotesModal.tsx`; the intervals are in the config file above). A note's index is the name of its short folder; each *kind* has an **interval** (note items `999`→`401`, and the three section kinds). A new note gets the index **one step past the furthest in use** of the interval it is made in (`nextIndexIn`; the interval's start when none is used, "no room" when nothing lies beyond the furthest — normalizing makes room) — **the note items' interval by default, or a section's when the person chooses one**: *New note…* (`NewNoteModal.tsx`) asks for the title and, alongside it, which of the four intervals the index comes from (a radio per interval, showing its range; one with no room is disabled with the reason) — the one place a note picks up an interval other than note items at the moment it's made, as opposed to being *converted* into one afterwards through the indexes dialog below. `createNote`/`nextNoteIndex` take the chosen interval (`NoteInterval`, default `NOTE_ITEMS`) instead of assuming note items. The note-indexes button of a notes page (*The indexes of these notes…*) opens **one dialog for everything**: every index can be typed over (checked: 1–999, none used twice; the interval of each is shown); the rows can be **reordered** by dragging their grip or with their up / down arrows — the *same* indexes are handed out again in the new order (`reorder`: a note takes another's place, nothing else moves, so no interval is disturbed), recalculated at once but **written only by Apply**; **Normalize** closes the gaps of *each interval on its own* from the interval's start, keeping the order (the notes outside every interval close up from their lowest); **Convert** moves **the selected notes** into another interval — each row has a checkbox, and *All*, *None* and one button **per interval** ("Note items (3)", "Outside the intervals (2)"…) select an entire interval at once (a second press unselects it) — keeping their order (the notes outside the intervals first, then each interval in the config's order, each in its own direction) and taking the first indexes of the target that others don't hold; a selected note that is in the target already stays (an error when there isn't room). **Apply** (`reassignIndexes`) checks everything first (valid, distinct, not held by a note that isn't moving, no leftover temporary name), then renames **in two phases through the temporary prefix**: every pair that moves takes `t_`+its index (both folders, the short one and the marker), then every one takes its final name; the parent's `[note-children].json` follows. A failure midway leaves the reached pairs under `t_`, which the next renumbering puts back first (`recoverInterrupted`). *Delete* asks in a dialog with the option to **normalize the notes that remain**. **Moving and copying notes under another parent** (`placeNotes`, over any two sources, in a branch too): the paste dialog gives each note by default **the next available index** of the new parent (as a new note would), or **fills the gaps** of the parent, or takes indexes of the person's own; a *copy* makes new pairs with everything inside (children, files), a *cut* renames within one source and copies-then-deletes across two, refusing a note into itself or under its own child and a cut to where it already is; a cut can **normalize what stays behind**. Tested (Node, an in-memory source, 60+ assertions — the intervals, next/gaps, normalize, convert, reorder, the two-phase renaming with its refusals and recovery, copy/cut, across two sources) and live on desktop and the Android emulator (isolated data): the numbering 999/998/997, F2 and the arrow steps, an index typed in the list, the dialog (normalize, convert, an arrow, Apply on disk), cut and paste with the next index, delete with normalize. **The interval choice in *New note…*** verified live on desktop (isolated data folder): the dialog listing all four intervals with their ranges, creating a note in "Primary note sections" landed it at `199` (the interval's start) on disk, beside the existing `999`-numbered note from the note items' interval, both showing correctly in the list afterward.

- **Go to a path** (`GoToPathModal`) keeps a query (`parsePathInput` → `{ segments, query }`): a file's address shows the view of its kind — the editor for a text file — and a note's address opens the note.
- Tested live on desktop (isolated data folder): a notebook made by hand, creating a note (its pair of folders and files on disk), editing and saving with the heading changed (marker folder, markdown file and both JSON files renamed), the note as a web app in a window, saving from the editor reloading that window, then (tab-hosted, isolated data folder, desktop and the Android emulator) a click on a note showing it in a second tab of the same window, a second click bringing that tab back (still two tabs, no window added), the page refused `open_file_as_web_app` and `save_to_device` yet allowed the clipboard and an app state of its own, the three-dots menu (index changed on disk with its marker, select by menu and by right click / long press, a separate tab, show/suspend/close of the syncing tab), the settings page (indexes hidden, clipboard cleared), and — desktop — a save in an editor in another window reloading the syncing tab and not the separate one; a child note, the note's files explorer (`01` made, a file made inside it, *Open in File Manager*), a note's address in *Go to a path*.

In a **Filen** source Notes also does the following (all through the cache commands below): **saving asks Filen first** (`filen_cache_check_version`) — if the file is no longer the version that was opened, nothing is written and a dialog offers *Overwrite*, *Discard changes* (the edits are lost and the file is read again) or *Cancel* (back to the editor, as if Save had not been pressed); the editor has a **New branch…** button (makes a branch and carries on in it: an unchanged file is checked out there, an edited one is saved into it with the next Save); each Filen file has a **lock** button (locked against caching) and, in a branch, a **check out** button (and *let go* for a file that was checked out and not changed) — see "Versions, locks and checkouts" below. The admin-app's own Filen tab has no editor; when an upload would replace a file of the same name it says so first.

**Editing a text file is part of the tab's place**: a tab whose editor is open has `&e=<file>` in its resource id (the file, relative to its source's root), its resource type is `editing` (its own icon), and its second row reads "Editing /file" plus, in italics, "unsaved changes" — so the window manager shows what each Notes tab is doing. Activating such a tab (or reloading the window) opens the editor on that file again, and switching to a tab that isn't editing closes it. **The unsaved text is kept as a draft** (`notes.drafts` in the app state: tab guid → source, branch, path, text, version), written a moment after the last key and when the tab is left, restored with the editor and dropped when the file is saved, its changes are discarded or the person closes the editor; the version check before saving still applies to a restored draft. A tab that names no place of its own starts from the last place but never in the editor.

## The Filen cache (`files/`)

`files_cache.rs` (the `Cache`, in `HostState`-style managed state), with `filen_cache.rs` as its commands (`filen_cache_account/_set_interval/_clear/_list/_read/_write/_mkdir/_rm/_rename/_branches/_create_branch/_branch_changes/_commit_branch/_discard_branch`, same shapes as the `filen_*` ones, plus an optional `branch`; no credential ever reaches a window). Layout inside `files/` (built with folder pairs — see below):

```
files/data.db                     listings, metadata, per-account settings, branch changes
files/a/NNN-filen@@<email>@@<id>/ only a .keep: says whose NNN is
files/a/NNN/c/…                   cached CONTENT of the account, at its Filen paths
files/a/NNN/b/MMM/…               what branch MMM of the account has changed (MMM-<branch name> beside it)
files/a/NNN/t/…                   thumbnails of the account's files (see "Media")
files/a/NNN/tb/MMM/…              thumbnails of the files branch MMM changed (goes with the branch)
```

**Everything of one account lives inside its own `NNN` folder in `a`** — its content, its branches, its thumbnails and its branches'
thumbnails — not spread across top-level folders of their own; a folder of this device's branches and thumbnails live inside its `NNN`
in `a` the same way (see "Branches of a folder of this device"). **An older layout kept `b`, `t` and `tb` as top-level folders beside
`a`** (each with its own `NNN-<owner>` pairs); `Cache::open` **migrates** whatever it finds there into the owner's folder in `a` the first
time it runs (`migrate_old_layout`: the folder is renamed in place, never copied, so a big branch isn't duplicated; a target that already
exists is left alone; the old top-level folders are removed once empty) — safe to run again, and it works for a folder of this device's old
pairs (`local-fs@@…`) the same way it does for a Filen account's. Rust-tested (a hand-built old layout, migrated, checked on disk, and
migrated again to confirm nothing more happens) and verified live on desktop: an old-layout `files/` folder made by hand had its branch,
its thumbnails and its branch's thumbnails all found inside the root's own folder in `a` after the next start, with the old `b`/`t`/`tb`
gone.

- **A cache, not a sync.** Nothing is fetched until asked: listing a folder fetches and remembers that listing; opening or exporting a file fetches and remembers its content. Everything remembered — listings, metadata and contents — expires after the account's **cache interval** (default 1 hour, chosen per account in Notes) and is then fetched again; with the interval turned off (`ttlSecs` = `null`) nothing ever expires, which is how a person makes things available offline. If Filen can't be reached, an expired listing/file is served marked *stale* rather than failing. Writes to the account itself go straight to Filen and update the cache.
- **Branches** are the git-like alternative: a set of local changes (files written, folders made, things deleted) kept under `b/` and in `data.db` until *committed* (applied to Filen, then the branch is deleted) or *discarded*. Reading through a branch shows Filen's cached state with the branch's changes on top. A commit first checks that Filen still looks as it did when each change was made; if not, it applies nothing and returns the `conflicts` unless `force`. A branch's name is any valid file name of ≤ 100 characters and is its folder's readable half.
- **Versions, locks and checkouts** (`files_cache.rs`, commands `filen_cache_version/_check_version/_rebase/_set_locked/_checkout/_release`):
  - A file's **version** is what Filen's listing says: whether it exists, its size and modification time (`FileVersion`). `filen_cache_version` gives the one the cache knows — what a window that has just opened the file is working on (in a branch that changed or checked out the file: the version *that* was based on). **`filen_cache_check_version` asks Filen itself, not the cache** (a locked file would keep the cache frozen), and compares it with the version the caller remembers: `{ upToDate, problem, current }` (*newer*, *different*, *deleted after you started*, *created after you started*); it fails when Filen can't be reached — the account can't be written to then anyway, and Notes lets a save into a *branch* go ahead (it stays local, and the commit checks again). In a branch, a person who chose to overwrite calls `filen_cache_rebase`, which bases the change on what Filen has now so the commit doesn't warn about the same thing again.
  - **Commit asks Filen directly too** (a fresh listing of each folder involved, no longer through the cache), and it now verifies **every** file in the branch, checkouts included: a file that changed or was deleted in Filen after it was changed *or checked out* is a conflict, reported unless `force`.
  - A **lock** (`file_locks` table, kept apart from `entries` so it survives its row being dropped and made again) freezes a file of the account: its cached copy is served as it is — no check that it is current, so it opens offline too — and neither the cache interval, a newer listing, a deletion in Filen, nor "Clear the cache" touches it (the folders above it stay too, their rows name it). Locking fetches the file first if it isn't cached (there has to be a copy to keep). It belongs to the **account's** file, so a branch that reads it through sees the same frozen copy, and the lock is available in the account and in every branch; writing to a locked file (or uploading over it) keeps it locked, on the new content, and deleting or moving it, or disconnecting the account, drops the lock. `Entry.locked` says so in listings.
  - A **checkout** (`filen_cache_checkout`, in a branch) takes a file into the branch *without changing it*: its content is copied into the branch and recorded as a change of kind `checkout`, based on the version that was copied, so it appears among the branch's pending changes. Editing it turns it into an ordinary `put` that keeps that base; `filen_cache_release` lets go of one that was never changed. Committing applies nothing for a checkout — it only had its version verified.
- **Lifecycle.** Connecting an account creates its two folders (`ensure_account`); disconnecting it (`filen_logout`) deletes its folders in `a`, `b`, `t` and `tb` — its cached files, every branch and their thumbnails — and its rows in `files/data.db` (`forget_account`); "Delete app data" and "clear the custom data folder" remove `files/` with the rest (after closing the cache's database — `Cache::close` — since Windows can't delete an open file), and relocating the data folder switches to the `files/` inside the new one, exactly as it does for `admin/`.
- The whole thing is tested without a network (`Remote` trait, in-memory remote): TTL expiry, offline stale serving, write-through, branch overlay/commit/conflict/discard, lifecycle. Live-verified on desktop **against a real Filen account** (the cache commands and the Notes UI, inside a throwaway folder in the account): folder/file write-through checked against Filen directly, a cache hit versus a forced refresh, the interval expiring and "never", rename, a branch that is committed, a real conflict (refused without `force`, the branch wins with it), a discarded branch, gap-filled branch indexes and the resulting `files/a` / `files/b` layout on disk. Also driven through the Notes UI with the `filen_*` IPC faked (the stale/offline indicator, which needs Filen to be unreachable). **Not** run live: disconnecting an account (it would log the person out; covered by unit tests), offline serving, and the Android build against a real account.

**Big files never sit in memory** (one chunk at a time is the most anything holds), on the way up, down and out:
- **Down.** A file is fetched from Filen chunk by chunk (`filen::ops::read_file_chunks`, 1 MiB at a time) into a `.part` file beside its cache location and **renamed into place only when complete** (`Cache::cached_file`); an interrupted download leaves no partial file and nothing marked as cached. `Cache::read` (the bytes API, for the editor's ≤ 2 MB) is built on it; Notes doesn't even fetch a file above 2 MB to edit it.
- **Up.** `begin_upload` / `upload_bytes` / `finish_upload` (`filen::ops::UploadSession`) cut whatever is pushed into exact 1 MiB Filen chunks, encrypt and send each as it completes, and only `finish_upload` makes the file exist (replacing an existing file by trashing the old one once the new one is readable). The cache wraps it in an `UploadJob` that also writes every piece to a temporary file in the account's `tmp/` folder, which *becomes the cached copy* when the upload finishes — Filen and the cache get each piece at the same moment. Dropping an unfinished job deletes its temporary file, and anything in flight when the app stopped is cleared at the next start (`remove_leftover_uploads`).
- **Two ways to feed an upload.** (1) *From the page*, for a `File` from the device's file chooser (which has no path): `filen_cache_upload_begin` → `filen_cache_upload_chunk` (the piece is the request body, any size) → `filen_cache_upload_finish` / `_abort`; a session belongs to the window that began it (another window's push, finish or abort is refused/ignored) and lapses after an hour. (2) *From a file the app may already read*: `filen_cache_upload_from_path(…, root, source)` — Rust reads it piece by piece; the file never goes through the window. Into a branch, either way, the file stays local until the branch is committed, and `commit_branch` streams each changed file from disk too.
- **Out.** `filen_cache_export` (to the device) and `filen_cache_download_to(…, root, dest)` (into a folder the app may use) fetch into the cache as above, then `fs::copy` on this side; `export_local_file` does the same for a local file. On Android the export streams into Downloads through MediaStore (`DeviceFiles.saveFileToDownloads`). Notes' copy/paste between sources uses these when one side is local and the other Filen, and `fs_copy` (a plain `std::fs::copy` between two places the scope allows, refusing to copy a file onto itself) when both are local — the Files tab's copy too; only the admin-app's own Filen tab (which doesn't use the cache) still moves a whole file through the page.
- **Into a local folder** the same idea, for a `File` from the device's file chooser (`fs_upload.rs`, the local counterpart of the Filen sessions): `fs_upload_begin(root, path)` → `fs_upload_chunk` (4 MiB pieces, request body + `id`) → `fs_upload_finish` / `_abort`, in `src/lib/fs.ts` `uploadFile` (used by Notes' local sources and the Files tab). Pieces are appended to a temporary file in `files/local-uploads/` — the app's own folder, never the person's — and renamed (or, across drives, copied) into place at the end, so the file appears only when complete; the destination is judged by the scope at the start *and* at the end (a folder forgotten meanwhile is refused), the upload belongs to its window, and the folder is emptied at every start. Verified live with a 96 MiB file into the user folder and a picked folder: byte-identical, 1.4 s each, and the backend's memory rose by a fixed ~25 MB (the pieces in flight), not with the size.
- Verified live against a real account with a 48 MiB file: byte-identical round trips through both upload routes and the streamed download, and the backend process's memory stayed within a few MB of idle (working set 41 → 47 MB during the upload, 45 MB during the download) instead of growing with the file.

**Folder pairs** (`folder_pairs.rs`; the strategy is in `docs/strategies/folder-pairs-strategy.md`): to make a folder that a program can address by a short name and a person can identify by a long one, create two siblings — `NNN` (the data folder; three digits, zero-padded) and `NNN-<full name part>` (a marker whose name says what `NNN` is, holding nothing but a `.keep` file with one dash in it, so it is never an *empty* folder — copying, mirroring and archiving tend to lose those; `create` and `ensure` write it, and the cache's `open` gives it to every pair at each start, which is how pairs made before the rule got theirs). `NNN` is worked out from a listing of the parent (never remembered), by the **`Numbering`** the caller uses (`Numbering::DEFAULT`: no prefix, upward from `001` with three digits, first free — in general a constant **prefix**, an **interval** of indexes going up or down, or a single constant index, and an **`Indexing`** option; `rename`/`reassign` renumber many pairs in two phases through the temporary prefix `t_`; see the strategy document, "Generalising the way the index is computed") — its **`Indexing`** option: `AfterLargest` (one more than the highest `NNN-…`; gaps are left, only an index freed by deleting the newest pair returns) or **`FillGaps`** (the lowest index, from 1, that isn't in use — `001` and `003` are followed by `002`; a bare short folder `NNN` with no full folder beside it counts as in use). **Everything we create now fills gaps** (`files_cache::NUMBERING`): accounts in `files/a`, account folders in `files/b` and branches — so deleting a pair leaves no permanent hole. One consequence to remember: a branch's index is what a Notes tab's resource id names (`b=<index>`), and a discarded branch's index can be handed to a *new* branch, so a stale tab that still names it would open the new one (a tab whose branch vanished, and whose index wasn't reused, falls back to the account). For accounts the part is `filen@@<email>@@<user id>`; for branches it is the branch's name. Use it for anything new that follows the same need.

## Media: the viewer, thumbnails, and serving files in pieces

**Serving a file in pieces** (`file_serving.rs`; used by the `csuser` protocol and, on Android, by `nativeServe`). A `<video>`/`<audio>` asks for its file with a `Range` header and seeks by asking for other ranges, so a request with a range is answered `206 Partial Content` with **at most 4 MiB** read from the file at that place (`Content-Range`, `Accept-Ranges: bytes`; a range past the end is `416`); the player asks again as it goes, so nothing bigger than a piece is ever held — in Rust, in the webview or (Android) in the JVM. A request with no range gets the whole file, as before (a picture, a script, a page). Every source is a file on disk by then: the user folder, a picked folder, or — for Filen — the cache's copy (`Cache::cached_file` fetches it there piece by piece first, so playing a Filen video starts once it is downloaded, and never holds it in memory). **Across origins**: Notes (`tauri.localhost`) loads files from the web apps' origin (`csuser`), so the CSP's `img-src` and `media-src` — and only those — name `csuser:` and `http://csuser.localhost` (the CSP test allows them for those two directives only), and an answer carries `Access-Control-Allow-Origin` **only for this app's own frontend origins** (`allowed_origin`; on Android, where the WebView doesn't always say where a request comes from, a request with no `Origin` is taken as the app's own) — so a thumbnail can be read back from a canvas, while a web page of the web, in an external site's window, can read nothing. `media_url(file)` gives a page the address for a `FileRef` — segment by segment, so a `#` or `?` in a name is part of the name, and never a real path. Tested with a 600 MB file: opening it moves the process's memory by nothing.

**The media viewer** (`components/MediaViewer.tsx`, `lib/media.ts`: `mediaKindOf` by extension — pictures png/jpg/gif/webp/bmp/svg/avif/ico, video mp4/m4v/webm/ogv/mov, sound mp3/m4a/aac/wav/ogg/opus/flac, as far as the webview plays them). In Notes' **File Manager and Note Files Explorer** (both are `NotesApp`) a click on such a file — or its *View* button (an svg also has *Edit as text*) — opens it over the whole window, with the folder's other media a step away (arrows in the bar, PageUp/PageDown, ← → for pictures). The file is never read into the page: it is an address the webview loads itself.
- **Picture**: opens showing the whole of it. Zoom by the wheel (about the pointer), a two-finger pinch, the buttons, +/−/0 or a double click; drag it when it is bigger than the window — it is kept from being dragged off (`clamp`: centred while smaller than the window on an axis, no gap at either edge once larger), so zoomed in enough it fills the window. **One press on it hides the bars, the next brings them back.**
- **Video / sound**: a bar with play/pause, **back and forward 10 seconds — acting on `pointerdown`**, the time, a draggable progress, sound on/off. Playing a video **hides the bars**; a press on the video brings them back and, if it keeps playing, they go again after 3 s (the timer restarts with any touch of the bar); pausing keeps them. A sound keeps its bar.
- **Full screen** for any of them (F, or the button; Esc leaves it): `requestFullscreen()` on the viewer — on Android through `WindowActivity`'s `onShowCustomView` (see "Android").
- Tested live on desktop and the Android emulator (isolated data): the whole picture at first, the wheel/buttons zooming to 7×+, a drag (synthetic pointer events on desktop, a real swipe on Android) that stops at the edges, the bars toggling by presses, the next media, full screen (and Back leaving it first on Android), a sound playing and seeking through ranges, ±10 s, a recorded video playing with its bars hiding/returning/staying when paused.

**Thumbnails** (*View thumbnails* in the File Manager's toolbar, `ThumbnailGrid.tsx`; the choice is `viewThumbnails` in Notes' settings). A grid of cards — the small image of a picture or of a video's first moments, an icon for everything else; a press opens (folder, viewer, editor), the card's three dots / right click / long press offer details, export, copy, cut, rename, delete (`menuFor`). A card makes its thumbnail when it comes into view (`thumbnails.ts`: the webview decodes the file — a picture, or a video seeked a moment in — and draws it to a 256 px JPEG; three at a time; a file that can't be decoded, or a Filen file over 32 MiB that isn't cached yet, keeps its icon).
- **On this device** thumbnails live for the session only (blob addresses, keyed by path, date and size); the files are right there.
- **In a Filen account** they are kept on disk with the cache, inside the account's own folder in `a`, beside its `c` and `b`: `files/a/NNN/t/…` (**t**humbnails of the account's files) and `files/a/NNN/tb/MMM/…` (of the files **b**ranch `MMM` changed), folder pairs like the branches' (`layout::FILES_THUMBNAILS_FOLDER`, `FILES_BRANCH_THUMBNAILS_FOLDER`; `Cache::thumb_get/_put`, commands `filen_cache_thumb_get`/`_put`, the latter with the JPEG as the body via `invokeWithBytes`, ≤ 512 KiB). A thumbnail is laid out like its file and named `<name>.<modified ms>-<size>.jpg`, so **a changed file simply has none until one is made for its new version, which replaces the old**. In a branch a file the branch has *not* changed shows the account's thumbnail; one it changed keeps its own in `tb`. **Committing or discarding a branch deletes both places** — its `b/MMM` pair and its `tb/MMM` pair (`delete_branch_files_and_rows`); "Clear the cache" clears the account's `t` folder, and disconnecting the account removes the account's whole `NNN` folder in `a` (content, branches and thumbnails together). (Rust unit tests: versions, replacement, branch/account separation, both deletions.)
- Not done: thumbnails aren't refreshed by the file's *content* changing with the same date and size; a Filen thumbnail is made from the file as the cache has it.

## The config file of the folder pairs and the notes (`config/folder-pairs-and-notes.json`)

**Every constant of the folder pairs and the notes is in one file**, `csdrive-webhost-tauriapp/config/folder-pairs-and-notes.json`: the folder pairs' `.keep` file and its content (`-`), the temporary prefix (`t_`), the longest name part (100), the storage provider named in a cached account's folder (`filen`), the default numbering (what the Filen cache's accounts and branches use: no prefix, from `001` up, three digits, first free), the notes' file names (`[note].json`, `[note-children].json`, `[note-book].json`, `[user-action].json`), the markdown's prefix and suffix (`0-`, `[note].md`), **the four numberings of the note items and sections** — note items `999`→`401` (after the largest), primary sections `199`→`111`, secondary `299`→`201`, ternary `399`→`301` — and the internals' pairs (`01` the note's files, `02` its internals, `03` the notebook's own; two digits, a constant each, with the name of the full folder).

**It is compiled in**, not read from the device: the Rust backend embeds it (`src-tauri/src/config.rs`, `include_str!`; `folder_pairs::keep_file()`, `temporary_prefix()`, `max_name_part_chars()` and `config::DEFAULT_NUMBERING` read it) and the frontend bundles the same file (`src/lib/appConfig.ts`, a JSON import: `KEEP_FILE`, `TEMPORARY_PREFIX`, `NOTE_JSON`, `NOTE_ITEMS`…), so it is inside every installer and APK, one file serves both languages, and nothing on a person's machine can change what a name means. To change a constant: edit the file and rebuild. `config::validate` (run at the first use and by a test, so a bad file stops the build) checks that the numberings of the note items and sections don't overlap, that a prefix doesn't start with a digit and is a valid file name, that an index fits its digits, that an internal pair is a constant of two digits with a name, and that the names are file names. **A new constant about folder pairs or notes goes in this file**, not in the code.

## User Action (Notes)

**What it is** (`docs/strategies/note-custom-actions.md` is the person's brief; `user_action.rs`, `userAction.ts`, `UserActionButton.tsx`, `UserActionModal.tsx`, `userActionScope.ts`): a web page of the person's own — an `.html` file of any source: the user folder, a picked folder, a Filen account — that Notes launches **in a window of its own**. **The control is two icon buttons and nothing else** (`UserActionButton`): **launch** (⚡) and **close** (⚡ crossed out, on only while the window is open). It is in the header of **every page of Notes**, and the same two sit **beside the "…" clipboard button of every text box** of Notes (`TextFieldMenu`'s `extra`, `UserActionFieldButtons`: one strip; pressing them doesn't take the focus from the box). A right click or a long press on the launcher opens the dialog (`UserActionModal`) that **chooses / changes / resets** the page and **explains** all this; a launch with no page chosen opens that dialog. The dialogs live in one place, `UserActionDialogs`, mounted once (the strip at a box is gone the moment the box loses the focus).

**One reused window per Notes window** (`user_action.rs`). The first launch opens it (`notes_pages::open_child_window`, listed under the Notes tab that launched it — an ordinary `user` window with `origin.role = UserAction`, which is also how the backend finds it again: no registry to lose at a restart; the init answer says `role: 'UserAction'`, `openedBy: 'NotesApp'`); the next launches **bring it to the front** (`window_host::focus`) and tell it again; it is never closed for going out of scope. **Close** (`user_action_close`) closes it and removes its entry. A window shown for another page than the one chosen now is replaced; a *suspended* one (its Notes window was suspended) is reopened. It counts as one of the app's windows — **the limit of ten** (`window_host::MAX_OPEN_WINDOWS`) applies, with its warning box. The Notes window is told whether it is open (`user-action-state` `{ open }`; `user_action_status` at start) so the buttons show it.

**The events** the page may listen to or ignore (`TabLib.userAction` in the samples; `getCurrentWebviewWindow().listen`):
- `user-action-launched` `{ resourceId, context, launchedAt }` — every launch. `resourceId` is the resource identifier of the Notes tab that launched it (`system:notes?…`), `context` says where from: `{ kind: 'button' }`, or for a text box `{ kind: 'input', fieldId, element, type, readOnly }` (`describeField`). **`fieldId` is a stable identifier, distinct for every text box of Notes** — its `data-ua-field` attribute (`notes.search.name`, `notes.notebook.title`, `notes.fileManager.rename`… one on every `<input>`/`<textarea>` of Notes; a box that was never given one reports `"notes.field"`, itself distinct from every real one) — so the page can tell *which* box asked without ever learning *what is in it*: not its label, its selection nor its length. **The bridge for actual text is the app's own clipboard, which the person controls**: they copy the selection to it from the box's “…” menu, the page may read it (`TabLib.internalClipboard`), and what the page puts there they paste back (every text box of Notes has both). The whole context is at most 256 KiB. **A window that was closed is opened first and the event waits for the page's `init_window_tab`** (`user_action::page_ready`, sent 250 ms later so the page can attach its listeners) — so, in effect, a launch's `fieldId` reaches the page as soon as it has completed its init request; a page that missed the event asks `user_action_context` (the last launch it was told of; only the User Action window itself gets one).
- `user-action-scope-left` `{ resourceId, now }` — the person went elsewhere in Notes, so what opened it is out of scope, **once** per launch (`userActionScope.ts`: every place Notes reports — `reportLocation`, `reportView`, `reportNotePlace`, a tab switch — passes the new resource identifier; `o=`, how far down a listing, is not a change). The window stays open: what it does about it (its default state) is the page's own.

**Where the choice is kept** is unchanged. Inside a listed notebook (`notebookContaining`: the notebook whose folder is the place or above it, the innermost when they are nested) it is the **notebook's**, kept in the notebook itself: `{ "Page": { "SourceId", "Path" } }` in `03/[user-action].json`, in the notebook's own internals pair (`03` + `03-[note-book]`, from the config file; made with its `.keep` when the notebook has none — `ensureNotebookInternals`), in the notebook's own source, so it goes with the notebook. Anywhere else — the home page, the notebooks and settings pages, a folder outside every notebook — it is **global**: the Notes app's state, key `notes.userAction` (`data.db`). *Reset* deletes the file (the pair stays) or clears the key. A damaged file says so in the dialog; it is never taken for "nothing chosen". Which place a launch is at is worked out from the resource identifier (`placeOfResource`), so the header buttons and the box buttons agree.

**Why a window and not a frame — the security comparison.** The earlier design showed the page in an iframe of the Notes window, which needed a relay (`postMessage`) so that the framed page could call the backend *as Notes* (a window's identity is the window's, not a frame's), a script injected into every web page, the CSP's `frame-src`, and the guard that refuses IPC from a frame of another origin. None of that is left (`frame-bridge.js`, `userActionRelay.ts`, `FRAME_SCRIPT_PATH`, the `frame-src` directive: removed). The page now has **its own identity** — its own `caller_guid`, its own app state (kept under its own path, so `get_app_state('notes.userAction')` in it is *its* state and Notes' is unreachable), no window state of Notes' — and exactly the rights every window has (nothing above them exists). It can no longer pass itself off as Notes, and Notes' own state can no longer be reached even by a page written to bypass a relay. What it costs: it is one more window (the limit of ten), and it is an OS window the person can see, move and close. (The IPC `Origin` check in `window_host::identify` stays as a general guard.) Exports it asks for are confirmed by the person as everywhere.

**Tested** live on desktop (isolated data folder): the guid, the two buttons in the header, a first launch (a window opened, listed under the Notes tab, the page told — `resourceId` and `kind: 'button'` — after its `init_window_tab`, its init saying `role: 'UserAction'`), its own state (it can't see Notes' setting nor window state), a second launch reusing the window and telling it again, going to the home page telling it the scope was left while the window stayed open, the buttons at a text box (the strip: clipboard menu, launch, close) with only the kind of box in the context, closing (the window gone, the Notes window told) and launching again (a new window, the event after its page started). Also on the Android emulator (isolated, fresh app data): the User Action window as its own task with the page told after it started, its `role`, its own state, **Back suspending it and the next launch opening it again and telling it once its page had started**, the scope-left event, and the ⚡ / ⚡✕ strip at a text box on a phone-width screen (it launched with the box as the context; the strip is placed by `requestAnimationFrame`, so it only appears while the Notes window is the one in front — a backgrounded Android window doesn't run it). Also on the emulator: the themes reaching an open Notes window at once and the `color-scheme` snippet, the refusal of `set_appearance` to Notes, the editor's Undo/Redo buttons, root guids, local branches (the branch bar, a window in a branch, a new window on the main view), and the orange icon and splash accent. **Not exercised live:** the cache options on a real Filen account (only the Rust tests and the fact that a folder of this device shows none), committing/discarding a local branch through the dialogs (unit tests only), and the *New branch…* prompt path of the same-window exception (the rule itself is Node-tested).


## Prompts and windows: the rules of `docs/app-security.md` (`prompt_guard.rs`, `window_host::MAX_OPEN_WINDOWS`)

**Read `docs/app-security.md` before widening what a page or a window may do**, and put a warning about any of its requirements a change touches in the final reply. What it asks, and what implements it:

- **Prompts can't be abused by a page.** Every native box the app shows goes through `prompt_guard` (`window_host::choose` *is* `prompt_guard::ask`; the raw box is `choose_unguarded`, called only from there): **one prompt at a time, in a queue the app itself keeps** — the OS queues nothing, it shows what it is told to on top of each other, so a prompt is handed to it only when the one before has been answered (`Guard::take_turn`: a turn held while a box shows; at most 8 wait, one more is refused; nobody waits more than 60 s; the ones waiting are dropped when the person prevents prompts) —, and a box nobody answers (its window can't be seen) gives up after 120 s so it can't hold the rest back for ever. The OS's own file dialogs a window can ask for (the folder picker, "save as") take their turn too (`os_dialog`).
- **"Prevent this app from showing prompts"** is an **in-memory flag, `false` at every start, that only a full restart of the app clears**, and **every kind of prompt can reach it**: a box with two choices carries it as a third button, *between* the choice and *Cancel* (a box that is closed answers as its last button, so closing is still *Cancel*); and the queue **counts every prompt of any kind** — a one-button box, a three-button link box, an OS file dialog, a page's own dialog — and **five within 30 s make the next one be preceded by a box that asks only that** (*Keep showing prompts* / *Prevent this app from showing prompts* / *Cancel*; a native box has at most three buttons, and this one uses them all), the mark of a page that keeps asking (*Keep showing* starts the count again). While the flag is set nothing is shown: a command that needs a prompt rejects with "Prompts are prevented until the app is restarted." (`choose_save_location`, `pick_folder`, `open_external_site`, an Android export), and the person's own destructive confirmations in Notes answer *no* — that is the price of the option, and the person restarts the app to get them back. Settings shows the state and how many windows are open (`prompt_guard_status`, admin only).
- **A page's own `alert`/`confirm`/`prompt`.** On **Android** they are Kotlin dialogs (`WindowActivity`): they ask the backend first (`nativeDialogBegin`/`nativeDialogEnd`: the same turn and the same flag; a page's thread can't wait, so one that finds the turn taken is cancelled), are **titled "A web page says"** so it is plain that the *page* is talking, and carry the option. On **desktop (Windows, WebView2)** — `page_dialogs_windows.rs`, installed in every secondary window and every external web site's window — three things: (1) Tauri's dialog plugin replaces `window.alert`/`window.confirm` in the main frame of every window with async calls to *its own* commands (boxes outside these rules, and commands no window is granted any more), so `DIALOGS_INIT_SCRIPT` (`code_snippets.rs`, after the plugin's) puts the app's own **`alert_dialog`** and **`confirm_dialog`** in their place — native boxes that say who asks, wait their turn and can prevent prompts; they keep Tauri's shape (`alert` doesn't wait, `confirm` returns a Promise of the answer, `false` when refused); (2) `prompt` — and every dialog a *frame* raises (the plugin's script isn't in frames) — is the webview's own, so the webview's own dialogs are **turned off** (`AreDefaultScriptDialogsEnabled = false`) and the `ScriptDialogOpening` event is answered from Rust: the dialog waits its turn, is counted, never shows once prompts are prevented, and is shown in **a window of the app** (`system/prompt/index.html`, label `prompt-…`, over the window it belongs to; not counted among the ten) that says who talks *as the app knows it* (`"ua/other.html" says`, `A page shown in "Notes" says`, `The web site "host" says` — never a title the page chose), shows the message and the default as plain text (never markup), gives a `prompt` its text box, has *OK* / *Cancel* and the option to prevent prompts, and treats closing it as *Cancel*; (3) `beforeunload` is accepted without asking. **macOS and Linux** webviews are not covered. A window's yes/no questions are `confirm_dialog`'s (`lib/dialogs.ts`'s `confirm` — Notes uses it; **the caller supplies only the question** (at most 1 500 characters): the box's title says who asks — the window's page as the app knows it, `"Notes" (or a page it shows)` for a system app's window, `prompt_guard::asker_label` — and its buttons are always *OK* and *Cancel*), the dialog plugin's `dialog:allow-confirm` being the admin-app's alone (`admin.json`). The bridge no longer offers a page a native dialog of its own (`CsdriveBridge.dialog` and `plugin:dialog|*` are gone on Android).
- **At most 10 secondary windows are open at once** (`MAX_OPEN_WINDOWS`, checked in `window_host::open` — the one place every window opens through, including an external web site's — and so for opening, reopening, a link's *new tab* that needs a window, `open_note_tab` with `new_window`…). At the limit nothing opens: the caller gets "10 windows are open already. Close or suspend one to open another." and the person a native box saying so (in the window that called last, else the admin-app's; `LAST_CALLER` is used only to choose where the warning shows, never to decide anything). A window that is showing is only brought forward, never refused. Suspending or closing one makes room. The external web sites' windows count too (on desktop they are windows like the rest; on Android their activities are counted from `external_sites`).
- **Not done** (the file says "maybe"): suspending every secondary window and freeing the admin-app's memory when the RAM gets critical.

Tested (Rust: the flag, the queue — one at a time, the short queue, dropped when prompts get prevented, the Kotlin turn —, the burst rule, the limit, the origin check; live on desktop and the Android emulator, isolated data): ten windows open and the eleventh refused with the box (Android: counting the external sites), a close making room, suspend/reopen, two windows asking at once with the second waiting for the first's answer, the third button in a two-choice box, *Prevent* setting the flag and every prompt kind refused after it (the confirmations, "save as", the folder picker, an Android export, a page's alert), a restart clearing it, the box before the fifth prompt in a row — one-button boxes counted —, and, on desktop, a page's `alert`/`confirm`/`prompt` (the boxes and the prompt window: who talks, plain-text message, text box and default, OK/Cancel/closing, no markup injection, a page in Notes' frame).

## Branches of a folder of this device (the File Manager's branches)

`files_cache/local_branches.rs` (a child of `files_cache.rs`), `local_branch_commands.rs`, `picked_roots::root_guid_of`, `sources.ts` (`BranchApi`, `localSource(root, branch)`, `filenBranchApi`, `localBranchApi`). The File Manager works on the user folder and on every picked folder in **branches** just as on a Filen account: changes (files written, folders made, deletions, files checked out) stay in the app's own folder until they are **committed** (applied to the real folder, checked against what the folder looks like now — a file that changed underneath is a conflict, refused unless forced) or **discarded**. Reading through a branch shows the real folder with the branch's changes on top. **There is no cache**: the real folder is always the base and is read as it is (through `FsScope::check_in`, so links out of the root and the app's own data are refused here too); the only things kept are the changed files — `files/a/NNN/b/MMM/<the folder's layout>`, inside the root's own folder in `a` — and, in `files/data.db`, `local_branches` and `local_branch_changes` (path, kind, and the version — size and modification time — each change is based on). A folder can't be renamed inside a branch (files can), as for Filen. The branch bar (a select, *New branch…*, the changes, *Commit*, *Discard*, *Check out* on a file, *New branch…* in the editor) is the one Filen has, through one `BranchApi` for both; only the cache's own row (interval, clear) is Filen's.

**Root guids.** Every root — the user folder and each picked folder — has a **guid**, made the first time it is asked for and kept in `data.db` (`root_guids`, keyed by the root's opaque id, so it lasts as long as the id does — a picked folder picked again has the same). It is what the app's own folders for the root are named after: **`local-fs@@<guid>`**, as a Filen account's are `filen@@<email>@@<id>`. It is shown on the root pills' **context menu** (right click, long press — *Show its ids…*: the guid, the root id and the name, each copyable; a Filen account shows its email and user id) in Notes and in the admin-app's Files tab (where it is also a field of the root's details). The layout, each pair with its readable half beside it:

```
files/a/NNN-local-fs@@<guid>/     only a .keep: says whose NNN is
files/a/NNN/b/MMM/…               what branch MMM of the root has changed (MMM-<branch name> beside it)
files/a/NNN/t/…                   thumbnails of the root's files      (kept: they used to be made again each session)
files/a/NNN/tb/MMM/…              thumbnails of the files branch MMM changed (goes with the branch)
```

A folder of this device sits in `a` beside the Filen accounts — the same numbering, told apart only by its part (`local-fs@@…` rather than
`filen@@…`) — so its branches and thumbnails live inside its own `NNN` exactly as an account's do.

Committing or discarding deletes the branch's `b` and `tb` pairs (the root's own pair in `b` goes with its last branch); **forgetting a root deletes its thumbnails but keeps its branches** (with their pending changes; they come back with the folder and its id). A page opened from a branch view is served **as that branch has it**: the address is `/@device/<root id>~<branch>/<path>` (`notes_pages::split_root`; the user folder is `user~<branch>`), so links, the media viewer and *Open as a web app* follow the branch. Unit-tested (`local_branches::tests`: overlay, layout on disk, commit, conflicts, checkouts, versions and rebase, renames, discard, thumbnails) and live on desktop.

**Per window.** The branch a Notes window works in is **the window's**: kept in the window's own state (`get_window_state`/`set_window_state`, `window_state` in `data.db`, deleted with the window's entry and kept while it is suspended), one branch per source (`notes.branches`, `windowBranch.ts`). Changing it in one window doesn't change it in another; **a new window starts on the main view**; every tab of a window shares it (a tab switched to takes the window's branch — the branch in a place's own resource identifier only counts in a scoped explorer). The "last place" the app remembers no longer carries a branch to other windows. **A change of the window's branch is refused when another tab of the same window holds unsaved edits** (drafts, `notes.drafts`) to a file that isn't the same in the two views (the branch it was edited in or the one the window is going to has changed it: `draftsInTheWay`) — the message names the files: save or discard them in that tab first. **The exception**: from the main view to a branch that has just been made (*New branch…*, also from the editor) is never refused: a new branch starts as the main view, so what the other tab has open carries on into it (a draft comes back in whichever branch the window is in now, with a note). Commit and discard follow the same rule (they leave the branch). Unsaved text is never lost by switching tabs: it is kept as a draft when the tab is left and comes back with the editor.

## Appearance: themes and light/dark mode

`src/lib/themes.ts` (the catalog), `src/lib/appearance.ts`, `components/AppearanceSettings.tsx` (Settings → Appearance), `appearance.rs`. **Fifty-eight themes**, each with a light and a dark palette of the css variables `App.css` is written in (`--bg --fg --muted --border --accent --accent-fg --panel-bg --row-hover`, the editor's `--tok-*`, the error and status colours), in families: the app's own (**Ayran orange** — the default, replacing the blue —, Classic blue), **hot desert**, **scorching earth**, **tropical volcanoes**, **sunny autumn**, **rainy autumn**, **misty swamps**, **snow and mist**, **clay, rust and copper** (Red clay, Rust, Copper), **coffee and chocolate** (Arabica coffee, Chocolate), **wood** (Oak, Walnut, Birch), **metals** (Gold, Silver, Platinum, Gun metal), **jewel tones** (Ruby, Magenta, Violet, Velvet, Cherry, Pink), **teal and seaweed** (Teal, Dark teal, Kelp, Nori, Sea lettuce), **green forest** (Deep woods, Pine canopy, Mossy glade), **blue** (Cobalt, Sky, Midnight), **steel blue** (Steel blue, Cold steel, Slate harbour) and **Mars** (Red planet, Olympus dust, Martian dusk). A script checked every palette's contrast (text on the page and on panels ≥ 4.5:1, the text of an accent button ≥ 3.6:1). The mode is **follow the device / light / dark**.

**Who chooses.** **Any window may choose the theme and the mode** (`set_appearance`, granted in `user-apps.json`; the person decided a web app may; `list_themes` says which ids there are — `appearance::THEME_IDS`, which a test keeps equal to the catalog's, in the same order), and it is one choice for the whole app, kept in `global_settings`; an id that isn't a theme is refused. **Only the admin-app sets the rotation** (`set_appearance_rotation`, `admin.json`), and the generic `set_global_setting` refuses every `appearance.` key. `set_appearance` **tells every window** (`appearance-changed` `{ theme, mode, dark, rotation }`, sent to the admin-app and every open window by `window_host::emit_to_all`, never to an external site's window): the system apps apply it at once (`applyAppearance` sets the variables on the root element; `initAppearance` reads it before the first render and listens); **a web app keeps its own colours** but may listen and follow the mode, or choose the theme (`TabLib.appearance.get/set/themes/onChange`). Beside the event, a manual mode reaches every window by itself: on desktop `App::set_theme` puts it on the webviews (their `prefers-color-scheme` follows — verified live in the admin-app, Notes and a web app), and every page gets a `color-scheme` snippet (`code_snippets`, from `appearance::color_scheme_css`), so form controls and scrollbars follow. Android's WebView takes `prefers-color-scheme` from the system, so a web app there learns of a manual mode from the snippet and the event. The launcher icon and the native splash accent are orange too (`src-tauri/icons`, the Android mipmaps, `csdrive_accent`).

**The picker is a dialog.** Settings → Appearance shows only a summary (the theme, the mode, the rotation if it is on) and a *Change…* button that opens the dialog (`AppearanceDialog`): the light/dark buttons, the rotation controls and every theme as a card, grouped by family. It keeps up with a change made anywhere else (`subscribeAppearance`).

**Rotation** (`Rotation` `{ enabled, mode, unit, every }`, `appearance.rotation` in `global_settings`) goes through *all* the themes, in the catalog's order (**ascending**, wrapping), backwards (**descending**) or at random (**random**: never the theme that is showing). It is done by the backend, so it goes on whatever is on screen: a task looks once a second whether the interval has passed (`rotate_if_due`), moves on, saves the theme and tells every window; a restart starts the clock again. **Choosing a theme by hand doesn't stop it and the picker is never disabled**: the rotation goes on from the theme chosen, its interval starting again. The interval is **seconds, minutes, hours or days** and a whole number of them, and **never shorter than 30 seconds** (`MIN_INTERVAL_SECS`; at most a year): every change recolours the whole window, and anything faster is tiring to look at — a few minutes or more is comfortable. The dialog only sends an interval that is valid and says why when it isn't; the backend refuses one anyway. **A change fades**: the colours slide over in about 0.6 s (`.theme-fade` on the root element for 0.7 s, a css transition of the colour properties) — never a flash — and not at all for a person whose device asks for less motion. Rust-tested (`next_theme` both ways and random, the interval, the list against the catalog) and live on desktop: a web app choosing the theme and Notes and the admin-app following, the refusals (a web app or Notes setting the rotation, 29 seconds), the dialog, and a real rotation of 30 seconds that moved on to the next theme by itself while the theme was also chosen by hand.

## Searching and sorting (Notes' File Manager, Note Files Explorer and lists of notes)

**The panel** (*Search and sort…* in the toolbar of a file manager and in the header of a notes page; `SearchPanel.tsx`; the logic is `search.ts`, plain functions and generators, tested in Node with an in-memory source: terms, contents, intervals, sorting, the walk, the pager, notes). **Search by**: **name** (a file's or folder's name, a note's title), **contents** (a file's text, a note's markdown), **last modified** and **created** time stamps and **size** — each an *interval* whose either edge may be left empty (infinity) —, **extension** (a list such as `jpg, png`), and **type** (files / folders). **Every text term can be a regular expression**; a regular expression on the contents is applied **line by line** (`^`/`$` are a line's) or **to the whole contents** (a newline is then the expression's business). A plain term is a case-insensitive substring unless *Match case*. **Depth**: 1 (this folder only) by default, any number of levels, or *No limit* (never deeper than 100, links can make a tree endless). A bad regular expression, an interval that ends before it starts or a wrong depth is refused with a message before anything runs. Enter in a box searches.

**Sorting** (the same panel; effective at once): by name (numbers as numbers), extension, last modified, created or size — *As listed* for files is folders first by name; for notes it is **by index** —, ascending or descending, folders first or not; a value nobody knows (a size, a date) goes last in either direction. Sorting a folder of this device by size or date reads them for the whole folder in **one call** (`fs_read_dir_detailed`: size, modified and created time per entry — `FileSource.listDetailed`; the plain listing has names only, and sizes are read for the page on screen as before); a Filen listing has size and modified time already, no creation time (the panel says so), and a folder of this device may not keep one either.

**Nothing is ever collected in memory.** A search is an *async generator* (`searchFiles`, `searchNotes`) that walks the tree folder by folder — one listing at a time — and yields one hit at a time; a `ResultPager` (`useResultPager`) pulls from it **only as far as the page on screen needs** and keeps the last six pages: the next page continues the walk, a page that was let go is found again by walking again (slower, never more memory), and Stop is just leaving (clearing, changing folder, closing). So a search that finds a million things holds a page or two, whatever the tree. What that costs is the **order**: results are **grouped by folder** — the folder's own hits (sorted as asked) first, then each subfolder's, depth first — and each says which folder it is in (**its ancestors**: the folder's path for files and folders, the titles of the notes above it for a note); a *global* sort of a deep search would need every hit at once, so it is exact within each folder and — at depth 1 — everywhere. The status line says how many were found so far (the total once the whole tree was looked at), how many folders were looked in, and how many files could **not be searched**: contents are read only from files of up to **10 MiB** that are text (no NUL in the first 8 000 characters), so nothing big is pulled into the page for a search, and a Filen file is fetched to the cache only if it is small enough (its size is in the listing).

**Results** replace the listing while a search is on (the folder's pagination and thumbnails give way; `FileSearchResults`, `NoteSearchResults`): a file result shows its name, its folder, the line that matched (`line 3: …`), size and date, opens like a listed file, and *Show it in its folder* leaves the search and lists that folder with the file focused; a note result shows its index, title, the notes above it and the matching line, and offers the web app, the markdown, its children and *show it among the notes next to it*. Changing folder clears the search. **While a list of notes is searched or sorted, everything that reorders, renumbers or converts indexes is off** — the indexes dialog, editing an index (the badge, Shift+F2, the menu item) and *normalize the remaining notes* in Delete: what is in view is not in the order those operations act on (`indexOps`).

Tested live on desktop (isolated data): sorting by size, date (folders first kept), name; searches by name (case), contents at every depth (line and folder shown, the big and the binary file reported), regular expressions line by line and on the whole contents, modified / created / size intervals with an edge left out, extension, a refused expression, a 60-file folder paged 25 at a time (next, next, previous, *Show it in its folder*); notes — sort by title and created, the index tools going off, a title and a contents search at every depth with the parent titles, the list coming back on clear. Tested on the Android emulator too (isolated data): the panel fits the phone's width with no sideways scroll, a contents search at every depth (each result with its folder), sorting by size through the one detailed listing, and the indexes dialog's interval buttons ticking a whole interval and converting it. **Not run live:** a search or sort in a Filen account (the cache's listings feed the same generator; it is covered by unit tests only) and the notes search on the Android emulator (verified on desktop).

## Links planted in `user/`

A directory junction or symlink planted inside `user/` (web apps can't create one — no command does — but the OS user, an unzip or a `git clone` can) is **refused in every direction**: the scope follows it to its real location, so listing, reading or creating files through a link that leads outside is an error (this used to be a gap with the fs plugin, which only resolved paths that already existed). The link itself can still be removed or renamed from inside, and its target is never touched. Tested with real symlinks (unit tests) and a Windows junction (live). On Android the `user` folder is in the app's private storage, so only `adb run-as` on a debug build (or root) can plant a link at all.

## Building and running (the admin-app is the frontend)

`csdrive-webhost-tauriapp` is a standard Tauri project: the frontend (the admin-app: React + Vite + TypeScript) at its root and the Rust backend in `src-tauri/`. `tauri.conf.json` points `frontendDist` at `../dist`, which Tauri embeds into the binary at compile time, so it is in every installer with no separate file and no network access — and there is no way for a user or a web app to swap it out, because it isn't a file in the data folder. (Its saved UI state is keyed by `layout::ADMIN_APP_ID`.)

- **Develop:** `cd csdrive-webhost-tauriapp && npm install && cargo tauri dev` — Vite on `:1420` with hot reload (`devUrl`), the app loading it, `devCsp` in force.
- **Installer:** `cargo tauri build` (runs `npm run build` first, via `beforeBuildCommand`, and turns on Tauri's `custom-protocol` feature so the embedded frontend is used). Android: `cargo tauri android build …` (see "Android").
- **Multi-page build:** `vite.config.ts` builds one html page per app — the admin-app (`index.html`) and each system app (`system/<id>/index.html`, see "System apps and Notes") — into `dist/`; Tauri embeds them all.
- **Run the embedded frontend without an installer:** `npm run build`, then in `src-tauri`: `cargo run --features tauri/custom-protocol`. A plain `cargo run` is Tauri's *dev mode*: it loads `devUrl` and needs Vite running — that is Tauri's normal behaviour.
- `cargo build`/`check`/`test` need `dist/index.html` to exist (Tauri embeds it at compile time); `build.rs` stops with the command to run if it doesn't.

## Web apps opened from Notes

Notes can open an **html or markdown file** as a web app — from the user folder, a folder the person picked, or a Filen account (in a branch too): the **Open as web app** button on such a file in its file list (`FileSource.openAsWebApp`, `open_file_as_web_app`; any window may call it — Notes' pages, and web apps too since the system apps' rights are the web apps' — and it needs a registered tab of the caller to list the page under).
- **Serving** (`notes_pages.rs`; the `csuser://` protocol is now *asynchronous* and percent-decodes the path): besides the user folder, two address spaces — `/@device/<root id>/<path>` (a picked folder, judged by the file scope like any other path) and `/@filen/<user id>/<branch index or ->/<path in the drive>` (through the Filen cache: fetched if not cached or expired, then served from the cache; a file the branch changed is served as the branch has it). A page's **relative references** (a stylesheet, an image, a script, a link — `../` included) resolve against its own address, so they are answered from the same place; an address in the reserved `/@…` space that names nothing valid is refused. Markdown is rendered as described below whatever it is served from. Nothing in these addresses is a real path.
- **The window** (when it is a window of its own — see below for a tab of the Notes window) is an ordinary window entry (`kind` user) whose path is `@device/…` or `@filen/…` (`validate_relative_html_path` lets those through — they are judged when served) and whose `origin` records how it came to be opened (`Origin`: `openedBy` `NotesApp`, `storage`, the path in that storage, the picked folder's root id, the Filen account with the branch's name and index), told to the page in its init response. It has a `parent_tab`: the Notes tab that opened it.
- **Listed under the Notes tab that opened it**, not among the apps (`list_secondary_windows` leaves children out; "close all"/"suspend all" and the shutdown include them): in the admin-app the tab's level of *opened from this tab* lists them together with the external web sites (`TabRecord.openedApps` next to `externalPages`, oldest first, reorderable within the tab; an item shows an app-window icon, the page's own label — its first tab's — and its storage and path, with tags on the window's guid and focus / suspend / reopen / close of the window).
- **Siblings — any web page can open another page, in a window of its own.** `open_related_web_app(path)` (`openRelatedWebApp`; `TabLib.openPage(path)` in the samples): `path` is relative to the page's own — the page its window is showing now, which a link may have changed (`join_relative`: `.`, `..`, query and fragment handled, never above the root; a leading `/` is from the root of its storage), resolved in the same storage (folder, picked folder, drive and branch). A page that was opened from Notes gives the new page **the same parent tab** — it appears beside the page that asked, under the Notes tab; any other page of the user folder gives it a window of the apps list (`secondary_windows::open_page_window`, like one opened from the admin-app). Nothing asks the person: it is a page's own doing — unlike a *link*, which the person is asked about (`link_navigation`). (A note's page can also be a *tab of the Notes window itself* — see "A web page inside a system window"; the window's rights then follow the page it shows.)
- **External web sites** asked for by such a page (or by Notes itself) are listed **directly under that Notes tab** (`open_external_site` uses the caller window's `parent_tab` when it has one; the events still go to the asking page).
- **Lifecycle.** They are children: **suspending the Notes window suspends them** (and, through their own destruction, their external sites); **closing/deleting the Notes tab, its group or its window closes and deletes them** — recursively, with their tabs, tags and external sites (`delete_window_and_tags` → `notes_pages::Closing`).
- **Links.** A click on a link to the web in such a page opens the OS browser (see "No network access…"); a link to another page of the same folder, picked folder or drive is put to the person — open it in this tab, in a new tab, or copy its address (next section).
- Tested live on desktop: a markdown file of a picked folder (its `../theme.css`, an image and a script), a sibling, an external site from such a page listed under the Notes tab, a link click that left the window where it was, suspending and closing the Notes tab; and, on the real Filen account with a scratch folder, an `.md` file whose stylesheet came from the cache, a sibling `.html` using `../style.css`, and the same page opened from a branch (the branch's text, `branch: "selftest-pages"`).

## Markdown web apps

A `.md` / `.markdown` file can be opened as a web app exactly like an `.html` file (Files tab → "Open as web app", the User Apps tab) — `validate_relative_html_path` accepts it. Unlike an html file, whose bytes are served as they are, the `csuser://` handler (`serve_file` in `lib.rs`) turns a markdown file into html on the Rust side first (`markdown.rs`, `pulldown-cmark` with tables, footnotes, strikethrough and task lists) and sends the resulting **whole page**: a charset, a viewport, a small default stylesheet (light/dark), the document, and a script at the end.
- **Raw html passes through untouched** (markdown is html-compatible), so `<style>` and `<script>` tags in the file work — under the same policy as every web app (inline script and style allowed, no `eval`, no network).
- **Relative references** (a `<link rel=stylesheet href>`, `@import`, `<script src>`, an image, a link to another `.md`) are ordinary requests for a path relative to the page's address, answered by the same handler from the same folder — for html pages as much as markdown ones. (An address outside the app — a CDN — is refused by the CSP: an app needing network goes through a backend command.) Following a link to another `.md` shows that page in the same window.
- **The page is a tab** like a hand-written app: the last script registers it (`init_window_tab`), applies the code snippets, and labels it with the document's title (its first heading, else the file name) and path, and sets its resource id to the page's path plus query — so what the window manager shows follows the page. A tab switched to while it is showing starts the page over.
- Tested: title, table, an inline `<style>` and `<script>`, a relative stylesheet, a relative link, the tab label and the init response, on desktop.

## Deploying apps

`csdrive-webhost-userapps/<name>/index.html` is source for a small standalone app that the admin-app's Files tab can *deploy*: pick "Deploy apps…" from the toolbar (available in any folder browsable by the file manager, not just the root), choose an app from the list, confirm or edit the destination folder name (defaults to `<name>`, the folder it sits under in `csdrive-webhost-userapps/`; rejected if a file/folder of that name already exists at the current location), and the admin-app creates that folder under the current location and writes the app's `index.html` into it — using the same generic `mkdirRoot`/`writeRootTextFile` root-relative file operations as the rest of the Files tab, not a separate Rust-side "deploy" command.

Each deployable app's `index.html` is embedded into the Tauri binary at compile time (`csdrive-webhost-tauriapp/src-tauri/src/deployable_apps.rs`, via `include_str!`) and exposed to the frontend via two read-only commands, `list_deployable_apps` and `get_deployable_app_html`. Adding a new deployable app means: create `csdrive-webhost-userapps/<name>/index.html`, add an entry to `deployable_apps::REGISTRY` (plus an `include_str!` for its `index.html`), and `cargo build`.

**`example-toolbar`** is the first one (`csdrive-webhost-userapps/example-toolbar/index.html`): a page that binds itself to its tab and draws two buttons of its own — *Suspend this window* and *Close this tab* — calling straight back into `suspend_secondary_window`/`close_tab` (the window's own guid is its Tauri window label, no round trip needed — see CLAUDE.md's "No real paths for web apps" for why that's exposed but not much else is). The file is split into two clearly marked halves: a **library** `<script>` (generic — binds the tab, listens for `tab-navigate`, exposes `suspendThisWindow`/`closeThisTab`; meant to be copied into any page unchanged) and an **example** half (this demo's own toolbar markup and the two lines wiring its buttons to the library; meant to be replaced). It is also what the Help tab's "Example: a page's own toolbar" section shows (fetched live via `get_deployable_app_html`, so the deployed file and the displayed one can never drift apart) — see "Help tab" below.

## Help tab

**`components/HelpTab.tsx`** (`src/App.tsx`'s eighth tab, after Settings) is the admin-app's own onboarding page for someone writing a web app of their own: an overview of what a web app is and how to get one running (write files under the Files tab, *Open as web app*, or deploy the sample below), the **essentials** snippet (the whole of `init_window_tab` + `tab-navigate` binding — the minimum any page needs), the **`example-toolbar`** sample above rendered read-only (fetched live, so it's always the exact file on disk), and an **API reference**: every command granted to a web app, as it is actually called from a page — `window.__TAURI__.core.invoke(...)`, never the admin-app's own internal `src/lib/*.ts` wrapper functions (camelCase helpers like `readDir`/`suspendSecondaryWindow`), since those aren't shipped to a web app's page at all and would mislead someone copying them.

**The reference is data, not prose** — `src/lib/apiReference.ts`, an array of categories (Files, SQLite, Windows & tabs, Tags, External web sites, Filen.io direct, the Filen cache, local branches, the app's clipboard, appearance, app state & global settings, picked folders, exporting, dialogs, code snippets, Notes-only helpers), each a list of `{ call, returns, summary, note? }` covering every `allow-*` permission in `user-apps.json` (~130 of them) with the call written exactly as a page would type it (byte payloads shown going through `invoke(cmd, bytes, { headers: {...} })`, matching `fs_write_file`/`filen_write_file`/`save_to_device`'s real shape, not a JSON field). `HelpTab.tsx` renders it as a searchable table (`CodeBlock`/`.api-table`; the search box filters by call, summary and note text, per category, hiding an empty category). **This file is the one place the web-app-facing API is documented for someone outside the codebase — keep it in sync with `user-apps.json` and the commands it grants**: adding, removing or changing a command that's part of the web-app grant means updating (or adding/removing) its entry here in the same change, or the reference silently goes stale. Nothing checks the two against each other automatically.

`CodeBlock.tsx` (a small, reusable, read-only counterpart to `CodeEditor` — for *showing* code, not editing it) renders a snippet through the existing `highlight()`/`Language` machinery (`lib/highlight.ts`, the same one behind the file editors), so the Help tab's code gets the same syntax colours for free, plus a copy-to-OS-clipboard button (`IconButton` pinned to the block's corner, `position: sticky`).

Verified live (isolated data folder, desktop): the tab renders with no console/backend errors; the essentials snippet and the fetched `example-toolbar` source both show as syntax-highlighted, copyable code blocks; the search box narrows both the categories shown and their rows (typing "suspend" left exactly the window/tab and external-site entries that mention it); deploying `example-toolbar` through Files → *Deploy apps…* wrote the real file to disk (read back and byte-compared); opening it as a web app, its status line picked up a real `tabGuid` from `init_window_tab`, *Close this tab* suspended the window and kept its entry (`isOpen: false`, matching `close_tab`'s documented behavior for the tab an open window is showing), and — after `reopen_secondary_window` — *Suspend this window* did the same via `suspend_secondary_window` directly.

## The top bar

The iframe-based top bar of the earlier design is gone for good (see "Why a window and not a frame" under "User Action" for the same reasoning applied there); this is the plain-DOM replacement, deliberately partial: **only Notes' own pages get one** — not a user web app, and not even a note opened as a web app (a genuinely different page, served over `csuser`, outside Notes' own React tree). A user web app that wants the same thing draws it itself, the same way `example-toolbar` does (see "Deploying apps").

**`NotesTopBar.tsx`**, mounted once in `NotesRoot.tsx` (above `{view}`, so every place of Notes — home, notebooks, the notes list, an editor, the file manager, settings — gets it uniformly without each page adding its own copy): **Suspend this window**, **Close this tab**, and its own **×** to hide itself. **Hidden by default** and **local to the window's current page-load** (plain `useState`, not persisted — suspending and reopening a window starts hidden again, same as a fresh window would), shown only when asked for: its own × hides it, and the `show-top-bar` event (below) shows it.

**`show_top_bar`** (`secondary_windows.rs`, admin-only — granted in `admin.json`, not `user-apps.json`; the person triggers this from the admin-app itself, never a page on its own behalf) sends the `show-top-bar` event to **one open window** (`guid`) or **every open window at once** (no `guid`) via the existing `window_host::emit_if_open`/`emit_to_all`. Two triggers, both in the admin-app:
- **A tab's own row**, in the System/User Apps tabs (`AppsTab.tsx`'s `TabRow`) — a `PanelTop`-icon *Show its top bar* action, offered only while `tab.showing` (the same gate `reload_tab`'s button uses — no open window means nothing to tell), calling `showTopBar(tab.windowGuid)` directly (no backend lookup needed: `TabRecord.windowGuid` is already loaded).
- **Settings → "Top bar" → "Show the top bar for every open window"** — one button, `showTopBar()` with no argument, for when a header is hidden somewhere and there's no reason to hunt down which tab.

**`src/lib/secondaryWindows.ts`** adds `showTopBar(guid?)` (the command wrapper) and `onShowTopBar(callback)` (`getCurrentWebviewWindow().listen('show-top-bar', …)`, the same "this window only, not the global `listen`" rule as `onTabNavigate`) — the second is what a page that draws its own header actually needs; the first is admin-app-only in practice (it's not even granted to a plain web app).

**`example-toolbar`** (see "Deploying apps") is the reference implementation of "a user app adding its own header of this kind": its toolbar is `hidden` by default, its library exposes `onShowTopBar(handler)` wired to reveal it, and it has its own × (`btn-hide`) to hide it again — the exact same shape as `NotesTopBar`, minus the window-management difference that Notes' pages always have a tab to close while an arbitrary web app might not need one. The Help tab's API reference documents the event (`getCurrentWebviewWindow().listen('show-top-bar', …)` under "Windows & tabs") since a page needs to know to listen for it even though it can never trigger it on itself.

Verified live (isolated data folder, desktop): a Notes window's bar starts hidden; Settings' global button revealed it in that window; its own × hid it again; the System Apps tab's per-tab *Show its top bar* revealed it again (drilled down to the tab's own row to confirm the button is there and gated correctly); from the bar, *Suspend this window* closed the window and kept its entry (`isOpen: false`); reopening, then re-showing the bar via a direct `show_top_bar` call, *Close this tab* suspended the window the same way (the tab it closed was the window's only one). Separately, `example-toolbar` deployed and opened as a web app: its toolbar started hidden, `show_top_bar` targeted at its window guid revealed it, and its own × hid it again.

## Tags

Tags (`window_tags` table) are not specific to windows: `guid` is any opaque id — a window, tab group, tab, or, in the Files tab, a file-manager root (keyed `root:<rootId>`, e.g. `root:user`; picked roots are remembered and keyed by their opaque id, so their tags persist with them; forgetting a root leaves its tags in the database, and they reappear if the same folder is picked again). **Everywhere tags appear they must be editable and sortable**, which is why every place renders them through the one shared `components/Tags.tsx` `TagList` component rather than its own markup: click a badge to edit its text/colors, drag badges (or use the arrows in the edit dialog) to reorder, × to remove. Backend commands: `list_tags`, `add_window_tag`, `update_window_tag`, `reorder_window_tags`, `remove_window_tag`; order is the `sort_order` column (new tags go last). Any new place that shows tags should use `TagList` too.

**A row of tags is shown only when the record has at least one tag** (`TagList` renders nothing for an empty list unless it is given `showWhenEmpty`), so a listing isn't padded with empty tag rows. The first tag is added from the record's **details popup** (below), which is the one place that passes `showWhenEmpty` — the "add tag" button — so every record that can have tags has a details popup, and a new listing with tags gets one too.

**Root tags** are the tags of a guid derived from a root (`src/lib/rootTags.ts`): `root:<rootId>` for a folder on this device (`root:user`, or `root:<id>` for a picked one — an opaque id, never a path), `root:filen:<userId>` for a Filen account. Every place that shows the root shows the same tags — the Files tab's root switcher and the **tab items in the System Apps tab**: a Notes tab (its resource id names its source, `rootOfTab`) shows two captioned lines, **Root** (the root's tags) and **Tab** (its own), so the two sets can't be mistaken for each other. Both are editable from there. A tab that shows no root keeps the single tag line. **Group by root** (System Apps tab only, at the tabs level; saved as `systemAppsTab.groupByRoot`): the tabs of the group are shown under a header per root (its name, and its tags when it has any; a button for its details) — a root's tabs are together, the tabs with no root last under "Tabs that show no root" — and the root is no longer repeated on each tab. Sorting by hand is off while grouped.

## Seeding demo data for the User Apps tab

`csdrive-webhost-tauriapp/src-tauri/examples/seed_demo_data.rs` populates the real `data.db` with demo data for the 9 sample apps in `user/qwer/` (`index1.html`-`index9.html`), for stress-testing the User Apps tab's nested windows/tab-groups/tabs UI at scale. To run it after a reset (or any time):

```
cd csdrive-webhost-tauriapp/src-tauri
cargo run --example seed_demo_data
```

It requires `data.db` to already exist and `user/qwer/index1.html`..`index9.html` to already be deployed (run the app once, and copy `sample-apps/qwer/` into the real `user/qwer/` folder, before running the script). It finds the real data folder itself the same way the app does, including a relocated custom data folder. Layout it creates: one `secondary_windows` entry per app, except `index1.html` which gets 10; the first of those 10 windows gets 10 `tab_groups`; the first of those groups gets 100 `tabs`. Safe to re-run — every row it creates is tagged `seeded:qwer-demo-data`, and each run starts by deleting only rows carrying that tag before recreating them, so it never touches any other window/tab/tag you created yourself.
