# CsDrive WebHost

Inside `csdrive-webhost-tauriapp` let's create a tauri app without the frontend app: just the backend and the user will provide their own frontend by writing a html file called `index.html` and will sit inside a folder called `user` located directly inside the machine app data folder for this app. So the app's backend will simply read the contents of this file and serve it to the webview component instead of the usual webapp that tauri provides out of the box. If there is no `index.html` file under `user` under the machine app data folder for this app, the app should create a sample one at that location, and that sample should contain simple instructions as to how this app functions and a link to open the folder location in the system's default file manager or the sample html file itself in the system's default text editor.

Now let's go inside folder csdrive-webhost-userapps/admin-app and there create a react app that builds all its bundle in only 1 file and, when copying the bundled index.html file at the %APPDATA%\com.ayran.csdrive-webhost-tauriapp\user\index.html location, it will be able to "talk" to the backend of our app just like a regular tauri frontend app communicates with the tauri backend. The actual app will act like a file manager for the %APPDATA%\com.ayran.csdrive-webhost-tauriapp\user root folder, along with a file manager for filen.io cloud storage provider (with possibility to allow multiple users to be connected), and a sqlite management studio that performs all types of operations upon sqlite database files from inside the %APPDATA%\com.ayran.csdrive-webhost-tauriapp\user folder.

## Browser storage naming convention

Every user app under `csdrive-webhost-userapps/` is served from the same `csuser://localhost` origin, so IndexedDB databases and Web Storage (localStorage/sessionStorage) are shared browser-wide across all of them unless deliberately namespaced. Rule: any IndexedDB database name or localStorage/sessionStorage key that an app creates for its own persistence must be prefixed with `[<html-file-relative-path>]` — the relative path (from the `user` folder) of the html file the page was served from, read from `location.pathname` rather than a hardcoded app name. E.g. the admin-app's own state database is `[index.html]app-state` when deployed at `user/index.html`, and any key it writes is `[index.html]<key>`. Deriving the prefix from the URL rather than a hardcoded name means the same app keeps separate state when copied to more than one location on disk, and there's nothing to hardcode per app. This applies to every app in `csdrive-webhost-userapps/`, present and future. It does not apply to databases/keys a user explicitly creates through a generic inspection tool (e.g. admin-app's Storage tab) — those are arbitrary by design and named by the user, not the app. If an existing differently-prefixed database is hard to rename in place (IndexedDB has no rename operation — it requires copying all data into a new database and deleting the old one), it's fine to just delete the old one rather than migrate it, unless it holds data too valuable to lose.
