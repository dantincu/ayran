## About huge directory listings

How do we handle cases when the directory listing itself is too big for our app's internal memory resources? What would such a situation look like? Say the average entry name is 20 characters long and contains mostly ASCII characters with ocasional unicodes. How many entries in one folder will become problematic? How about when the average entry name is 100 characters long and most names are chinese names or mostly non ASCII unicodes?

Is there a way to retrieve just a list of ids for entries of a folder? Then if we only have the ids, we can retrieve metadata in chunks.

## New features

1. Everywhere we have tags: only show the row of tags if at least one tag has been added. When no tag has been added (or all of them were removed) there should be an option to add tags from the details popup modal for that record (all our listings should have a details popup model for each record).

2. In the system apps tab page add an option to group records by root. In this mode the root will no longer be visible under each record.

3. Let's optimize our listings for mobile and other slim width situations even further: make the row of action buttons fall bellow the rows of text and tags if the width of the window is slim.

4. All our text editors (and single line textboxes) should have 3 options:
   - select paragraphs (or select all for single line textboxes): will select the paragraph(s) that is partially selected (or where our text cursor was the last time the editor was focused) entirely while discarding trailing and leading whitespaces (trailing whitespaces after the last paragraph and leading whitespaces before the first paragraph).
   - copy to internal clipboard (our app's own internal clipboard mechanism that will only be able to hold text - that is a string - that will be available globally - that is accross all secondary windows and the main window / admin app) will copy the text from the current text selection to internal clipboard
   - paste from internal clipboard will replace the text from the current text selection with the text from the internal clipboard
   - copy to clipboard - will copy the text from the current text selection to OS clipboard
   - paste from clipboard will replace the text from the current text selection with the text from the OS clipboard

5. All our file managers will give the option for seeing the details of a folder or file in a popup modal and there the path should be visible along with options to copy to OS clipboard / internal clipboard. Same rule applies to Filen explorers (and besides the path, there should also be an option to view/unhide the item id and copy it to OS clipboard / internal clipboard). For folder listings there should be away to update the path (paste it from OS clipboard or internal clipboard in a popup modal textbox to navigate to the new path).


## Follow-up 1:

### How we handle anchors

I remember that we disabled anchor-based navigation in our web apps. How do we do that? We don't inject javascript in our web apps, do we? Anyway, we should still have a way to respond to internal navigation requests (call pushState or pressing on an anchor whose url contains only a path - with optional query).  We should show an OS prompt showing the file path and resource type (it might be a note path - if the a folder path is followed by the question mark and there's a query key called "note", that's a note url, not the path to a folder or file). In that prompt we should ask the user if to open the link in the same tab, in a new tab (in the same tab group), copy url to OS clipboard / internal clipboard, or cancel. Also, we mentioned above that inside a folder listing we can change the path of the navigated folder. If the new path is a file path (we detect that afterwards) redirect the user to the appropriate view. If it's a note url (contains the "note" query key) redirect to note. Viceversa, when visiting a note, we should offer the same "change the note path directly" where the same redirects should apply. Lastly, about relative/absolute paths in these links: relative paths will be relative to the current file that has been opened as a web app (html or markdown or a note in the note module). Absolute paths will be relative to the notebook root folder when in a note view (web app representing the markdown of a note) or relative to the root of Filen account root of its corresponding markdown or html web app.

### Note files explorer

Let's add a file explorer scoped to the note files (files present in the "01" short name folder). the file explorer should function similar to the file manager we with which we started developing this Notes app (let's call that simply File Manager, because we'll call this one Note Files Explorer). It should be its own page, separated from that of the note or notes children (the list of a note's children should again be a separate page). From there every file or folder should have the option to "Open in File Manager" which will navigate to that file or folder in the File Manager. Even notes themselves will have this option. Opening a note in the File Manager will navigate to the note's short name folder (and see its contents).

### Viewing media files

Let's add options for viewing image and video files and listening to audio files. For these cases we should give the user the option to enter the Full Screen Mode. Any menu that will still be opened in the image viewer should dissapear when pressing on the image once and reappear when pressing on the image again. Pressing play on the video player will hide the menu there. Pressing the video again will bring back the menu and after a reasonable interval it will dissapear again if the user doesn't pause it. For videos and audios, besides the draggable progress, let's add left and right buttons for rewind 10 seconds and forward 10 seconds and trigger those actions on pointerdown event. Let's add these media features both for the File Manager and for the Note Files Explorer. And of course make sure that large files like videos are never fully loaded in memory. Finally, let's add a "View thumbnails" mode in directory listings (both File Manager and Note Files Explorer). For creating thumbnails, let's create 2 new folders inside the "files" folder in our app data folder called "t" and "tb" similar to how we created the "c" and "b" folders: one holding the thumbnails for the main branch, and one for holding the thumbnails for individual branches. Now when committing / discarding a branch, you have 2 places where you have to delete a pair of folders. Also, about the image viewer: it needs to be zoomable and draggable. It first opens by showing the whole image (it fits in the viewport entirely) then the user can zoom in a drag it. When it's zoomed in enough, the visible part of the image should take up all the viewport.
