# CsDrive WebHost

Inside `csdrive-webhost-tauriapp`, the Tauri app's main window always shows the admin-app (see below) — its own bundle lives in an `admin` folder directly inside the machine app data folder, a sibling of a `user` folder meant purely for arbitrary user-authored content. The user can still write their own `.html` files anywhere under `user` (e.g. `user/index.html`, `user/myapp/index.html`), but those are only ever opened as *secondary* windows (via the admin-app's own Files tab or Apps tab — "Open as web app"/"add a new window entry") — placing one at `user/index.html` does not make it the main window's content the way it originally did before the admin-app took over that role permanently.

## Folder layout

**Where all of this lives is defined in exactly one place: `csdrive-webhost-tauriapp/src-tauri/src/layout.rs`** — `DEFAULT_DATA_FOLDER` (the default data folder; `%APPDATA%\com.ayran.csdrive-webhost-tauriapp` today), `ADMIN_BUNDLE_PATH` (the admin bundle file, relative to it; `admin/dist/index.html` today), and the `admin`/`user` folder names. Nothing else hardcodes them: the backend, the keychain entry names (the last component of `DEFAULT_DATA_FOLDER`), the `seed_demo_data` example (`#[path]`-includes that file) and the admin-app (which asks the backend for the user folder via `get_user_folder`) all derive from it. To run the app **completely isolated** from real data (e.g. for tests), set `DEFAULT_DATA_FOLDER` to a scratch absolute path (`r"C:\Temp\csdrive-isolated-test"`) and rebuild: the run gets its own data folder, database, admin bundle and keychain entries, and can't reach the real one. (The WebView2 browser-storage profile is still shared, as it is keyed by the app identifier; the app keeps no state there.) Remember to set it back.

Both folders sit directly under the data folder (the default above, or wherever Settings' "Change data folder" points):
- `admin/dist/index.html` — the admin-app's own single-file bundle, served to the main window via the `csadmin://` custom protocol (which serves `admin/dist/` as its root, so the URL is `csadmin://localhost/index.html`). The app makes this file byte-identical to the copy embedded in the binary (see "Bundling the admin-app into the installer" below) **on every start**: that installs it on a fresh install or after "Delete app data", updates it when the app is upgraded, and undoes any tampering (the admin window is the privileged one, so nothing may persist changes to its code). Anything else found in its folder is deleted. So during development, rebuild the Tauri app after building the admin-app; a bundle copied in by hand is replaced at startup. `data.db` sits next to `dist/`, not inside it, so it can never be served.
- `admin/data.db` — this app's own SQLite database (secondary windows/tab groups/tabs/tags, the generic `app_state` table, etc. — see `secondary_windows::init_db`).
- `user/` — arbitrary user-authored `.html`/`.js`/`.css`/etc., served to secondary windows via the `csuser://` custom protocol. The backend never reads anything from here except in response to the admin-app explicitly asking to open/list something in it.

Both folders are created unconditionally at startup (`main.rs`'s `.setup()`), regardless of which files inside them do or don't already exist.

Now let's go inside folder csdrive-webhost-admin-reactapp and there create a react app that builds all its bundle in only 1 file and, when installed by the backend as the admin bundle file (`ADMIN_BUNDLE_PATH` in `layout.rs`), it will be able to "talk" to the backend of our app just like a regular tauri frontend app communicates with the tauri backend. The actual app will act like a file manager for the %APPDATA%\com.ayran.csdrive-webhost-tauriapp\user root folder, along with a file manager for filen.io cloud storage provider (with possibility to allow multiple users to be connected), and a sqlite management studio that performs all types of operations upon sqlite database files from inside the %APPDATA%\com.ayran.csdrive-webhost-tauriapp\user folder.

`csdrive-webhost-userapps/` holds source for small standalone apps that can be *deployed* — copied as a new folder of `.html`/etc. content into the `user` root — via the admin-app's own Files tab (see "Deploying apps" below), as opposed to `csdrive-webhost-admin-reactapp`, which is the one privileged app that's always built into the installer and always occupies the main window.

## App state storage: data.db, not browser storage

An app's own UI-state persistence (active tab, last-browsed folder, collapsed groups, ...) belongs in the app-owned `data.db` (see the generic `app_state` table in `secondary_windows`'s crate — `get_app_state`/`set_app_state`), *not* IndexedDB or Web Storage. Reason: the data folder can be relocated (see the Settings tab / `data_location`) precisely so testing can switch between profiles, but browser storage lives in the fixed WebView2 profile rather than wherever the data folder currently points — so it never actually switched with the rest of the app's data. Rows are namespaced by an `app_id` — the relative path of the html file the window was opened from (from `user/` for a secondary-window app, or just `index.html` for the admin-app itself, served from `admin/`) — which the **backend** works out from the calling window itself (`get_app_state`/`set_app_state` take no app id; any one a caller sends is ignored), so an app can only ever reach its own state — so the same app keeps separate state when copied to more than one location on disk, and multiple apps sharing this one database never collide. This applies to every app in `csdrive-webhost-userapps/`, present and future; the admin-app's own `src/lib/appState.ts` is the reference implementation. It does not apply to browser storage a user explicitly creates through a generic inspection tool (e.g. admin-app's Storage tab) — those are arbitrary by design and named by the user, not the app, and have nothing to do with an app's own settings. If an app used browser storage for this before switching to `data.db`, it's fine to just abandon the old IndexedDB database/keys rather than migrate their contents, unless they hold data too valuable to lose.

**The admin-app writes nothing to browser storage.** Verified against a pristine WebView2 profile after using every tab: `localStorage`, `sessionStorage`, IndexedDB, cookies, the Cache API, service workers and OPFS are all empty, and the profile holds no data for the admin origin beyond the engine's own bookkeeping (navigation history, site-interaction and preference records, which any webview keeps for any page). The only code that touches these APIs is the Storage tab, on the user's explicit action. Keep it that way: new admin-app state goes through `appState.ts` (`data.db`).

## What the backend exposes to web apps (capabilities)

User-provided web apps run in secondary windows (label = the window guid); the admin-app is the window labelled `main`. Tauri capabilities are per window label, so `src-tauri/capabilities/` has two files, and **every new command must be listed in `build.rs` and granted in exactly one of them**:

- `user-apps.json` (`windows: ["*"]`, so it covers the admin window too) — everything a web app is meant to be able to do: files under the user folder and folders the user picks with a native dialog (the fs plugin's *runtime* scope: at startup we allow the user folder, and native dialogs add whatever the person picks; the fs permissions in the capability are granted bare, with no static path scope. A web app finds the user folder with `get_user_folder`, then passes absolute paths to the fs commands); SQLite on `.db` files in those same places (below); Filen.io file operations on the accounts the user has connected (below); managing app windows, tab groups, tabs and their tags; reporting itself as a tab (`init_window_tab` etc.); and its own `get_app_state`/`set_app_state`. Deliberately **not** granted: system/OS/app/window introspection (`core:default` — app version, monitors, paths…), event emitting, connecting/disconnecting Filen accounts.
- `admin.json` (`windows: ["main"]`) — extras only the admin-app gets: `filen_login`/`filen_logout` (the only place a Filen password is ever typed), data-folder relocation and "Delete app data", the bundled-app deploy commands, and path resolution.

**SQLite** is our own (`sqlite_db.rs`), not `tauri-plugin-sql` (which opens any path on disk): `sqlite_load` takes an absolute path or one relative to the user folder, resolves symlinks/`..`, and refuses anything outside the fs scope; the returned handle only works in the window that loaded it and is closed when the window closes. SQL can itself name files, so every connection also runs under an authorizer: `ATTACH` is allowed only for in-memory/temp databases or absolute paths inside the same scope, `PRAGMA temp_store_directory`/`data_store_directory` and `load_extension` are denied, and `VACUUM INTO` (which SQLite doesn't route through the authorizer) is refused by a token scan of the statement. (Without these, `ATTACH DATABASE '…/admin/data.db'` read straight past the path check.) `sqlite_execute(db, query, values)` → `{rowsAffected, lastInsertId}`; `sqlite_select(db, query, values)` → array of `{column: value}` (BLOBs as byte arrays).

**Filen.io lives entirely in Rust** (`src/filen/`: `crypto.rs`, `api.rs`, `ops.rs`, `mod.rs`; ported from the Ayran Notes app's Rust client). No credential ever reaches a webview: the connected-accounts list (user id + email) is a table in `data.db`, and each account's session (API key, master keys, name-hash key) is one OS-keychain entry, `filen-session:<userId>`. Web apps identify an account by its numeric `userId` and call, with Filen paths (`/`, `/Folder/file.txt`): `filen_list_accounts` → `[{userId, email}]`, `filen_readdir` → `[{name, isDirectory, size, mtimeMs}]`, `filen_stat`, `filen_read_file` (returns an `ArrayBuffer`), `filen_write_file` (creates or replaces; the bytes are the raw request body, the account and path go in headers: `invoke('filen_write_file', bytes, { headers: { userId: String(id), path: encodeURIComponent(path) } })`), `filen_mkdir` (recursive), `filen_rm` (to trash), `filen_rename` (also moves). `src/lib/filen.ts` is the reference wrapper. Crypto is tested against vectors from Filen's own JS SDK (`@filen/sdk`); accounts on auth version 3 salt name hashes with an HMAC key derived from the RSA private key (fetched at login). "Delete app data" / clearing a custom data folder also deletes the keychain sessions.

The `csadmin://` protocol serves `admin/dist/` only, and only to the `main` window. The sample dashboard's CPU/memory numbers are just `Math.random()` — the backend has never exposed system info.

## No network access for any window (CSP)

Every page we serve (`csuser://` and `csadmin://`, so user web apps and the admin-app alike) carries a `Content-Security-Policy` header (`CONTENT_SECURITY_POLICY` in `main.rs`) under which a script can reach only its own origin's files, `data:`/`blob:` URLs, and the IPC channel to this backend (`ipc:` / `http://ipc.localhost`) — `fetch`, XHR, WebSocket, EventSource, beacons, external scripts/styles/images/fonts/frames and form posts to anything else are all blocked, and `default-src` is `'none'` so anything not listed is too. Inline scripts/styles remain allowed (the admin bundle is one inlined file); `eval` is not. CSP doesn't cover navigating the window itself, so `lock_down_navigation` (`on_navigation` + denying `window.open`) confines every window to our two origins — applied to the main window and every secondary window, so any new window builder must use it. A web app that needs anything from outside talks to it through a backend command (as Filen does), never directly. To add an exception, edit the constant and its test (which asserts the policy names no external host).

## Known limitation: links planted in `user/`

The fs plugin's scope check resolves links for paths that exist but not for ones that don't yet, so a directory junction/symlink that someone plants *inside* `user/` (web apps can't create one — no command does — but the OS user, an unzip, or a `git clone` can) lets a web app **create new files** (never overwrite or read existing ones) under the link's target. Nothing in `admin/` is affected in practice: `admin/dist/index.html` exists, so it's protected, and extra files in `dist/` are deleted at startup. Avoid linking folders into `user/` that you don't want web apps writing into.

## Bundling the admin-app into the installer

`csdrive-webhost-tauriapp/src-tauri/src/main.rs` embeds `csdrive-webhost-admin-reactapp/dist/index.html` at Rust compile time via `include_str!`, as `ADMIN_APP_INDEX_HTML` — so it's baked into the compiled binary (and thus every installer built from it, with no separate resource file or internet access needed at runtime) and is what gets written out as `admin/dist/index.html` at every start. This means **the admin-app must be built before the Tauri app** — `cd csdrive-webhost-admin-reactapp && npm run build` — or `cargo build`/`cargo tauri build` fails fast with a clear message from `build.rs` pointing at that command, rather than a cryptic `include_str!` error. `build.rs` also declares `cargo:rerun-if-changed` on that file, so rebuilding the admin-app and then the Tauri app picks up the new bundle (this crate wouldn't otherwise notice changes in a sibling package). The same pattern is used for each deployable app under `csdrive-webhost-userapps/` — see "Deploying apps" below.

## Deploying apps

`csdrive-webhost-userapps/<name>/index.html` (none exist yet — the registry is currently empty, and the Deploy dialog says so) is source for a small standalone app that the admin-app's Files tab can *deploy*: pick "Deploy apps…" from the toolbar (available in any folder browsable by the file manager, not just the root), choose an app from the list, confirm or edit the destination folder name (defaults to `<name>`, the folder it sits under in `csdrive-webhost-userapps/`; rejected if a file/folder of that name already exists at the current location), and the admin-app creates that folder under the current location and writes the app's `index.html` into it — using the same generic `mkdirRoot`/`writeRootTextFile` root-relative file operations as the rest of the Files tab, not a separate Rust-side "deploy" command.

Each deployable app's `index.html` is embedded into the Tauri binary at compile time (`csdrive-webhost-tauriapp/src-tauri/src/deployable_apps.rs`, via `include_str!`, the same pattern as the admin-app's own bundle — see "Bundling the admin-app into the installer" above) and exposed to the frontend via two read-only commands, `list_deployable_apps` and `get_deployable_app_html`. Adding a new deployable app means: create `csdrive-webhost-userapps/<name>/index.html` (or point at a built bundle the same way the admin-app's `dist/index.html` is), add an entry to `deployable_apps::REGISTRY` (plus an `include_str!` for its `index.html`), and `cargo build`.

## Tags

Tags (`window_tags` table) are not specific to windows: `guid` is any opaque id — a window, tab group, tab, or, in the Files tab, a file-manager root (keyed `root:<rootId>`, e.g. `root:user`; custom `ext:` roots are session-only, so their tags stay in the database and reappear if the same folder is added again). **Everywhere tags appear they must be editable and sortable**, which is why every place renders them through the one shared `components/Tags.tsx` `TagList` component rather than its own markup: click a badge to edit its text/colors, drag badges (or use the arrows in the edit dialog) to reorder, × to remove. Backend commands: `list_tags`, `add_window_tag`, `update_window_tag`, `reorder_window_tags`, `remove_window_tag`; order is the `sort_order` column (new tags go last). Any new place that shows tags should use `TagList` too.

## Seeding demo data for the Apps tab

`csdrive-webhost-tauriapp/src-tauri/examples/seed_demo_data.rs` populates the real `data.db` with demo data for the 9 sample apps in `user/qwer/` (`index1.html`-`index9.html`), for stress-testing the Apps tab's nested windows/tab-groups/tabs UI at scale. To run it after a reset (or any time):

```
cd csdrive-webhost-tauriapp/src-tauri
cargo run --example seed_demo_data
```

It requires `data.db` to already exist and `user/qwer/index1.html`..`index9.html` to already be deployed (run the app once, and copy `sample-apps/qwer/` into the real `user/qwer/` folder, before running the script). It finds the real data folder itself the same way the app does, including a relocated custom data folder. Layout it creates: one `secondary_windows` entry per app, except `index1.html` which gets 10; the first of those 10 windows gets 10 `tab_groups`; the first of those groups gets 100 `tabs`. Safe to re-run — every row it creates is tagged `seeded:qwer-demo-data`, and each run starts by deleting only rows carrying that tag before recreating them, so it never touches any other window/tab/tag you created yourself.
