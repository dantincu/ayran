# Ayran Piano Player

I want to create a piano player react web app that displays all of the piano keys to the screen but instead of them being rectangular, I want them to be square, in order for all 88 keys to fit on the screens of all tablets (and even most phones). The size of square keys (the length of its sides) should be configurable as an integer number anywhere between 40 and 80 that represents the length of its sides in px. The default value should be as big as possible while allowing all 88 keys to fit the browser window but not fall outside the 40-80 px range for the size of squares. The button sizes should adjust accordingly when the window resizes only if the default size is being applied (that is no custom size has been specified). To specify a custom size, let the user add sizes by showing a numeric text box and save and cancel buttons inside a popup window. Also allow the user to delete existing sizes from the settings page.

The user should be able to customize the look of this app by providing a custom css file whose contents are to be applied as a custom theme: so users will be able to define custom themes by associating a name (and a unique id generated by the app) with a custom css stylesheet uploaded by the user. Here too the user should be able to delete existing themes and also edit them (by reuploading the css stylesheet).

The sounds that are played when keys are pressed should also be configurable: in the settings page the user should have a list of sound-sets each containing contents of mp3 files for each of the 88 notes. So when adding a new soundset the app should use the FileSystemApi to ask the user for a folder where it can find those 88 mp3 files and load them to indexed db. Each file should be named like `note-<note-code>.mp3`; files that don't have names of this format should be ignored. If not all 88 notes can be matched with a file found in the user's folder, a default sound should be played for that note instead and that sound should be generated from javascript from a single frequency corresponding to the note pressed. That's actually how all the note should sound at the beginning, before the user has created the first sound-set. Here too the user should be able to delete sound-sets and edit them either by uploading files for each note individually or by changing (or updating) the folder where the app should upload the mp3 files from.

Finally, there should be a record button somewhere on the main screen that will record the sound produced by the app. After the user presses the "start recording" button, there will be 2 buttons: a pause recording and a stop recording. When the user presses the stop recording button, a popup window should open where the user is asked for the name of the mp3 file to be generated and downloaded by the browser. There should be a cancel button in that window. Besides generating the mp3 file the app should also store in indexdb the blueprint for generating that mp3 file in the form of an array of objects, each such object having 3 properties: the moment the key was pressed (touchstart or pointerdown event), the note that was played and the interval in milliseconds that the note lasted (notes should last a minimum amount before fading out with a configurable interval of milliseconds, the default of which should be 100ms; if the note lasts longer, it should still fade out when the touchend or pointerup event fires; if the mp3 finishes playing before the touchend or pointerup event fires, there should no longer be a fade out and it should only played once for every key stroke). Generating and storing this array in indexeddb should be done as soon as the user presses the stop recording button. It should first be stored as the current recording and then, if the user saves the recording to mp3, it should appear in the list of saved songs. Otherwise, there should still be a button for saving the recording until the user presses the record button again, when the current recording should be erased (if it has not been saved).
