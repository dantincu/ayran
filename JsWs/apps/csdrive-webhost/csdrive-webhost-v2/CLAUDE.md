# CsDrive WebHost

Inside `csdrive-webhost-tauriapp`, the Tauri app's main window always shows the admin-app (see below) — its own bundle lives in an `admin` folder directly inside the machine app data folder, a sibling of a `user` folder meant purely for arbitrary user-authored content. The user can still write their own `.html` files anywhere under `user` (e.g. `user/index.html`, `user/myapp/index.html`), but those are only ever opened as *secondary* windows (via the admin-app's own Files tab or Windows tab — "Open as web app"/"add a new window entry") — placing one at `user/index.html` does not make it the main window's content the way it originally did before the admin-app took over that role permanently.

## Folder layout

Both folders sit directly under the machine app data folder (`%APPDATA%\com.ayran.csdrive-webhost-tauriapp` by default, or wherever Settings' "Change data folder" points):
- `admin/index.html` — the admin-app's own single-file bundle, served to the main window via the `csadmin://` custom protocol. Created automatically (from the copy embedded in the binary — see "Bundling the admin-app into the installer" below) whenever missing, so a fresh install or a folder wiped via Settings' "Delete app data" always comes back up with a working UI.
- `admin/data.db` — this app's own SQLite database (secondary windows/tab groups/tabs/tags, the generic `app_state` table, etc. — see `secondary_windows::init_db`).
- `user/` — arbitrary user-authored `.html`/`.js`/`.css`/etc., served to secondary windows via the `csuser://` custom protocol. The backend never reads anything from here except in response to the admin-app explicitly asking to open/list something in it.

Both folders are created unconditionally at startup (`main.rs`'s `.setup()`), regardless of which files inside them do or don't already exist.

Now let's go inside folder csdrive-webhost-admin-reactapp and there create a react app that builds all its bundle in only 1 file and, when copying the bundled index.html file at the %APPDATA%\com.ayran.csdrive-webhost-tauriapp\admin\index.html location, it will be able to "talk" to the backend of our app just like a regular tauri frontend app communicates with the tauri backend. The actual app will act like a file manager for the %APPDATA%\com.ayran.csdrive-webhost-tauriapp\user root folder, along with a file manager for filen.io cloud storage provider (with possibility to allow multiple users to be connected), and a sqlite management studio that performs all types of operations upon sqlite database files from inside the %APPDATA%\com.ayran.csdrive-webhost-tauriapp\user folder.

`csdrive-webhost-userapps/` holds source for small standalone apps that can be *deployed* — copied as a new folder of `.html`/etc. content into the `user` root — via the admin-app's own Files tab (see "Deploying apps" below), as opposed to `csdrive-webhost-admin-reactapp`, which is the one privileged app that's always built into the installer and always occupies the main window.

## App state storage: data.db, not browser storage

An app's own UI-state persistence (active tab, last-browsed folder, collapsed groups, ...) belongs in the app-owned `data.db` (see the generic `app_state` table in `secondary_windows`'s crate — `get_app_state`/`set_app_state`), *not* IndexedDB or Web Storage. Reason: the data folder can be relocated (see the Settings tab / `data_location`) precisely so testing can switch between profiles, but browser storage lives in the fixed WebView2 profile rather than wherever the data folder currently points — so it never actually switched with the rest of the app's data. Rows are namespaced by an `appId` — the relative path of the html file the page was served from (from `user/` for a secondary-window app, or just `index.html` for the admin-app itself, served from `admin/`), read from `location.pathname` rather than a hardcoded name — so the same app keeps separate state when copied to more than one location on disk, and multiple apps sharing this one database never collide. This applies to every app in `csdrive-webhost-userapps/`, present and future; the admin-app's own `src/lib/appState.ts` is the reference implementation. It does not apply to browser storage a user explicitly creates through a generic inspection tool (e.g. admin-app's Storage tab) — those are arbitrary by design and named by the user, not the app, and have nothing to do with an app's own settings. If an app used browser storage for this before switching to `data.db`, it's fine to just abandon the old IndexedDB database/keys rather than migrate their contents, unless they hold data too valuable to lose.

## Bundling the admin-app into the installer

`csdrive-webhost-tauriapp/src-tauri/src/main.rs` embeds `csdrive-webhost-admin-reactapp/dist/index.html` at Rust compile time via `include_str!`, as `ADMIN_APP_INDEX_HTML` — so it's baked into the compiled binary (and thus every installer built from it, with no separate resource file or internet access needed at runtime) and is what gets written out as the default `admin/index.html` whenever that file is missing. This means **the admin-app must be built before the Tauri app** — `cd csdrive-webhost-admin-reactapp && npm run build` — or `cargo build`/`cargo tauri build` fails fast with a clear message from `build.rs` pointing at that command, rather than a cryptic `include_str!` error. `build.rs` also declares `cargo:rerun-if-changed` on that file, so rebuilding the admin-app and then the Tauri app picks up the new bundle (this crate wouldn't otherwise notice changes in a sibling package). The same pattern is used for each deployable app under `csdrive-webhost-userapps/` — see "Deploying apps" below.

## Deploying apps

`csdrive-webhost-userapps/<name>/index.html` (currently `notes` and `files`, each a placeholder `<h1>` page) is source for a small standalone app that the admin-app's Files tab can *deploy*: pick "Deploy apps…" from the toolbar (available in any folder browsable by the file manager, not just the root), choose an app from the list, confirm or edit the destination folder name (defaults to `<name>`, the folder it sits under in `csdrive-webhost-userapps/`; rejected if a file/folder of that name already exists at the current location), and the admin-app creates that folder under the current location and writes the app's `index.html` into it — using the same generic `mkdirRoot`/`writeRootTextFile` root-relative file operations as the rest of the Files tab, not a separate Rust-side "deploy" command.

Each deployable app's `index.html` is embedded into the Tauri binary at compile time (`csdrive-webhost-tauriapp/src-tauri/src/deployable_apps.rs`, via `include_str!`, the same pattern as the admin-app's own bundle — see "Bundling the admin-app into the installer" above) and exposed to the frontend via two read-only commands, `list_deployable_apps` and `get_deployable_app_html`. Adding a new deployable app means: create `csdrive-webhost-userapps/<name>/index.html` (or point at a built bundle the same way the admin-app's `dist/index.html` is), add an entry to `deployable_apps::registry()`, and `cargo build`.

## Seeding demo data for the Windows tab

`csdrive-webhost-tauriapp/src-tauri/examples/seed_demo_data.rs` populates the real `data.db` with demo data for the 9 sample apps in `user/qwer/` (`index1.html`-`index9.html`), for stress-testing the Windows tab's nested windows/tab-groups/tabs UI at scale. To run it after a reset (or any time):

```
cd csdrive-webhost-tauriapp/src-tauri
cargo run --example seed_demo_data
```

It requires `data.db` to already exist and `user/qwer/index1.html`..`index9.html` to already be deployed (run the app once, and copy `sample-apps/qwer/` into the real `user/qwer/` folder, before running the script). It finds the real data folder itself the same way the app does, including a relocated custom data folder. Layout it creates: one `secondary_windows` entry per app, except `index1.html` which gets 10; the first of those 10 windows gets 10 `tab_groups`; the first of those groups gets 100 `tabs`. Safe to re-run — every row it creates is tagged `seeded:qwer-demo-data`, and each run starts by deleting only rows carrying that tag before recreating them, so it never touches any other window/tab/tag you created yourself.
