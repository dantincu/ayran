# CsDrive WebHost

The Tauri app in `csdrive-webhost-tauriapp` has exactly one frontend, the **admin-app** — a React/Vite project living at the root of that same folder (`src/`, `index.html`, `package.json`, `vite.config.ts`, with the Rust backend in `src-tauri/`). It is the Tauri app's own compiled-in frontend (`frontendDist` in `src-tauri/tauri.conf.json`, embedded into the binary and so into every installer), it always occupies the main window, and nothing — neither the user nor a web app — can replace it. It manages a machine-wide *data folder* (below) holding an `admin` folder for the app's own database and secrets, a `user` folder meant purely for arbitrary user-authored content, and a `files` folder for the Notes app's cache. The user can write their own `.html` files anywhere under `user` (e.g. `user/index.html`, `user/myapp/index.html`), but those are only ever opened as *secondary* windows (via the admin-app's own Files tab or User Apps tab — "Open as web app"/"add a new window entry"). Besides those *user apps* the app ships **system apps** — more pages of the same compiled-in frontend, **Notes** being the first — which are opened the same way and managed in the System Apps tab (see "System apps and Notes" below).

## Folder layout

**Where all of this lives is defined in exactly one place: `csdrive-webhost-tauriapp/src-tauri/src/layout.rs`** — `DEFAULT_DATA_FOLDER` (the default data folder; `%APPDATA%\com.ayran.csdrive-webhost-tauriapp` today), the `admin`/`user`/`files` folder names (and inside `files`: `a`, `b`, `c` and `data.db`, see "The Filen cache"), `FILEN_SESSIONS_FILE`, and `ADMIN_APP_ID` (the admin-app's key for its saved UI state). Nothing else hardcodes them: the backend, the keychain entry names (the last component of `DEFAULT_DATA_FOLDER`), the `seed_demo_data` example (`#[path]`-includes that file) and the admin-app (which asks the backend for the user folder via `get_user_folder`) all derive from it. To run the app **completely isolated** from real data (e.g. for tests), set `DEFAULT_DATA_FOLDER` to a scratch absolute path (`r"C:\Temp\csdrive-isolated-test"`) and rebuild: the run gets its own data folder, database and keychain entries, and can't reach the real one. (The WebView2 browser-storage profile is still shared, as it is keyed by the app identifier; the app keeps no state there.) Remember to set it back.

The folders sit directly under the data folder (the default above, or wherever Settings' "Change data folder" points):
- `admin/` — the app's own files, none of which is ever served to a window: `data.db` (this app's SQLite database — secondary windows/tab groups/tabs/tags, the generic `app_state` table, the `global_settings` table, remembered device folders, connected Filen accounts; see `secondary_windows::init_db`) and `filen-sessions.enc` (below). The admin-app itself is **not** in the data folder: it's the Tauri app's compiled-in frontend, so there is no `admin/dist` and nothing on disk to tamper with.
- `user/` — arbitrary user-authored `.html`/`.js`/`.css`/etc., served to secondary windows via the `csuser://` custom protocol. The backend never reads anything from here except in response to the admin-app explicitly asking to open/list something in it.

- `files/` — the Notes app's cache of Filen accounts and their branches (`a/`, `b/`, `c/` and its own `data.db`; see "The Filen cache"). Like `admin/`, it is a **protected path** (`data_location::protected_paths`): no file command or SQLite call can reach it, even inside a picked folder — only the `filen_cache_*` commands read and write it.

The three folders are created unconditionally at startup (`lib.rs`'s `.setup()`), regardless of which files inside them do or don't already exist. Whenever a folder needs a short name a program can rely on and a long one a person can read, the app uses **folder pairs** (`folder_pairs.rs`, strategy in `docs/strategies/folder-pairs-strategy.md`; `docs/strategies/` is where the app's strategies are written down, one `.md` each).

**The admin-app** is a React app (TypeScript, built by Vite into `dist/`, embedded by Tauri — see "Building and running"). It is a file manager for the `user` folder and any folders the user picks, a file manager for connected filen.io accounts (any number of them), a SQLite management studio for `.db` files in those places, the manager of the apps' windows/tabs/tags (the System Apps tab, first and the default, and the User Apps tab — the same component, `AppsTab kind="system" | "user"`), a browser-storage inspector, and the settings.

`csdrive-webhost-userapps/` holds source for small standalone apps that can be *deployed* — copied as a new folder of `.html`/etc. content into the `user` root — via the admin-app's own Files tab (see "Deploying apps" below), as opposed to the admin-app, which is the one privileged app: always built into the installer and always the main window.

## App state storage: data.db, not browser storage

An app's own UI-state persistence (active tab, last-browsed folder, collapsed groups, ...) belongs in the app-owned `data.db` (see the generic `app_state` table in `secondary_windows`'s crate — `get_app_state`/`set_app_state`), *not* IndexedDB or Web Storage. Reason: the data folder can be relocated (see the Settings tab / `data_location`) precisely so testing can switch between profiles, but browser storage lives in the fixed WebView2 profile rather than wherever the data folder currently points — so it never actually switched with the rest of the app's data. Rows are namespaced by an `app_id` — the relative path of the html file the window was opened from (from `user/`, for a secondary-window app; `system:<id>`, e.g. `system:notes`, for a system app; `layout::ADMIN_APP_ID` for the admin-app itself) — which the **backend** works out from the calling window itself (`get_app_state`/`set_app_state` take no app id; any one a caller sends is ignored), so an app can only ever reach its own state — so the same app keeps separate state when copied to more than one location on disk, and multiple apps sharing this one database never collide. This applies to every app in `csdrive-webhost-userapps/`, present and future; the admin-app's own `src/lib/appState.ts` is the reference implementation. It does not apply to browser storage a user explicitly creates through a generic inspection tool (e.g. admin-app's Storage tab) — those are arbitrary by design and named by the user, not the app, and have nothing to do with an app's own settings. If an app used browser storage for this before switching to `data.db`, it's fine to just abandon the old IndexedDB database/keys rather than migrate their contents, unless they hold data too valuable to lose.

**Global settings** are the exception to "an app only reaches its own state": the `global_settings` table (`get_global_setting`/`set_global_setting`, granted to every window) holds the few preferences that are deliberately shared by every app — today the list **page size** (`listPageSize`, `src/lib/listPageSize.ts`), so paging 10 rows a page in the Files tab does so in Notes too. Keep it to genuinely global preferences.

**The admin-app writes nothing to browser storage.** Verified against a pristine WebView2 profile after using every tab: `localStorage`, `sessionStorage`, IndexedDB, cookies, the Cache API, service workers and OPFS are all empty, and the profile holds no data for the admin origin beyond the engine's own bookkeeping (navigation history, site-interaction and preference records, which any webview keeps for any page). The only code that touches these APIs is the Storage tab, on the user's explicit action. Keep it that way: new admin-app state goes through `appState.ts` (`data.db`).

## What the backend exposes to web apps (capabilities)

User-provided web apps run in secondary windows (label = the window guid); the admin-app is the window labelled `main`. Tauri capabilities are per window label, so `src-tauri/capabilities/` has three files, and **every new command must be listed in `build.rs` and granted in exactly one of them**:

- `user-apps.json` (`windows: ["*"]`, so it covers the admin window too) — everything a web app is meant to be able to do: files under the user folder and folders the user picks with a native folder picker, through **our own file commands** (`fs_read_dir`, `fs_stat`, `fs_exists`, `fs_read_file`, `fs_write_file`, `fs_mkdir`, `fs_remove`, `fs_rename`), which obey our own scope (see "The file scope" below) — the fs plugin isn't used at all. A web app finds the user folder with `get_user_folder` and the picked folders with `list_picked_roots`, then passes absolute paths to the fs commands; `pick_folder` asks the person to choose one. SQLite on `.db` files in those same places (below); Filen.io file operations on the accounts the user has connected (below); managing app windows, tab groups, tabs and their tags; reporting itself as a tab (`init_window_tab` etc.); its own `get_app_state`/`set_app_state`; the shared `get_global_setting`/`set_global_setting`; `list_system_apps`; and the Filen *cache* commands (`filen_cache_*`, below). System apps are pages of the admin-app's own frontend but are **not** the admin-app: they run in ordinary secondary windows and get exactly this file's grants (plus the one below). Deliberately **not** granted: system/OS/app/window introspection (`core:default` — app version, monitors, paths…), event emitting, connecting/disconnecting Filen accounts.
- `admin.json` (`windows: ["main"]`) — extras only the admin-app gets: `filen_login`/`filen_logout` (the only place a Filen password is ever typed), data-folder relocation and "Delete app data", and the bundled-app deploy commands. The capability files can't tell the admin-app from a web app on Android (see "Android" below), so those commands also call `window_host::require_admin`, which is what actually enforces it there — and on desktop too. (Path joining is our own `joinPath` in `src/lib/localFs.ts`; Tauri's `path.join` permission isn't granted to anything.)
- `system-apps.json` (`windows: ["*"]`) — `save_to_device`/`choose_save_location`, exporting a file (the desktop "save as" dialog, or Android's Downloads folder), for the admin-app **and the system apps** (Notes exports Filen files with it). It is granted to every window only because the capability files can't tell a system app from a user app — both are secondary windows on desktop, one shared webview on Android — so the commands call `window_host::require_trusted` (admin page **or** system page, read from the page's address), which refuses a user web app. Verified live: a user web app gets "Only the admin-app and the system apps can do that."; Notes gets past the check.

**SQLite** is our own (`sqlite_db.rs`), not `tauri-plugin-sql` (which opens any path on disk): `sqlite_load` takes an absolute path or one relative to the user folder, resolves symlinks/`..`, and refuses anything outside the file scope; the returned handle only works in the window that loaded it and is closed when the window closes. SQL can itself name files, so every connection also runs under an authorizer: `ATTACH` is allowed only for in-memory/temp databases or absolute paths inside the same scope, `PRAGMA temp_store_directory`/`data_store_directory` and `load_extension` are denied, and `VACUUM INTO` (which SQLite doesn't route through the authorizer) is refused by a token scan of the statement. (Without these, `ATTACH DATABASE '…/admin/data.db'` read straight past the path check.) `sqlite_execute(db, query, values)` → `{rowsAffected, lastInsertId}`; `sqlite_select(db, query, values)` → array of `{column: value}` (BLOBs as byte arrays).

**Filen.io lives entirely in Rust** (`src/filen/`: `crypto.rs`, `api.rs`, `ops.rs`, `mod.rs`; ported from the Ayran Notes app's Rust client). No credential ever reaches a webview: the connected-accounts list (user id + email) is a table in `data.db`, and every account's session (API key, master keys, name-hash key; the RSA private key is used once at login and never kept) is in one encrypted file in the data folder, `layout::FILEN_SESSIONS_FILE` (`admin/filen-sessions.enc`), so it travels with `data.db` when the folder is relocated and is gone when the folder is wiped. Web apps identify an account by its numeric `userId` and call, with Filen paths (`/`, `/Folder/file.txt`): `filen_list_accounts` → `[{userId, email}]`, `filen_readdir` → `[{name, isDirectory, size, mtimeMs}]`, `filen_stat`, `filen_read_file` (returns an `ArrayBuffer`), `filen_write_file` (creates or replaces; the bytes are the raw request body, the account and path go in headers: `invoke('filen_write_file', bytes, { headers: { userId: String(id), path: encodeURIComponent(path) } })`), `filen_mkdir` (recursive), `filen_rm` (to trash), `filen_rename` (also moves). `src/lib/filen.ts` is the reference wrapper. Crypto is tested against vectors from Filen's own JS SDK (`@filen/sdk`); accounts on auth version 3 salt name hashes with an HMAC key derived from the RSA private key (fetched at login). 

The backend exposes no system information (CPU, memory, OS, paths…) to any window.

## Secrets at rest (`secure_store.rs`)

One random 32-byte key, generated the first time it's needed and kept in the platform key store (desktop: the OS keychain via the `keyring` crate — Credential Manager / Keychain / Secret Service, entry `app-encryption-key` under the service name from `layout::keychain_service()`; Android: the Android Keystore, see "Android"), encrypts everything sensitive that we persist. The sensitive data itself lives in ordinary AES-256-GCM files (`nonce(12) || ciphertext+tag`, written atomically) inside the data folder: the Filen sessions file (above) and the small pointer file (`data-location.enc`, in the *default* data folder) that records a relocated data folder. The key store therefore only ever holds 32 bytes (no entry-size limits), and the only platform-specific code is `platform::resolve_key`. **iOS is not implemented yet** — `resolve_key` returns an error there (rather than keeping the key unprotected); implement it with the iOS Keychain and nothing else in the module changes. (`keyring` is a desktop-only dependency in `Cargo.toml` for that reason.) New secrets should be added the same way: a JSON structure written with `secure_store::write_json`.

## The file scope (`fs_scope.rs`, `fs_commands.rs`)

Which files the file commands and SQLite may touch is decided in one place, our own `FsScope` — replacing the fs plugin's, whose runtime scope can only grow (paths can be allowed or forbidden, never taken back), so "forget this folder" couldn't revoke anything until a restart. Ours: the **user folder** is always allowed and can't be revoked; **picked folders** are allowed until revoked, at once, and can be picked again in the same session; the app's own **`admin/` folder** (database, Filen sessions), the Notes cache in **`files/`** and the data-location pointer file are **never** reachable, even inside a picked folder (so picking a folder that contains them exposes nothing). Every path is resolved before it is judged: it must be absolute, `..` is refused, symlinks/junctions are followed to the real location (also for a file that doesn't exist yet, by resolving its nearest existing folder — which closes the plugin's old gap where a link planted in `user/` let a web app *create* files outside), a dangling link is refused, and the command then operates on the resolved path. Removing or renaming an entry acts on the entry itself (a link pointing outside is removed, never its target). Picking is done in Rust (`pick_folder`: the OS folder dialog on desktop, `FolderPicker.kt` on Android), which adds the folder to the scope and remembers it in `data.db` (`picked_roots`); `allow_saved` allows the remembered ones again at every start, and `remove_picked_root` revokes one. The frontend's `src/lib/fs.ts` wraps the commands with the shapes the plugin had. The dialog plugin remains only for message boxes (`confirm`) and Rust-side dialogs (folder picking, "save as", the data-folder chooser); a web app can't get a path out of a dialog and use it, because only `pick_folder` adds to the scope. Tested with real symlinks/junctions, `..`, protected paths and revocation (Rust unit tests), and live on desktop and the Android emulator.

## No network access for any window (CSP)

The policy is written once, in `src-tauri/tauri.conf.json` (`app.security.csp`; `devCsp` is the same plus the Vite dev server's websocket). Tauri applies it to the admin-app's own pages (adding hashes for the inline scripts in `index.html`), and `respond` in `lib.rs` sends the very same string, read back from the config, as a header with every `csuser://` page — so user web apps and the admin-app alike are under it. A script can reach only its own origin's files, `data:`/`blob:` URLs, and the IPC channel to this backend (`ipc:` / `http://ipc.localhost`, depending on the OS): `fetch`, XHR, WebSocket, EventSource, beacons, external scripts/styles/images/fonts/frames and form posts to anything else are all blocked, and `default-src` is `'none'` so anything not listed is too. Inline scripts/styles remain allowed (`style-src-attr` is spelled out because Tauri's script/style hashes make `'unsafe-inline'` inert for `style-src`, which would otherwise break inline `style=""` attributes); `eval` is not. CSP doesn't cover navigating the window itself, so `lock_down_navigation` (`on_navigation` + denying `window.open`) confines every window to our own origins — web app windows to `csuser` only, the main window also to the admin-app's (`tauri://localhost`; `http://tauri.localhost` on Windows and Android; the dev server under `tauri dev`) — applied to the main window and every secondary window, so any new window builder must use it. A web app that needs anything from outside talks to it through a backend command (as Filen does), never directly. To add an exception, edit `tauri.conf.json` and the test that reads it (which asserts the policy names no external host).

## Android (and every other platform)

**Standing rule: everything in this app — what exists and everything added from now on — must work on Android as well as on desktop.** Check each new feature on the emulator, and keep desktop-only code behind `#[cfg(desktop)]` with a real Android counterpart (or an honest "not available on this platform" that the UI hides).

**Building.** The crate is a lib (`src/lib.rs`, `pub fn run()`, `#[cfg_attr(mobile, tauri::mobile_entry_point)]`) plus a two-line `src/main.rs`. The Android Studio project is `src-tauri/gen/android` — generated by `cargo tauri android init` but **committed and hand-edited**: `MainActivity.kt` (edge-to-edge + the safe-area bridge), `SecureKey.kt` and `DeviceFiles.kt` (Kotlin helpers Rust calls over JNI). From `csdrive-webhost-tauriapp`: `cargo tauri android build --debug --target x86_64 --apk` (it runs `npm run build` itself; needs `ANDROID_HOME`, `NDK_HOME`, and **JDK 17** as `JAVA_HOME` — Android Studio's bundled JDK 25 breaks Gradle). Testing without a device: an emulator (`quick_notes_pixel_34`, headless), `adb install -r` (keeps app data), and Chrome DevTools remote debugging (`adb forward tcp:9222 localabstract:webview_devtools_remote_<pid>`, then the CDP HTTP/WebSocket API) to run `window.__TAURI__.core.invoke(...)` in the pages. In Git Bash set `MSYS_NO_PATHCONV=1` for adb. The emulator's app data is its own — nothing touches the desktop data.

**Windows on Android** (`window_host.rs`, the one place that knows the difference). Desktop opens real OS windows; a phone has one webview, so the "windows" model becomes *navigating that webview* between the admin-app and web apps. A window entry (`secondary_windows` row) is **open** while its page is showing, **suspended** when the user leaves it (Back, another app, the admin-app: entry and tabs are kept, `reopen_secondary_window` navigates back), and deleted by an explicit close. Opening app B from app A suspends A. `activate_tab` navigates to the tab's window. All the commands (`open_new_/reopen_/suspend_/close_/close_all_/suspend_all_secondary_window(s)`, `focus_`, `activate_tab`) keep their signatures on both platforms. Which window a call comes from is worked out from the page's *address* plus `HostState.active`, never from the window label (there's only `main`): `window_host::caller_guid`/`caller_key` give web apps and system apps their identity (app state, SQLite handles), `require_admin` gates admin-only commands, `require_trusted` those the system apps may use too. A system app is navigated to like any web app — its page `tauri://localhost/system/<id>/index.html` (`system_apps::page_url`, converted by `navigation_url`) is a different page of the same origin as the admin-app, which is why admin identity is decided by the path.

**Custom protocols.** On Windows and Android the scheme `x://localhost/...` is served as `http://x.localhost/...`. `WebviewUrl::CustomProtocol` converts it when a window is built, but `navigate()` does not — always go through `window_host::navigation_url` (Android showed `chrome-error://chromewebdata` without it). Custom-protocol pages count as local, so capabilities can't scope by URL (hence `require_admin`). The admin-app is served by Tauri itself, not by us: `http://tauri.localhost` on Android (`tauri://localhost` elsewhere), recognised by `window_host::is_admin_url`.

**System bars and the safe area.** Tauri apps fill the whole screen on Android, under the status bar and the gesture/navigation bar. Android's WebView reports `env(safe-area-inset-bottom)` as 0, so `MainActivity.kt` measures the real insets (system bars + display cutout, in CSS px) and publishes them as CSS variables `--csdrive-safe-area-inset-top/right/bottom/left` on `<html>` (an initialization script on every page reads them from the `CsdriveSafeArea` JS interface and `__csdriveApplySafeArea` keeps them current). They are 0 when the bars are hidden, so a full-screen mode simply gets the whole screen — **the trigger for a full-screen mode isn't built yet**. The css that consumes them (`SAFE_AREA_CSS` in `code_snippets.rs`: pad `<html>` by the four variables, `height:100%`) reaches every page not because each web app copies it but as a **code snippet**: `init_window_tab`'s response has a `codeSnippets` list of `{ code, type }` entries (`type`: `css`, `html` or `javascript`; today one css entry), and `get_code_snippets` returns the same list. **Web apps must apply the snippets they receive** (`sample-apps/qwer/_tab-lib.js` does — `TabLib.applySnippets`, also called automatically for `openTab`'s response and on load; the admin-app does it before its first render, `src/lib/codeSnippets.ts`). Anything platform-specific that every page needs should be added to that list rather than asked of each web app. Layout inside the admin-app therefore uses `height:100%`, not `100vh`.

**Loading indicator.** Nothing web-side can be shown until a page exists, so startup has two spinners. (1) From the first paint: `index.html` contains a spinner inside `#root` (styles `.app-splash` in `App.css`, same markup as `components/Splash.tsx`, which `App` shows while the saved tab loads). (2) Android only, for everything before that: `MainActivity.showSplash` puts a native spinner (`SplashSpinnerView`, app background/accent colours, light and dark) over the whole window from `onCreate`, on the decor view because wry later installs the WebView with `setContentView`, which would discard anything added to the content area; the window theme's `windowBackground`/splash background (`csdrive_bg`, `res/values{,-night}`) avoids a white flash before it. The admin-app removes it (`hideNativeSplash` in `src/lib/nativeSplash.ts`, via the `CsdriveSplash` JS interface) when its first screen is ready; it also removes itself after 10 s so a page that fails to load is never hidden behind it (`adb logcat -s CsdriveSplash` shows when it appeared and how long it stayed). The spinner draws itself from the clock rather than using Material's indicator or any `Animator`, because Android's "remove animations" / animator-scale-0 setting turns those into a static icon or nothing at all. On desktop the blank stretch is native startup (release build, warm profile: ~0.45 s for WebView2 before any page can exist, then ~0.13 s to first paint; a debug build adds ~0.4 s of unoptimised runtime start), which page content can't cover. The database setup is ~30 ms and not a factor.

**Secrets.** `secure_store` on Android keeps the 32-byte key wrapped by an Android Keystore key (`SecureKey.kt`; the wrapped blob is in the private `csdrive_secure_store` preferences); Rust reaches it through `android_jni.rs` (`on_activity`, `helper_class` — the activity's class loader is required to find our own classes). Verified: same key across restarts.

**Admin-app differences** (`src/lib/platform.ts`: `isMobile` from the user agent). No custom data folder (`pick_and_set_custom_data_folder` errors; `DataFolderInfo.canRelocate` is false and Settings hides it). "Add root folder" uses our own picker — see "Picked folders" below. Uploads use the webview's own `<input type="file">` chooser (`pickFilesFromDevice`) because the native dialog returns content URIs the fs scope can't cover. Exports go through `save_to_device` (`device_files.rs` + `DeviceFiles.kt`): admin-app and system apps only (`require_trusted`), the bytes are the request body and the name a header, stored in the public Downloads folder via MediaStore (no permission needed on Android 10+; a name collision gets ` (1)`); on desktop `exportToDevice` first asks the backend for a location (`choose_save_location` shows the native "save as" dialog and returns a one-time token) and only then reads the data and sends it with the token (`save_to_device` writes it there — so a big Filen file isn't fetched before the person has chosen where it goes). Byte payloads to the backend go through `invokeWithBytes` (see "Sending bytes to the backend"). "Delete app data" ends the process on mobile (`app.restart()` can't relaunch there) — the next launch starts fresh.

**Picked folders (the Files tab's "Add root folder"; see also "The file scope").** On desktop this is the OS folder dialog. Android has no folder-picking dialog that hands back a real path (the official dialog plugin has none on mobile, and the system one gives `content://` URIs that path-based code can't use), so the app ships its own, `FolderPicker.kt`: a dialog that browses the real filesystem — storage volumes (internal storage, SD card/USB) and their folders, Up, New folder, Cancel, Use this folder — and hands back a **real absolute path**. From then on a picked folder is the same on both platforms: `picked_roots.rs` adds it to our scope and remembers it in `data.db`; the Files tab lists it again after a restart (`loadSavedRoots`, ids `ext:<path>`, so tags keyed by root id persist); SQLite databases in it and web apps use it through the ordinary file commands. **Persistent on both platforms** (desktop picks used to last one session). The ×/`remove_picked_root` **revokes it at once**. Rust starts the Android dialog over JNI and **polls** a static result string (`pending` → `picked:<path>` / `cancelled` / `error:<message>`) — no native callback needed. It needs Android's **All files access** (`MANAGE_EXTERNAL_STORAGE`, Android 11+; on 10 and older the classic READ/WRITE_EXTERNAL_STORAGE with `requestLegacyExternalStorage`), asked for the first time a folder is picked: the app opens that system settings page and on coming back continues, or reports "Storage access wasn't granted…". **Google Play restricts this permission** (a declaration and approval are needed); for sideloaded or personal builds it is fine. Verified on the emulator (API 34): the first-use permission flow, browsing, New folder, cancel/back, denied access, read/write/mkdir/rename, SQLite in a picked folder, the scope boundary, immediate revocation (read, list, write and SQLite all refused right after forgetting) and picking the same folder again in the same session, persistence across restarts. Not run: the Android 10-and-older permission path. Real deletes are permanent, as on desktop.

**Sending bytes to the backend.** Android's WebView can't hand a POST body to a custom protocol, so Tauri's IPC there falls back to postMessage, where a `Uint8Array` becomes a JSON array of numbers — 20 MB is tens of millions of JSON values (11 s and a huge memory spike in testing). Commands that take a file's bytes (`filen_write_file`, `filen_cache_write`, `save_to_device`) therefore read them through `ipc.rs` (`body_bytes`, `field`), which accepts the raw body + percent-encoded headers (desktop), or a JSON object `{ ...arguments, data: "<base64>" }` (Android; ~1 s for 20 MB), and the frontend calls them through `invokeWithBytes` (`src/lib/ipcBytes.ts`). A new upload-style command must do the same, and web apps sending big files on Android should send base64 that way too. (The fs plugin's own writes — the Files tab on the user folder — still use the plugin's array path on Android.) Responses are unaffected: raw `ArrayBuffer` responses work everywhere.

**Not done:** a full-screen mode; iOS (`secure_store` has an error stub; the Xcode project doesn't exist).

## System apps and Notes

A **system app** is an app that ships inside this one: a page of the admin-app's own Vite project under `system/<id>/index.html` (its React code in `src/system/<id>/`), listed in the Rust catalog `system_apps::APPS` (`id`, `name`, `entry`) and as a `rollupOptions.input` entry in `vite.config.ts` (the two must agree — the multi-page build puts each in `dist/system/<id>/`). The set is fixed: there is no way for a user to add one, and the System Apps tab (first tab, the default) lists the catalog by name — `list_system_apps`, so an app shows there even before it has a window. **Adding a system app** means: the folder above, the catalog entry, the `input` entry, and a `cargo build` after `npm run build`.

The whole window machinery is the user apps' one, kept separate by a `kind` (`user`|`system`) on `secondary_windows` rows: the `list_/open_new_/add_…entry/close_all_/suspend_all_` commands take an optional `kind` (all kinds when omitted — the data-wipe path closes everything), `reopen_secondary_window` needs only the guid (the row says what to show), and the admin-app's `AppsTab` is one component with a `kind` prop and its own saved orderings (`systemAppsTab.*` vs `windowsTab.*`). A system window stores `system:<id>` as its relative path (also the key of its app state, tab icons and app version), so nothing can be confused with a user app's html path. Tabs work identically — `init_window_tab`, `update_tab_resource`, `submit_resource_icons`, `activate_tab`, the `codeSnippets` in the init response. **Closing a tab** (`close_tab`, the × on a tab item in either tab page) deletes the tab and its tags; if it is the tab an *open* window is showing, that window is also **suspended** (entry and other tabs kept, `reopen_secondary_window` brings it back with a fresh tab), and closing any other tab leaves windows alone. "The tab a window is showing" is `SecondaryWindowsState::current_tabs`, set by `init_window_tab` and dropped when the window goes away.

**Switching tabs is an event** — the same for system apps and user apps. `activate_tab` on a tab of an *open* window sends that window (only) the **`tab-navigate`** event (`secondary_windows::EVENT_TAB_NAVIGATE`), whose payload is exactly what `init_window_tab` answers with — `{ tabGuid, resourceId, codeSnippets }`, the tab's own stored resource id (empty for a tab never used) — and the page **shows that tab in place; it is not reloaded**. An app with several tabs must therefore handle it (`onTabNavigate` in `src/lib/secondaryWindows.ts`; `TabLib.openTab(params, version, type, onNavigate)` for the samples, whose default handler starts the page over at its own address). **Attach the listener before calling `init_window_tab`** (`await onTabNavigate(…)` first) so no event can be missed. A window that isn't open is simply opened, and its page's init response says which tab it is. The activated tab is also left *pending* for the window, so if its page loads again (a reload the app does itself in response, or the person pressing reload) its init binds to that tab instead of creating another. **Listen on the page's own webview window** (`getCurrentWebviewWindow().listen(…)`, `webviewWindow.getCurrentWebviewWindow()` in the samples), never the global `listen`: a global listener also hears events sent to *other* windows (found live: it made another window reload and create an extra tab). Notes handles it by switching to the tab's place (`system:notes?s=…` in its resource id), keeping each tab's own place; its editor keeps the source of the file it holds, so a switch can't redirect a save.

**A system app is not the admin-app.** Admin identity is **path-based**, not origin-based: `window_host::is_admin_url` is true only for the frontend's root page (`/`, `/index.html`), `is_system_url` for pages under `/system/`, and navigation is confined per kind (`Allowed{user,system,admin}`: a user window reaches only `csuser`, a system window only its own pages, the main window the admin-app's). A system window gets exactly the user apps' capabilities (+ `system-apps.json`), never `filen_login`, data-folder or deploy commands — verified live: Notes is refused `filen_logout`/`delete_app_data` like a user app. On Android, where every page shares one webview, the same address check is what `require_admin`/`require_trusted` rely on.

**Notes** (`src/system/notes/`) is a *unified file manager* whose sources are folders on this device (the user folder and picked folders, through the ordinary `fs_*` commands) and the connected Filen accounts (through the cache below), behind one `FileSource` interface (`sources.ts`) — so copy/cut/paste works between any two of them (read + write; same-source cut is a rename). It lists **paginated** (client-side, the page size being the global one), fetches a local folder's sizes/dates only for the page on screen, edits text files (≤ 2 MB, UTF-8), uploads, exports (`save_to_device`), renames, deletes. Per Filen account it shows the **cache interval** selector (incl. "Never (available offline)"), the cache's freshness (or "Offline — showing the listing as it was"), "Clear the cache", and the **branch** bar (switch, new, changes, commit — asking before overwriting on conflict — discard). Each Notes tab is a *place*: its resource id is `system:notes?s=<source>&b=<branch>&p=<path>` (`tabs.ts`), updated (and put in the page's own address) as the person navigates, so activating, cloning or reloading a tab returns to it; the window manager's tab icon distinguishes local / Filen / branch. Notes also remembers the last place in its own app state, for a tab that doesn't name one.

## The Filen cache (`files/`)

`files_cache.rs` (the `Cache`, in `HostState`-style managed state), with `filen_cache.rs` as its commands (`filen_cache_account/_set_interval/_clear/_list/_read/_write/_mkdir/_rm/_rename/_branches/_create_branch/_branch_changes/_commit_branch/_discard_branch`, same shapes as the `filen_*` ones, plus an optional `branch`; no credential ever reaches a window). Layout inside `files/` (built with folder pairs — see below):

```
files/data.db                     listings, metadata, per-account settings, branch changes
files/a/NNN/c/…                   cached CONTENT of account NNN, at its Filen paths
files/a/NNN-filen@@<email>@@<id>/ empty: says whose NNN is
files/b/NNN/MMM/…                 what branch MMM of account NNN has changed
files/b/NNN/MMM-<branch name>/    empty: says which branch MMM is
```

- **A cache, not a sync.** Nothing is fetched until asked: listing a folder fetches and remembers that listing; opening or exporting a file fetches and remembers its content. Everything remembered — listings, metadata and contents — expires after the account's **cache interval** (default 1 hour, chosen per account in Notes) and is then fetched again; with the interval turned off (`ttlSecs` = `null`) nothing ever expires, which is how a person makes things available offline. If Filen can't be reached, an expired listing/file is served marked *stale* rather than failing. Writes to the account itself go straight to Filen and update the cache.
- **Branches** are the git-like alternative: a set of local changes (files written, folders made, things deleted) kept under `b/` and in `data.db` until *committed* (applied to Filen, then the branch is deleted) or *discarded*. Reading through a branch shows Filen's cached state with the branch's changes on top. A commit first checks that Filen still looks as it did when each change was made; if not, it applies nothing and returns the `conflicts` unless `force`. A branch's name is any valid file name of ≤ 100 characters and is its folder's readable half.
- **Lifecycle.** Connecting an account creates its two folders (`ensure_account`); disconnecting it (`filen_logout`) deletes both — its cached files and every branch — and its rows in `files/data.db` (`forget_account`); "Delete app data" and "clear the custom data folder" remove `files/` with the rest (after closing the cache's database — `Cache::close` — since Windows can't delete an open file), and relocating the data folder switches to the `files/` inside the new one, exactly as it does for `admin/`.
- The whole thing is tested without a network (`Remote` trait, in-memory remote): TTL expiry, offline stale serving, write-through, branch overlay/commit/conflict/discard, lifecycle. Live-verified on desktop through the Notes UI with the `filen_*` IPC faked (the UI's interval, branch, commit-conflict-then-force, discard, stale/offline flows) — **not** against a real Filen account this time.

**Folder pairs** (`folder_pairs.rs`; the strategy is in `docs/strategies/folder-pairs-strategy.md`): to make a folder that a program can address by a short name and a person can identify by a long one, create two siblings — `NNN` (the data folder; three digits, zero-padded) and `NNN-<full name part>` (an empty marker whose name says what `NNN` is). `NNN` is one more than the highest `NNN-…` already in the parent (computed from a listing of the parent, never remembered), so an index freed by deleting the highest pair may be reused. For accounts the part is `filen@@<email>@@<user id>`; for branches it is the branch's name. Use it for anything new that follows the same need.

## Links planted in `user/`

A directory junction or symlink planted inside `user/` (web apps can't create one — no command does — but the OS user, an unzip or a `git clone` can) is **refused in every direction**: the scope follows it to its real location, so listing, reading or creating files through a link that leads outside is an error (this used to be a gap with the fs plugin, which only resolved paths that already existed). The link itself can still be removed or renamed from inside, and its target is never touched. Tested with real symlinks (unit tests) and a Windows junction (live). On Android the `user` folder is in the app's private storage, so only `adb run-as` on a debug build (or root) can plant a link at all.

## Building and running (the admin-app is the frontend)

`csdrive-webhost-tauriapp` is a standard Tauri project: the frontend (the admin-app: React + Vite + TypeScript) at its root and the Rust backend in `src-tauri/`. `tauri.conf.json` points `frontendDist` at `../dist`, which Tauri embeds into the binary at compile time, so it is in every installer with no separate file and no network access — and there is no way for a user or a web app to swap it out, because it isn't a file in the data folder. (Its saved UI state is keyed by `layout::ADMIN_APP_ID`.)

- **Develop:** `cd csdrive-webhost-tauriapp && npm install && cargo tauri dev` — Vite on `:1420` with hot reload (`devUrl`), the app loading it, `devCsp` in force.
- **Installer:** `cargo tauri build` (runs `npm run build` first, via `beforeBuildCommand`, and turns on Tauri's `custom-protocol` feature so the embedded frontend is used). Android: `cargo tauri android build …` (see "Android").
- **Multi-page build:** `vite.config.ts` builds one html page per app — the admin-app (`index.html`) and each system app (`system/<id>/index.html`, see "System apps and Notes") — into `dist/`; Tauri embeds them all.
- **Run the embedded frontend without an installer:** `npm run build`, then in `src-tauri`: `cargo run --features tauri/custom-protocol`. A plain `cargo run` is Tauri's *dev mode*: it loads `devUrl` and needs Vite running — that is Tauri's normal behaviour.
- `cargo build`/`check`/`test` need `dist/index.html` to exist (Tauri embeds it at compile time); `build.rs` stops with the command to run if it doesn't.

## Deploying apps

`csdrive-webhost-userapps/<name>/index.html` (none exist yet — the registry is currently empty, and the Deploy dialog says so) is source for a small standalone app that the admin-app's Files tab can *deploy*: pick "Deploy apps…" from the toolbar (available in any folder browsable by the file manager, not just the root), choose an app from the list, confirm or edit the destination folder name (defaults to `<name>`, the folder it sits under in `csdrive-webhost-userapps/`; rejected if a file/folder of that name already exists at the current location), and the admin-app creates that folder under the current location and writes the app's `index.html` into it — using the same generic `mkdirRoot`/`writeRootTextFile` root-relative file operations as the rest of the Files tab, not a separate Rust-side "deploy" command.

Each deployable app's `index.html` is embedded into the Tauri binary at compile time (`csdrive-webhost-tauriapp/src-tauri/src/deployable_apps.rs`, via `include_str!`) and exposed to the frontend via two read-only commands, `list_deployable_apps` and `get_deployable_app_html`. Adding a new deployable app means: create `csdrive-webhost-userapps/<name>/index.html`, add an entry to `deployable_apps::REGISTRY` (plus an `include_str!` for its `index.html`), and `cargo build`.

## Tags

Tags (`window_tags` table) are not specific to windows: `guid` is any opaque id — a window, tab group, tab, or, in the Files tab, a file-manager root (keyed `root:<rootId>`, e.g. `root:user`; picked `ext:` roots are remembered, so their tags persist with them; forgetting a root leaves its tags in the database, and they reappear if the same folder is picked again). **Everywhere tags appear they must be editable and sortable**, which is why every place renders them through the one shared `components/Tags.tsx` `TagList` component rather than its own markup: click a badge to edit its text/colors, drag badges (or use the arrows in the edit dialog) to reorder, × to remove. Backend commands: `list_tags`, `add_window_tag`, `update_window_tag`, `reorder_window_tags`, `remove_window_tag`; order is the `sort_order` column (new tags go last). Any new place that shows tags should use `TagList` too.

**Root tags** are the tags of a guid derived from a root (`src/lib/rootTags.ts`): `root:<rootId>` for a folder on this device (`root:user`, `root:ext:<path>`), `root:filen:<userId>` for a Filen account. Every place that shows the root shows the same tags — the Files tab's root switcher and the **tab items in the System Apps tab**: a Notes tab (its resource id names its source, `rootOfTab`) shows two captioned lines, **Root** (the root's tags) and **Tab** (its own), so the two sets can't be mistaken for each other. Both are editable from there. A tab that shows no root keeps the single tag line.

## Seeding demo data for the User Apps tab

`csdrive-webhost-tauriapp/src-tauri/examples/seed_demo_data.rs` populates the real `data.db` with demo data for the 9 sample apps in `user/qwer/` (`index1.html`-`index9.html`), for stress-testing the User Apps tab's nested windows/tab-groups/tabs UI at scale. To run it after a reset (or any time):

```
cd csdrive-webhost-tauriapp/src-tauri
cargo run --example seed_demo_data
```

It requires `data.db` to already exist and `user/qwer/index1.html`..`index9.html` to already be deployed (run the app once, and copy `sample-apps/qwer/` into the real `user/qwer/` folder, before running the script). It finds the real data folder itself the same way the app does, including a relocated custom data folder. Layout it creates: one `secondary_windows` entry per app, except `index1.html` which gets 10; the first of those 10 windows gets 10 `tab_groups`; the first of those groups gets 100 `tabs`. Safe to re-run — every row it creates is tagged `seeded:qwer-demo-data`, and each run starts by deleting only rows carrying that tag before recreating them, so it never touches any other window/tab/tag you created yourself.
